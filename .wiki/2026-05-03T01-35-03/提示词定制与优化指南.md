# 提示词定制与优化指南

提示词模板是 wiki-cli 文档生成质量的核心杠杆。理解了这四个模板文件的设计哲学，你就掌握了调整整个工具输出的能力——从文章风格、分析深度到内容结构，全在掌控之中。

## 四模板解耦架构

`prompts/` 目录下的四个文件构成一个 2×2 矩阵，按**阶段**（outline / page）和**角色**（system / user）两个维度解耦：

| 文件 | 角色 | 阶段 | 核心职责 |
|------|------|------|----------|
| `outline-system.md` | 系统提示 | 大纲生成 | 定义代码分析者的身份、工具集与分析框架 |
| `outline-user.md` | 用户提示 | 大纲生成 | 提供本次分析任务的上下文与输出格式指令 |
| `page-system.md` | 系统提示 | 页面生成 | 定义写作者的身份、写作原则与质量标准 |
| `page-user.md` | 用户提示 | 页面生成 | 提供本次写作的元数据、交叉引用列表与具体任务 |

[来源](prompts) — 四个模板文件的实际内容可直接查看。

这一设计的核心思想是：**system 模板定义「谁在写 + 怎么写」，user 模板定义「写什么 + 约束条件」**。修改 system 模板影响的是风格和深度，修改 user 模板影响的是输入信息量。

## outline vs page：两次完全不同的人格

对比 `outline-system.md` 和 `page-system.md`，你会看到两套完全独立的人格设定：

### 角色身份

- **outline-system** 定义的作者是「资深软件工程师兼技术文档专家」，工作方式是「拆解复杂代码库」、「洞察设计哲学」。
- **page-system** 定义的作者是「架构分析型技术作者」，工作基于「第一性原理：先抓核心逻辑，再展开实现细节」。

### 工具权限

- **outline-system** 配备完整的 8 个只读代码分析工具（`list_directory`、`read_file`、`git_log` 等），允许 LLM 像开发者一样探索仓库。
- **page-system** 仅声明「先提问再调工具，只获取最低必要片段」的策略，不列出具体工具——因为页面生成阶段理论上不需要再探索仓库，所有信息已通过 user 模板的 `availablePages` 和 `pageTask` 注入。

### 分析/写作框架

- **outline-system** 使用 4 步分析框架：① 高层愿景 → ② 架构深度剖析 → ③ 受众分析 → ④ 生成 JSON 目录。
- **page-system** 使用 **Diátaxis 框架** + 叙事节奏（吸引→兴趣→欲望→行动）+ 视觉规范（Mermaid 图表、表格、粗体） + 证据标准（源码引用）+ 交叉引用要求。

### 输出形态

- **outline-system** 要求严格输出 JSON，无额外文字。
- **page-system** 要求输出完整的 Markdown 文档。

[来源](prompts/outline-system.md) | [来源](prompts/page-system.md)

## 变量占位符清单与注入时机

模板引擎使用 `{{变量名}}` 语法进行变量插值。`fillPrompt` 函数通过正则全局替换实现注入，未匹配的变量会原样保留（不会被替换为空字符串）[来源](src/ai/prompts.ts#L14-L20)。

### outline-system.md 占位符

| 占位符 | 值来源 | 注入时机 |
|--------|--------|----------|
| `{{workDir}}` | `resolve(process.cwd())` | Phase 1 开始前，`generateOutline()` 函数内 |
| `{{os}}` | `` `${process.platform} ${process.arch}` `` | 同上 |

### outline-user.md 占位符

| 占位符 | 值来源 | 注入时机 |
|--------|--------|----------|
| `{{workDir}}` | 同上 | 同上 |
| `{{os}}` | 同上 | 同上 |
| `{{lang}}` | `config.lang`（用户配置的语言） | 同上 |

[来源](src/commands/generate.ts#L88-L91)

### page-system.md 占位符

| 占位符 | 值来源 | 注入时机 |
|--------|--------|----------|
| `{{workDir}}` | `resolve(process.cwd())` | Phase 2，逐页生成时 `generateOne()` 函数内 |
| `{{os}}` | `` `${process.platform} ${process.arch}` `` | 同上 |
| `{{pageTitle}}` | `topic.title`（从大纲解析得到） | 同上 |
| `{{audienceLevel}}` | `topic.level`（从大纲解析得到，如"中级""高级"） | 同上 |

### page-user.md 占位符

| 占位符 | 值来源 | 注入时机 |
|--------|--------|----------|
| `{{workDir}}` | 同上 | 同上 |
| `{{pageTitle}}` | `topic.title` | 同上 |
| `{{audienceLevel}}` | `topic.level` | 同上 |
| `{{pageSlug}}` | `toSlug(topic.title)`（slug 化后的标题） | 同上 |
| `{{projectSummary}}` | **硬编码为空字符串 `''`** | 同上 |
| `{{lang}}` | `config.lang` | 同上 |
| `{{availablePages}}` | 由所有大纲 topics 动态拼接的列表字符串 | 同上 |
| `{{pageTask}}` | `topic.task`（大纲生成时 LLM 写入的指令） | 同上 |

## 定制建议：四类修改场景

### 1. 修改大纲生成的文档结构风格

`outline-system.md` 中的「4 步分析框架」直接决定了 LLM 如何理解仓库并生成目录结构。如果你想改变文档的分类方式：

- **当前框架**：高层愿景 → 架构剖析 → 受众分析 → JSON 输出。这生成的是「入门指南 + 深入探索」二分结构。
- **替换为其他框架**：例如替换成「功能概览 → 核心 API → 最佳实践 → 附录」的四段式，或「概念 → 教程 → 参考 → 解释」的 Diátaxis 结构。
- **操作**：修改 `prompts/outline-system.md` 中「## 分析框架」部分的内容，并同步调整 JSON 输出格式要求。

### 2. 修改页面生成的写作质量

`page-system.md` 的「内容原则」「视觉规范」「证据标准」直接控制了每篇文档的写作风格：

- **叙事节奏**（吸引→兴趣→欲望→行动）适合面向开发者的技术文档。替换为「问题→原因→方案→验证」序列会产生更技术化的风格。
- **证据标准**（每节末尾标注源码引用）是当前最严格的要求。移除或放宽此约束可提升写作速度但降低可验证性。
- **视觉规范**（Mermaid 图表、表格）增加生成时间。如果追求速度，可以移除这些要求。

### 3. 修改交叉引用的格式

`page-system.md` 中定义了 `[](page_slug)` 的交叉引用格式，`page-user.md` 则通过 `{{availablePages}}` 注入所有可用页面列表。如果你想改用 GitHub Flavored Markdown 的 `[title](path)` 格式，需要同时修改 system 模板中的引用语法说明。

### 4. 补充 `projectSummary` 注入

`page-user.md` 中声明了 `{{projectSummary}}`，但源码中对应值为空字符串 `''`。这是现成的扩展点：修改 `generate.ts` 中 `pageUserVars` 的 `projectSummary` 字段，填入从 README.md 读取的摘要或从 package.json 提取的描述。

## 关键警告：变量名一致性

这是最容易踩坑的地方。`fillPrompt` 函数是纯文本替换——它只做全局正则替换 `{{变量名}}`。这意味着：

**如果你在模板中新增了一个 `{{newVar}}` 占位符，但忘记在 `prompts.ts` 或 `generate.ts` 的变量对象中添加对应键，该占位符会原样输出在 prompt 中**（因为 `fillPrompt` 不会替换未匹配的变量，也不会报错）[来源](tests/prompts.test.ts#L17-L19)。

更隐蔽的问题是**前后命名不一致**：例如你在 `page-system.md` 中使用 `{{pageTitle}}`，但在 `generate.ts` 的变量对象中写作 `pageTitle`（一致，没问题）。但如果你在某处用了 `{{task}}` 而在另一处用了 `{{pageTask}}`，LLM 收到的是未经渲染的原始模板文本。

**最佳实践清单**：
1. 修改或新增模板占位符后，立即检查 `generate.ts` 中对应阶段的变量对象。
2. 变量名使用 camelCase，保持 system 和 user 模板之间的命名风格统一。
3. 运行测试确保 `fillPrompt` 按预期工作——`prompts.test.ts` 覆盖了基础替换场景，你可以扩展它来测试新变量。
4. 如果删除了某个占位符，同步从变量对象中移除对应键，避免多余的字符串传递。
