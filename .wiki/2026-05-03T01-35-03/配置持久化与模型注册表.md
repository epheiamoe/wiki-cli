配置持久化与模型注册表是 wiki-cli **配置子系统**的两大支柱。前者负责将用户的提供商、模型、API Key 等选择写入文件系统，在会话间保持状态；后者维护一份内置的模型清单，驱动交互式配置向导的选项列表。两者都集中在 `src/config/` 目录下，仅有两个文件：`config-store.ts`（逻辑）和 `default-models.json`（数据）。

---

## WikiCliConfig：六字段的配置契约

**WikiCliConfig** 接口定义了持久化配置的完整形状，共 6 个字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `provider` | `string` | 提供商名称，如 `"OpenAI"`、`"Anthropic"` |
| `baseUrl` | `string` | API 端点地址，每个提供商在模型注册表中预定义 |
| `model` | `string` | 模型标识，如 `"gpt-5.5"`、`"claude-opus-4-7"` |
| `apiKey` | `string` | 用户的实际 API 密钥 |
| `lang` | `string` | 文档语言，如 `"zh"`、`"en"` |
| `jsonMode?` | `boolean` | 可选字段，见下文 JSON mode 三态逻辑 |

[来源](config-store.ts#L6-L12)

这些字段由交互式配置向导逐一收集，最终由 `saveConfig` 序列化为 JSON。

## 读写流程：loadConfig / saveConfig

配置文件的存储路径为 `~/.wiki-cli/config.json`，通过 node:os 的 `homedir()` 和 node:path 的 `join` 拼合而成：

```typescript
const CONFIG_DIR = join(homedir(), '.wiki-cli');
const CONFIG_PATH = join(CONFIG_DIR, 'config.json');
```

[来源](config-store.ts#L19-L20)

**`loadConfig`** 的流程是：先检查文件是否存在（`existsSync`），不存在则返回 `null`；存在则用 `readFile` 读取并 `JSON.parse`，任何异常（格式错误、权限不足等）都吞掉并返回 `null`。这种"静默失败"的设计意味着：首次使用时，配置不存在是预期状态，上层逻辑据此进入配置向导。

**`saveConfig`** 的流程是：先用 `mkdir({ recursive: true })` 确保目录存在，再用 `writeFile` 写入格式化的 JSON（缩进 2 空格）。`recursive: true` 保证了首次使用无需手动创建 `~/.wiki-cli/`。

[来源](config-store.ts#L28-L38)

## 模型注册表：default-models.json

`loadDefaultModels()` 直接返回导入的 JSON 数组，没有中间处理逻辑。这个数组的类型是 **ModelEntry**，每个条目包含 5 个字段：

```typescript
export interface ModelEntry {
  provider: string;    // 提供商名称
  model: string;       // 模型标识
  baseUrl: string;     // API 基础 URL
  description: string; // 人类可读的描述
  pricingHint?: string;// 价格提示（可选）
}
```

[来源](config-store.ts#L14-L18)

当前内置了 **7 大提供商、21 个模型**，涵盖 OpenAI（GPT 系列）、Google Gemini、Anthropic Claude、xAI Grok、DeepSeek、Kimi (Moonshot)、Mistral。具体模型列表见 [支持的LLM提供商一览](支持的llm提供商一览.md)。

值得注意的设计决策是：**模型数据与逻辑分离**。`default-models.json` 是一个纯 JSON 文件，不包含任何代码逻辑。这使得未来更新模型列表时无需改动 TypeScript 源码，也方便外部工具解析。

[来源](default-models.json)

## 查询辅助：getProviders / getModelsByProvider

这两个函数服务于配置向导的下拉菜单生成：

- **`getProviders(models)`** — 遍历模型数组，提取唯一的 `provider` 值，返回去重后的提供商列表。
- **`getModelsByProvider(models, provider)`** — 按提供商名称过滤，返回该提供商下的所有模型条目。

[来源](config-store.ts#L44-L51)

它们是纯函数式的过滤逻辑，没有任何缓存或副作用，每次调用都全量遍历数组。在模型条目数量有限（当前 21 条）的背景下，性能开销可以忽略。

## JSON mode 三态逻辑

**`supportsJsonMode(provider)`** 是配置子系统中最有趣的一个函数。它返回 `boolean | undefined`，对应三种状态：

| 返回值 | 含义 | 适用场景 |
|---|---|---|
| `true` | 该提供商已知支持 JSON mode | OpenAI、DeepSeek、xAI Grok、Mistral、Kimi (Moonshot) |
| `false` | 该提供商已知不支持 JSON mode | Google Gemini、Anthropic 等 |
| `undefined` | 未知，需要在运行时询问用户 | 提供商为 `"Custom"` 时 |

[来源](config-store.ts#L22-L26)

判断依据是一个硬编码的 **Set**：

```typescript
const JSON_MODE_PROVIDERS = new Set([
  'OpenAI',
  'DeepSeek',
  'xAI Grok',
  'Mistral',
  'Kimi (Moonshot)',
]);
```

不在集合中的已知提供商（如 Google Gemini、Anthropic）直接返回 `false`。而对于 `"Custom"` 提供商——代表用户自定义接入任意兼容 API——返回 `undefined`，由交互式配置向导额外弹出询问"是否启用 JSON mode？"。

这种三态设计的精妙之处在于：它区分了"已知不支持的确定状态"和"未知的不确定状态"，避免了对自定义端点武断地下结论。配置向导根据 `undefined` 走询问分支，而 `true` / `false` 则静默应用默认行为。

[来源](config-store.ts#L22-L26)

## 设计要点总结

1. **文件路径固化**：`~/.wiki-cli/config.json` 是唯一配置存储位置，无环境变量覆盖，保持简单。
2. **模型与代码解耦**：模型数据以纯 JSON 文件独立存在，增删模型无需重编译。
3. **静默容错**：`loadConfig` 内部捕获所有异常，上层统一按"无配置"处理，避免配置损坏导致程序崩溃。
4. **JSON mode 保守策略**：对已知提供商直接判定，对自定义端点退回询问用户，不做假设。
