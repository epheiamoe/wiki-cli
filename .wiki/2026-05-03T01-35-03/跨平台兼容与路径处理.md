# 跨平台兼容与路径处理

wiki-cli 的目标用户可能分布在 Windows、macOS 和 Linux 任意一种操作系统上，这意味着三处显式的 `process.platform` 分支、一组通过 `execSync` 发起的 Shell 调用、以及所有路径工具函数都必须在不同分隔符约定和 Shell 语法下保持正确行为。

## 平台检测的三处锚点

项目中一共有三处 `process.platform` 引用，分别服务于**浏览器启动**和**LLM 上下文注入**两个不同目的。

**浏览器启动命令**（`commands/browse.ts`）是唯一需要处理三者差异的业务逻辑：

```typescript
const start =
  process.platform === 'win32' ? 'start' :
  process.platform === 'darwin' ? 'open' : 'xdg-open';
execSync(`${start} ${url}`, { stdio: 'ignore' });
```

[来源](src/commands/browse.ts#L131-L134)

Windows 用 `start`（启动默认浏览器并立即返回）、macOS 用 `open`（遵循 URL Scheme 注册）、Linux 用 `xdg-open`（桌面环境无关的抽象层）。`execSync` 在这里接收的是用户态命令而非路径参数，Shell 环境稳定，不存在跨平台转义风险。若调用失败（如 Linux 无桌面环境），`catch` 块仅打印提示，不会中断进程。

**LLM 提示词上下文注入**（`commands/generate.ts`）在两处将 `process.platform` 与 `process.arch` 拼接为字符串 `"${process.platform} ${process.arch}"` 注入到模板变量 `os` 中。第一处位于 `generateOutline` 函数（第 127 行），第二处位于 `generateOne` 内部（第 398 行）。这个字符串直接嵌入 System Prompt 和 User Prompt，目的是让 LLM 了解仓库运行环境的操作系统和 CPU 架构，从而在生成代码示例时自动选择匹配的路径风格（如 Windows 用 `\\` 而 Unix 用 `/`）或可执行文件后缀（如 `.exe`）。两处注入使用完全相同的表达式，但作用于不同的模板上下文：大纲阶段告诉 LLM "你要为一个 `{os}` 上的仓库写文档"，页面生成阶段告诉 LLM "当前页面对应 `{os}` 环境"。[来源](src/commands/generate.ts#L127-L128) [来源](src/commands/generate.ts#L398-L398)

## `execSync` 调用 Git 命令的 Shell 转义风险

`ai/tools.ts` 中的 `gitLog`、`gitShow`、`gitRemoteInfo` 三个工具函数通过 `execSync` 执行 Git 命令。与 browse.ts 不同，这些调用涉及**路径参数的字符串拼接**：

```typescript
// gitLog
let cmd = `git log --oneline --max-count=${count}`;
if (path) cmd += ` -- "${path}"`;

// gitShow
let cmd = `git show ${object}`;
if (path) cmd += `:${path}`;

const output = execSync(cmd, { encoding: 'utf-8', cwd: process.cwd() });
```

[来源](src/ai/tools.ts#L272-L292)

这里存在两个跨平台风险点。第一，**路径分隔符**：LLM 传入的 `path` 参数是字符串，在 Windows 上 Git Bash 或 cmd.exe 对反斜杠的解释不同——路径 `src\utils` 在 cmd.exe 中被视为合法相对路径，但在 Git Bash 中 `\u` 可能被转义为 Unicode。第二，**Shell 元字符**：`cmd` 被直接传递给 `execSync` 的默认 shell（Windows 上是 `cmd.exe`，Unix 上是 `/bin/sh`），如果 LLM 构造的 `path` 包含空格、`&`、`|` 或 `$`，在未经过 `shellQuote` 转义的情况下可能引发命令注入或语法错误。当前代码仅对路径加了双引号（`"${path}"`），这只覆盖了空格，不覆盖其他元字符。若要在生产级修复，应考虑用 `spawnSync` 配合参数数组来彻底规避 Shell 注入。

## 路径清理函数：`sanitizePath` 的分隔符语义

`commands/browse.ts` 中的 `sanitizePath` 函数用于 HTTP API 的路径安全过滤：

```typescript
function sanitizePath(rawPath: string): string | null {
  const normalized = normalize(rawPath).replace(/^(\\.\\.(\\/|\\\\))+/g, '');
  const resolved = resolve(PROJECT_ROOT, normalized);
  if (!resolved.startsWith(PROJECT_ROOT + sep) && resolved !== PROJECT_ROOT) {
    return null;
  }
  return normalized;
}
```

[来源](src/commands/browse.ts#L243-L249)

关键设计细节：`normalize` 来自 `node:path`，在 Windows 上会将 `/` 统一转为 `\\`，在 POSIX 上保持 `/`。这使得正则 `(\\/|\\\\)` 需要同时匹配两种分隔符才能正确剥离前导 `../` 遍历攻击。**但**在 Windows 上，`normalize('..\\..\\foo')` 产生 `'..\\..\\foo'`，正则 `/^(\.\.(\\/|\\\\))+/g` 匹配到 `..\\..\\`，剩余 `'foo'` 被传入 `resolve`，这一流程在 Windows 上工作正常。在 POSIX 上，`normalize('../../foo')` 产生 `'../../foo'`，同样被正确剥离。该函数通过 `PROJECT_ROOT + sep` 比对来解决分隔符不匹配问题——`sep` 是平台原生分隔符。这是一个经过深思熟虑的跨平台路径安全守卫。

## `toSlug` 的字符过滤而非路径处理

`file.ts` 中的 `toSlug` 函数与路径分隔符无关：

```typescript
export function toSlug(title: string): string {
  return title
    .toLowerCase()
    .replace(/[^\w\u4e00-\u9fff]+/g, '-')
    .replace(/^-+|-+$/g, '')
    || 'untitled';
}
```

[来源](src/utils/file.ts#L42-L48)

它只处理**标题文本**（如"跨平台兼容与路径处理"），将其转为安全文件名片段。正则 `[^\w\u4e00-\u9fff]` 保留字母数字下划线和中文字符，其余全部转为连字符。这个函数不操作文件系统路径，不存在分隔符问题。

`writeTextFile` 中使用了 `sep` 来拆分路径以创建目录：

```typescript
await ensureDir(filePath.split(sep).slice(0, -1).join(sep));
```

[来源](src/utils/file.ts#L18-L18)

`filePath.split(sep)` 按平台原生分隔符拆分路径，取出除最后一段外的所有目录部分交给 `ensureDir`（内部调用 `mkdir({ recursive: true })`）。这个设计确保无论用户在 Windows 上使用 `\\` 还是 Unix 上使用 `/`，目录提取逻辑都能正确工作。`mkdir` 本身在 `recursive: true` 下也跨平台兼容。

## Node.js 版本与环境要求

`package.json` 声明 `"node": ">=18"`。[来源](package.json#L20-L22) Node.js 18 是第一个将 `node:path` 模块的跨平台行为完全稳定的 LTS 版本（包括 `normalize` 和 `resolve` 对 Windows UNC 路径的支持）。低于 18 的版本在 Windows 上处理长路径（>260 字符）和 UNC 路径时可能表现不一致。所有 `node:fs/promises` API 也在 Node 18 中达到稳定。

## 总结

| 位置 | 跨平台维度 | 安全措施 | 风险级别 |
|------|-----------|---------|---------|
| `browse.ts` 浏览器启动 | 命令名称 | `try/catch` 静默降级 | 低 |
| `generate.ts` osInfo | 提示词上下文 | 无（仅信息传递） | 无 |
| `tools.ts` git 命令 | Shell 路径拼接 | 双引号包裹 | 中（Shell 注入） |
| `browse.ts` sanitizePath | 路径分隔符 | `normalize` + 双分隔符正则 + `sep` 比对 | 低 |
| `file.ts` writeTextFile | 路径分割 | `split(sep)` + `mkdir recursive` | 低 |

风险最高的代码段是 `tools.ts` 中的 `gitLog` 和 `gitShow`——若 LLM 在 Agent 循环中构造了包含 Shell 元字符的路径字符串，当前的双引号保护可能不足。其他位置均已通过 Node.js 标准库的跨平台抽象获得基本安全保障。
