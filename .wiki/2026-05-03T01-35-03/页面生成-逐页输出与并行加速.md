# 页面生成：逐页输出与并行加速

`generatePages` 是 Wiki 生成的第二阶段核心函数。它将[大纲生成：代码理解与结构化输出](大纲生成-代码理解与结构化输出.md)阶段产出的 `Topic[]` 逐条转化为 Markdown 文件，写入 `.wiki/temp` 目录。该函数同时实现了两种执行模式——串行流式与并行非流式——用户通过交互式问答选择。其设计意图是在"可见性"与"吞吐量"之间取得平衡。

## 核心循环：从 Topic 到 Markdown 文件

函数接收四个参数：`LLMClient` 实例、配置对象、工作目录、Topic 列表，以及包含 `parallel` 和 `concurrency` 字段的选项对象。返回值为生成失败的 Topic 列表，供调用者决定是否重试 [来源](src/commands/generate.ts#L383-L386)。

处理流程分为三步筛选与过滤：

1. **过滤非 group 的 topic** — group 是仅用于索引分组的逻辑节点，不产出独立页面。若 `retryList` 存在（来自失败重试），则直接使用该列表替换全部 topic 列表 [来源](src/commands/generate.ts#L387-L388)。
2. **跳过已生成页面** — 若目标文件已存在于 `.wiki/temp/{slug}.md` 且非重试模式，则跳过该 topic。这个机制支撑了[断点续传与失败重试](断点续传与失败重试.md)的"不重复已成功页面"语义 [来源](src/commands/generate.ts#L398-L403)。
3. **构建并发送双提示词模板** — 每个 topic 独立渲染 `page-system.md` 和 `page-user.md` 两个模板，拼装为 `ChatMessage[]` 后调用 LLM [来源](src/commands/generate.ts#L415-L437)。

双模板的分工延续了[提示词模板引擎](提示词模板引擎.md)的设计：`page-system.md` 承载作者人格与写作原则，`page-user.md` 承载本次生成的任务描述和上下文。二者的变量集合不同——`pageSysVars` 包含 `workDir`、`os`、`pageTitle`、`audienceLevel`，`pageUserVars` 额外注入 `pageSlug`、`lang`、`availablePages`、`pageTask` [来源](src/commands/generate.ts#L405-L426)。

## availablePages：自动化的交叉引用注入

**availablePages** 是 `generatePages` 实现跨页面智能引用的关键机制。它在循环之外、单页生成之前构建一次，作为所有 topic 共享的全局上下文：

```typescript
const availablePages = allTopics
  .filter(t => !t.isGroup && t.slug)
  .map(t => `- slug: ${t.slug}.md | 标题: ${t.title} | 简介: ${(t.description || t.task || '').slice(0, 80)}`)
  .join('\n');
```

该字符串被注入到 `page-user.md` 模板的 `{{availablePages}}` 占位符处 [来源](prompts/page-user.md#L13)。`page-user.md` 的指令要求 LLM 在写作时，若提及任何其他页面标题或内容，必须使用 `[页面标题](slug.md)` 格式的超链接。通过将全部页面的 slug、标题和简介摘要一次性提供给 LLM，模型得以在生成过程中自主判断何时应该引用哪些页面，实现**自动化的交叉引用网络**，无需人工维护链接关系 [来源](src/commands/generate.ts#L390-L394)。

值得注意的是，简介信息截取至多 80 字符，以控制提示词长度在 token 预算内。

## runConcurrent：带限流的并发执行器

当用户选择并行模式时，`generatePages` 将所有 pageTopics 映射为无参异步任务数组，交由 `runConcurrent` 执行 [来源](src/commands/generate.ts#L451-L455)。

```typescript
async function runConcurrent(tasks: (() => Promise<void>)[], concurrency: number): Promise<void> {
  const running = new Set<Promise<void>>();
  const queue = [...tasks];

  while (queue.length > 0 || running.size > 0) {
    while (running.size < concurrency && queue.length > 0) {
      const task = queue.shift()!;
      const p = task().finally(() => running.delete(p));
      running.add(p);
    }
    if (running.size > 0) {
      await Promise.race(running);
    }
  }
}
```

该实现是一个经典的 **Semaphore 模式** 的变体：

- 用 `Set<Promise<void>>` 跟踪正在运行的任务。
- 每次循环尽量填满"槽位"（`running.size < concurrency` 时启动新任务）。
- `Promise.race` 等待任意一个任务完成，释放槽位后启动下一个。
- `task().finally(...)` 确保无论成功还是失败，任务都会从 `running` 集合中移除。

用户通过交互式问答设置的并发数在 1-10 之间。交互逻辑位于 `generateCommand` 中，通过 `inquirer` 的 `validate` 函数限制上限 [来源](src/commands/generate.ts#L56-L68)。

## 串行 vs 并行：流式与速度的权衡

选择串行还是并行的决策体现在 `collectFullResponse` 的第四个参数 `stream` 上：

| 维度 | 串行模式 | 并行模式 |
|------|---------|---------|
| `stream` 参数 | `true` | `false` |
| 执行方式 | `for` 循环逐页等待 | `runConcurrent` 并发执行 |
| 输出效果 | 每个 token 实时打印到控制台 | 仅页面完成时输出 `[i/N] Generated: title` |
| 速度 | 慢（串行等待 + 流式逐 token） | 快（多任务并行 + 批量获取） |
| 适用场景 | 调试、观察生成过程、模型行为分析 | 生产运行、长文档批量生成 |
| 工具调用可视化 | 每次工具调用都有 `logToolCall` / `logToolResult` 输出 | 无中间过程输出 |

在串行模式下，每个 topic 的生成过程完全可见：LLM 的推理过程（`reasoning_content`）、内容输出、以及工具调用（如需读取源码来补充细节）都会实时打印，帮助开发者观察模型行为。并行模式牺牲了这种可见性以换取吞吐量——每个页面仅在成功写入文件后输出一条成功日志 [来源](src/commands/generate.ts#L441-L448)。

两种模式共享同一个 `collectFullResponse` 函数。该函数内部通过 `stream` 参数选择调用 `client.chatStream`（流式迭代器）还是 `client.chat`（非流式单次请求），但无论哪种模式，都保留了相同的**工具调用循环**（最多 30 次迭代），确保 LLM 可以在生成过程中调用文件系统工具集来查阅源码 [来源](src/commands/generate.ts#L233-L376)。

## 失败收集与重试入口

函数始终返回 `failed: Topic[]`。失败的定义是 `collectFullResponse` 返回 `null`（可能是 API 错误、网络中断或工具调用异常）。在 `generateCommand` 中，如果 `failed` 非空，会触发交互式确认，用 `retryList` 重新调用 `generatePages`，形成**递归式的失败重试循环**。完整的重试策略分析见[断点续传与失败重试](断点续传与失败重试.md) [来源](src/commands/generate.ts#L88-L113)。
