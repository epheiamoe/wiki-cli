# 测试策略与覆盖

wiki-cli 采用 **Vitest** 作为测试框架，在 `tests/` 目录下部署了 6 个测试文件。测试策略遵循 **纯函数全覆盖 + 高层集成抽样** 的原则——对无副作用的工具函数追求边界条件穷举，对有外部依赖的高层模块则通过 mock 或真实文件系统验证核心路径与错误路径。

## 测试环境配置

`vitest.config.ts` 声明了三项核心配置：

| 配置项 | 值 | 含义 |
|--------|-----|------|
| `environment` | `'node'` | 使用 Node 运行时，无 DOM 模拟 |
| `globals` | `true` | `describe` / `it` / `expect` 等全局可用，无需手动 import |
| `include` | `['tests/**/*.test.ts']` | 测试文件匹配模式 |

[来源](../vitest.config.ts#L1-L7)

## 六个测试文件一览

### 1. `config-store.test.ts` — 配置读写与模型注册表

验证 `src/config/` 下的 `default-models.json` 文件结构完整性：

- 是合法的 JSON 数组，条目数 ≥20
- 每条记录包含 `provider`、`model`、`baseUrl`、`description` 字段
- 内置 7 大 provider 全部存在：OpenAI、Google Gemini、Anthropic、xAI Grok、DeepSeek、Kimi、Mistral
- 关键模型名存在性校验
- `getProviders()` 返回无重复的 provider 列表
- `getModelsByProvider()` 按 provider 过滤正确

[来源](../tests/config-store.test.ts#L1-L67)

### 2. `file.test.ts` — 文件操作工具函数

测试 `src/utils/file.js` 导出的纯函数：

- **目录/文件操作**：`ensureDir` 递归创建目录 → `writeTextFile` + `readTextFile` 读写一致性 → `removeDir` 递归删除
- **`toSlug` 边界覆盖**：空输入返回 `'untitled'`、中文保持原样、英文转小写加连字符、混合内容、多余分隔符合并、首尾清理、特殊符号过滤
- **`getTimestamp`**：验证 `YYYY-MM-DDTHH-mm-ss` 格式和年份正确性

测试在 `os.tmpdir()` 下创建临时目录，确保不污染项目文件。所有操作使用真实文件系统（非 mock）。

[来源](../tests/file.test.ts#L1-L65)

### 3. `llm-client.test.ts` — API 通信与自动重试

通过 mock `globalThis.fetch` 模拟各种网络场景，覆盖 `LLMClient` 的两种调用模式：

- **`chatStream`（流式）**：验证 content 块、tool_call 块、reasoning_content 块、done 信号的分发顺序
- **`chat`（非流式）**：验证请求体格式（model、messages、tools）、响应解析
- **错误处理**：401 → 直接报错不重试；502/503 → 自动重试后成功；`ECONNRESET` → 指数退避重试后恢复
- **reasoning_content 回传**：验证 assistant 消息携带推理内容时，请求体中保留该字段

每个测试通过 `beforeEach`/`afterEach` 保存和恢复原始 fetch，做到完全隔离。

[来源](../tests/llm-client.test.ts#L1-L183)

### 4. `outline-parser.test.ts` — JSON/XML 大纲解析

测试 `stripCodeFence`（消除 Markdown 代码围栏）和局部的 `parseOutlineJson` 函数：

- 标准 JSON → 正确解析 sections → topics 层级
- **围栏兼容**：裸 JSON、```` ```json ```` 包裹、额外前后文本 → 均能正确提取
- **字段降级**：`description` / `task` / `brief` 三种字段名的优先级回退逻辑
- **容错**：无效 JSON、空字符串、结构不匹配 → 返回空数组
- **group 类型**：`type: "group"` 条目正确标记为 `isGroup`

[来源](../tests/outline-parser.test.ts#L1-L125)

### 5. `prompts.test.ts` — 模板渲染引擎

测试 `fillPrompt` 的变量插值机制，这是一个经典的**纯函数**测试：

- 单个变量替换 → 多变量替换 → 同一变量多处出现
- 缺失变量保持 `{{name}}` 原样，不报错
- 空模板 / 空变量对象 / 中文变量值

[来源](../tests/prompts.test.ts#L1-L28)

### 6. `tools.test.ts` — 工具函数执行引擎

覆盖 `toolDefinitions` 和 `executeToolCall` 两个核心导出：

- **schema 验证**：8 个工具全部导出、每个工具的 `parameters.type` 为 `'object'`
- **成功路径**：`list_files`（含扩展名过滤）、`read_file`（含行范围）、`search_in_files`（匹配/不匹配）、`list_directory`（树结构）
- **错误路径**：文件不存在、路径不存在、工具名不识别、缺少必填参数返回 `{ type: 'error' }`

使用 `mkdtempSync` 在临时目录搭建迷你文件系统，验证工具操作真实文件。

[来源](../tests/tools.test.ts#L1-L117)

## 两层测试覆盖模式

从测试对象性质看，6 个文件可归入两个层级：

| 层级 | 特点 | 代表文件 | 测试手法 |
|------|------|----------|----------|
| **纯函数层** | 无副作用，输入→输出 | `file.test.ts`、`prompts.test.ts`、`outline-parser.test.ts` | 边界条件枚举，无 mock |
| **集成层** | 依赖外部系统（网络/文件系统） | `llm-client.test.ts`、`tools.test.ts`、`config-store.test.ts` | mock fetch / 真实临时目录 |

这种分层保证了：底层工具函数在隔离环境中被穷尽验证，而高层模块的关键交互路径（网络请求、文件读写、配置加载）在可控条件下得到覆盖。
