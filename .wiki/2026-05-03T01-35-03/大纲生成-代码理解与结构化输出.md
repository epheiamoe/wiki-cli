# 大纲生成：代码理解与结构化输出

## 第一阶段的战略定位

在 Wiki 生成的两阶段管线中，**大纲生成**是第一阶段的**核心**。它不直接生成任何 Markdown 文本，而是让 LLM 通过工具调用**自主探索仓库**，输出一份结构化的 JSON 大纲。这份大纲随后驱动第二阶段——逐页生成。两阶段设计的关键收益在于：大纲先行保证了文档**整体结构的连贯性**，避免逐页生成时各自为政的内容碎片化。

[来源](../src/commands/generate.ts#L61-L62)

## 流程总览：从提示词到结构化JSON

`generateOutline` 的完整执行路径可分为四个阶段：

```mermaid
flowchart TD
    A[加载outline-system.md] --> B[加载outline-user.md]
    B --> C[构建消息队列: system + user]
    C --> D{LLM对话循环}
    D -->|最多25轮| E[collectFullResponse]
    E --> F[parseOutlineJson 尝试解析]
    F -->|成功| G[保存_outline.json<br>返回Topic[]]
    F -->|失败| H[将assistant响应追加到消息队列]
    H --> D
    D -->|25轮耗尽| I[最终尝试解析finalContent]
    I -->|失败| J[返回空数组]
```

[来源](../src/commands/generate.ts#L126-L172)

### 第1步：提示词加载与变量注入

函数首先构建两个模板的渲染变量：

```typescript
const osInfo = `${process.platform} ${process.arch}`;
const outlineSysVars = { workDir, os: osInfo };
const outlineUserVars = { workDir, os: osInfo, lang: config.lang };
```

- `outline-system.md` —— 定义 LLM 的角色（资深软件工程师 + 技术文档专家）、可用工具集、四步分析框架（高层愿景 → 架构剖析 → 受众分析 → 生成目录）、以及期望的 JSON 输出结构。
- `outline-user.md` —— 用户消息，告知 LLM 要分析哪个仓库，并提示"使用工具探索项目布局"。

**关键设计决策**：system 模板固定分析框架，user 模板提供上下文变量（工作目录、语言）。这种解耦使得 system 提示词可在不同项目中复用，user 提示词只需变更变量值。详见 [提示词模板引擎](提示词模板引擎.md)。

[来源](../src/commands/generate.ts#L128-L133)

### 第2步：LLM 对话循环（最多25轮）

```typescript
const maxIterations = 25;
for (let i = 0; i < maxIterations; i++) {
    const fullContent = await collectFullResponse(client, messages, config, true, useJsonMode);
    // 尝试解析
    const topics = parseOutlineJson(fullContent);
    if (topics.length > 0) return topics;
    // 否则继续对话
    messages.push({ role: 'assistant', content: fullContent });
}
```

循环的**退出条件**只有两个：(1) `parseOutlineJson` 返回非空数组（解析成功）；(2) 达到 25 轮上限后，对 `finalContent` 做最终解析尝试。

**为什么需要多轮对话？** LLM 可能在一轮输出中包含了 JSON 之外的思考过程、或者 JSON 格式有误。将 assistant 响应追加回消息队列后，LLM 可在下一轮修正输出。这是一种**自愈机制**——让 LLM 看到自己上一轮的输出，自我纠错。

[来源](../src/commands/generate.ts#L142-L171)

### 第3步：工具调用引擎（collectFullResponse）

`collectFullResponse` 实现了一个**内层工具循环**（最多 30 次工具迭代），与 LLM 提供商的 function calling API 深度集成。它支持两种模式：

| 模式 | 实现方式 | 适用场景 |
|------|----------|----------|
| 流式 | `client.chatStream()` + for-await | 默认，提供实时输出反馈 |
| 非流式 | `client.chat()` | JSON mode 启用时降级 |

内层循环的伪逻辑：

```
while (iteration < 30) {
    调用 LLM API（流式或非流式）
    收集 content + tool_calls
    if (无工具调用) → 返回 content（本轮完成）
    else → 逐个执行工具，将结果追加为 tool 角色消息，继续循环
}
```

工具执行结果以 `role: 'tool'` 的形式追加到消息队列，LLM 在下一轮迭代中看到工具返回的数据，继续分析或生成最终输出。支持的 8 个只读工具详见 [工具调用与Agent循环](工具调用与agent循环.md)。

[来源](../src/commands/generate.ts#L178-L268)

## parseOutlineJson：三层回退解析防御

这是整个大纲生成中最**关键的容错机制**。LLM 输出的文本可能含有各种格式瑕疵，`parseOutlineJson` 用三层防御逐级净化：

```typescript
function parseOutlineJson(text: string): Topic[] {
    // 第1层：去除代码块标记
    let cleaned = stripCodeFence(text);
    // 第2层：正则提取 JSON 对象
    const jsonMatch = cleaned.match(/\{[\s\S]*\}/);
    if (!jsonMatch) return [];
    // 第3层：JSON.parse + 字段校验
    try {
        const parsed = JSON.parse(jsonMatch[0]);
        if (!parsed.sections || !Array.isArray(parsed.sections)) return [];
        // ... 逐字段解析为 Topic[]
    } catch { return []; }
}
```

[来源](../src/commands/generate.ts#L174-L213)

### 第1层：stripCodeFence 去除代码块标记

```typescript
// 来自 llm-client.ts
export function stripCodeFence(text: string): string {
    return text.replace(/^```(?:json)?\s*\n?/gm, '')
               .replace(/\n?```\s*$/g, '')
               .trim();
}
```

这个正则匹配所有以 `` ``` `` 或 `` ```json `` 开头的行，以及末尾的闭合标记。即使 LLM 把 JSON 包裹在 Markdown 代码块中（这在 system 模板中明确禁止，但 LLM 有时仍然会做），也能被剥离。

[来源](../src/ai/llm-client.ts#L52-L55)

### 第2层：正则提取 JSON 对象体

```typescript
const jsonMatch = cleaned.match(/\{[\s\S]*\}/);
```

`[\s\S]` 匹配包括换行符在内的任意字符，`*` 贪婪匹配确保捕获从第一个 `{` 到最后一个 `}` 之间的全部内容。这能处理 LLM 在 JSON 前后添加了任何额外解释文字的情况——只提取最外层的大括号块。

### 第3层：JSON.parse + 字段结构校验

即使通过了前两层，JSON 本身也可能是无效的或结构不符合预期。第三层做了三件事：

1. **`JSON.parse`** —— 标准 JSON 解析，语法错误直接 `catch` 返回 `[]`。
2. **根结构校验** —— `parsed.sections` 必须存在且为数组，否则返回 `[]`。
3. **遍历 sections** —— 每个 section 需有 `name`，其 `topics` 必须为数组；每个 topic 根据 `type` 字段分流处理。

Topic 解析分流逻辑：

```typescript
if (item.type === 'group') {
    topics.push({
        title: item.title, level: '', slug: '',
        section: sectionName, isGroup: true,
    });
} else {
    const description = item.description || item.brief || '';
    const task = item.task || item.brief || '';
    topics.push({
        title: item.title,
        level: item.level || '中级',
        slug: toSlug(item.title),
        section: sectionName,
        description, task,
    });
}
```

**兼容性设计**：同时支持 `description` + `task` 和旧版单字段 `brief`。如果 LLM 只提供了 `brief`，它会被同时赋值给 `description` 和 `task`，确保向后兼容。

[来源](../src/commands/generate.ts#L195-L213)

## Topic 接口的字段语义

```typescript
interface Topic {
    title: string;       // 页面显示标题
    level: string;       // 难度：初学/中级/高级
    slug: string;        // URL友好的唯一标识（由 toSlug 自动生成）
    section: string;     // 所属章节名（如"入门指南"、"深入探索"）
    description?: string;// 30-80字页面简介，供侧边栏和其他页面引用
    task?: string;       // 50-150字LLM指令，仅目标页面接收
    isGroup?: boolean;   // 是否为分组标记（非实际页面）
}
```

**`section` 字段**是分组的核心机制。system 提示词要求 LLM 将目录划分为 `入门指南` 和 `深入探索` 两个 section。每个 topic 通过 `section` 字段归属到其中一个。在后续生成索引时，`generateIndex` 函数按 `section` 去重分组：

```typescript
const sections = [...new Set(topics.map(t => t.section).filter(Boolean))];
```

这种设计意图在于：**文档天然具有从入门到深入的渐进结构**。`入门指南` 包含概览、快速开始、安装配置等新手友好内容；`深入探索` 覆盖架构、高级配置、贡献指南等进阶主题。两个 section 在侧边栏中自动渲染为两个分组标题。

**`isGroup` 字段**处理 section 内部的子分组。例如在"深入探索"中，可以将多个相关 topic 归入一个"核心模块"组，在侧边栏中显示为次级标题而非页面链接。

**`slug` 字段**由 `toSlug(item.title)` 自动生成，转换为 URL 安全的标识符，用于生成文件名和链接路径。详见 [文件系统工具集](文件系统工具集.md)。

[来源](../src/commands/generate.ts#L7-L15)

## 从 JSON 大纲到侧边栏导航

大纲生成完成后，`generateOutline` 将原始 JSON 写入 `_outline.json` 暂存，同时返回 `Topic[]` 给上层命令流程。`generateCommand` 随后将 topics 传递给 `generatePages` 和 `generateIndex`。

`generateIndex` 使用相同的 `section` 分组逻辑生成 `index.json`：

```typescript
const jsonOut: { sections: { name: string; topics: any[] }[] } = { sections: [] };
```

这个 `index.json` 最终被 [侧边栏导航与索引解析](侧边栏导航与索引解析.md) 读取，渲染为左侧导航菜单。从大纲生成 → 页面生成 → 索引生成 → 侧边栏渲染，**`section` 字段是贯穿始终的组织线索**。

[来源](../src/commands/generate.ts#L348-L369)

## 失败路径分析

`generateOutline` 有三种失败模式：

| 失败场景 | 行为 |
|----------|------|
| LLM 在25轮内始终未输出有效 JSON | 返回 `[]`，`generateCommand` 检测到 `topics.length === 0` 后 `process.exit(1)` |
| LLM 返回空响应或 API 错误 | `collectFullResponse` 返回 `null`，触发 `break` 退出循环，尝试最终解析 |
| JSON 结构合法但 sections 为空 | `parsed.sections` 为数组但长度为 0，返回 `[]`，同上处理 |

所有失败最终汇聚到 `generateCommand` 的检查点：

```typescript
if (topics.length === 0) {
    logError('Failed to generate outline. No topics found.');
    process.exit(1);
}
```

这意味着大纲生成是整个管线的**刚性依赖**——没有大纲就无法进入页面生成阶段。

[来源](../src/commands/generate.ts#L63-L67)

## 设计要点总结

1. **双循环架构**：外层25轮对话循环 + 内层30次工具循环，提供了充足的互动空间让 LLM 探索仓库并自我纠错。
2. **三层解析防御**：从代码块剥离 → 正则提取 → 结构化校验，逐层收紧，容忍 LLM 输出的各种不规范格式。
3. **section 作为组织原语**：`section` 字段是跨阶段的文档结构标识，从大纲 → 索引 → 侧边栏始终一致。
4. **兼容性设计**：`description/task` 与旧版 `brief` 的双轨支持降低了提示词变更的迁移成本。
