# 项目结构与模块职责

仓库的源代码和资源配置遵循**分层职责**原则组织：`src/` 目录承载全部业务逻辑，`prompts/` 目录存放解耦的提示模板，`tests/` 目录镜像核心模块的测试覆盖。构建产物输出到 `dist/`，通过 `package.json` 的 `bin` 字段暴露为命令行工具。

```
wiki-cli/
├── src/                     # 源代码根目录
│   ├── cli.ts               # 入口 + 命令路由
│   ├── commands/            # 三条子命令
│   │   ├── config.ts        # 配置向导
│   │   ├── generate.ts      # Wiki 生成核心流程
│   │   └── browse.ts        # 本地浏览服务器
│   ├── ai/                  # LLM 通信层
│   │   ├── llm-client.ts    # OpenAI 兼容 API 客户端
│   │   ├── prompts.ts       # 提示词模板引擎
│   │   └── tools.ts         # 工具定义 + 执行引擎
│   ├── config/              # 持久化配置
│   │   ├── config-store.ts  # 配置读写 + 模型注册表
│   │   └── default-models.json  # 内置 7 大提供商模型列表
│   └── utils/               # 跨模块工具
│       ├── file.ts          # 文件系统操作封装
│       └── progress.ts      # 控制台进度与日志美化
├── prompts/                 # 提示模板（与代码解耦）
│   ├── outline-system.md    # 大纲阶段 system prompt
│   ├── outline-user.md      # 大纲阶段 user prompt
│   ├── page-system.md       # 页面阶段 system prompt
│   └── page-user.md         # 页面阶段 user prompt
├── tests/                   # 6 个 Vitest 测试文件
│   ├── config-store.test.ts
│   ├── file.test.ts
│   ├── llm-client.test.ts
│   ├── outline-parser.test.ts
│   ├── prompts.test.ts
│   └── tools.test.ts
├── dist/                    # TypeScript 编译输出
├── package.json
├── tsconfig.json
└── vitest.config.ts
```

## CLI 入口：`cli.ts`——命令调度中心

`src/cli.ts` 是整个应用的**唯一入口**。它使用 Commander.js 框架做三件事：

1. **注册元信息**：`program.name('wiki-cli').description(...).version('1.0.0')` 定义 CLI 的身份标识。 [来源](src/cli.ts#L8-L11)
2. **注册三条子命令**：`config`、`generate`、`browse` 分别绑定到 `commands/` 目录下对应的处理函数。每条命令的 `action` 回调外围包裹了 `try/catch`，将异常统一交由 `logError` 输出并 `process.exit(1)`。 [来源](src/cli.ts#L13-L48)
3. **空参数回退**：若用户仅输入 `wiki-cli` 不带参数，自动调用 `program.outputHelp()` 打印帮助信息。 [来源](src/cli.ts#L50-L52)

核心设计原则：cli.ts **只做路由，不做业务**。任何数据读取、API 调用、文件操作都委托给下层模块。

更详细的命令路由与生命周期见 [命令调度与生命周期](命令调度与生命周期.md)。

## 三个子命令：各司其职

### `config`——交互式配置向导

`src/commands/config.ts` 支持两种模式：

- **全参数模式**：如果用户通过 `--provider` `--base-url` `--model` `--api-key` `--lang` 提供了全部参数，直接调用 `saveConfig()` 跳过交互。 [来源](src/commands/config.ts#L13-L22)
- **交互模式**：使用 `inquirer` 依次引导用户选择提供商、模型，输入 API Key、语言偏好。对于 JSON mode 能力，已知提供商自动判定，未知（Custom）则询问用户。 [来源](src/commands/config.ts#L24-L102)

关键职责：它不内置任何 API 逻辑，纯粹是配置的**收集与持久化**。底层存储方式见 [配置持久化与模型注册表](配置持久化与模型注册表.md)。

### `generate`——两阶段 Wiki 生成引擎

`src/commands/generate.ts` 是项目**最复杂的模块**，驱动完整的两阶段流程：

- **Phase 1（大纲生成）**：调用 `generateOutline()`，LLM 通过多轮工具调用探索仓库，输出 JSON 格式的文档大纲。`collectFullResponse()` 是核心编排函数，管理流式/非流式响应、工具调用循环、JSON 解析回退。 [来源](src/commands/generate.ts#L83-L162)
- **Phase 2（页面生成）**：调用 `generatePages()`，遍历大纲中的每个 Topic，调用 LLM 逐页生成 Markdown。支持串行（流式输出）和并行（`runConcurrent` 控制并发数）两种模式，并提供断点续传和失败重试。 [来源](src/commands/generate.ts#L272-L360)

该模块引用了 `ai/` 层（LLM 客户端、提示词引擎、工具执行引擎）和 `utils/file.ts`（文件写入、目录创建）。详细的两阶段逻辑见 [大纲生成：代码理解与结构化输出](大纲生成-代码理解与结构化输出.md) 和 [页面生成：逐页输出与并行加速](页面生成-逐页输出与并行加速.md)。

### `browse`——本地 HTTP 预览服务器

`src/commands/browse.ts` 启动一个基于 Node.js 原生 `http` 模块的静态服务器：

- 读取 `.wiki/` 目录下最新一个时间戳子目录
- 解析 `index.json`（或回退 `index.md` XML 格式）生成侧边栏导航
- 提供 `/api/page/`（Markdown 渲染为 HTML）和 `/api/source/`（源码高亮显示）两条 API 路由
- 自动检测空闲端口（从 3000 开始递增）
- 调用平台默认浏览器打开，通过 `execSync` 跨平台兼容 `start` / `open` / `xdg-open`

服务器实现和路由分发详见 [HTTP服务器与路由分发](http服务器与路由分发.md)，侧边栏逻辑见 [侧边栏导航与索引解析](侧边栏导航与索引解析.md)。

## AI 层：与 LLM 对话的三重封装

### `llm-client.ts`——OpenAI 兼容 API 客户端

核心类是 `LLMClient`，提供两种调用方式：

- **`chat()`**：非流式，一次请求获取完整响应，返回 `LLMResponse`（含 content、tool_calls）。 [来源](src/ai/llm-client.ts#L148-L196)
- **`chatStream()`**：流式，以 `AsyncGenerator<StreamChunk>` 形式逐块产出 content、reasoning、tool_call、error 四种类型的数据块。 [来源](src/ai/llm-client.ts#L83-L146)

两者共用 `buildRequest()` 构建请求体，支持工具定义注入和 `response_format: json_object` 模式。自动重试逻辑对 5xx 和 429 状态码执行指数退避（最多 3 次）。 [来源](src/ai/llm-client.ts#L37-L54)

详细通信协议见 [LLM客户端通信协议](llm客户端通信协议.md)。

### `prompts.ts`——提示词模板引擎

三个函数构成解耦的渲染管线：

- `loadPrompt(filename)`：从 `prompts/` 目录读取模板文件
- `fillPrompt(template, vars)`：将模板中的 `{{varName}}` 替换为实际值
- `renderPrompt(filename, vars)`：上述两步的组合

模板文件路径通过 `__dirname` 相对定位，确保编译后 `dist/ai/prompts.js` 能正确找到同级 `prompts/` 目录。 [来源](src/ai/prompts.ts#L6-L8)

提示词模板的设计哲学和定制方法见 [提示词模板引擎](提示词模板引擎.md) 和 [提示词定制与优化指南](提示词定制与优化指南.md)。

### `tools.ts`——工具定义 + 执行引擎

定义 8 个 LLM 可调用的只读工具，每个工具包含 JSON Schema 参数声明和对应的执行函数：

| 工具名 | 用途 |
|--------|------|
| `list_directory` | 递归遍历目录树，支持 `max_depth` |
| `list_files` | 按扩展名过滤文件列表 |
| `read_file` | 按行范围读取文件内容 |
| `search_in_files` | 正则搜索文件内容 |
| `git_log` | 获取 Git 提交历史 |
| `git_show` | 查看某次提交的文件内容 |
| `git_remote_info` | 获取远程仓库信息 |
| `dotenv_template` | 读取 `.env.example` |

所有工具返回统一的 `ToolResult` 类型（`{ type: 'success' | 'error', data: any }`），`executeToolCall()` 函数按名称路由到具体处理器。 [来源](src/ai/tools.ts#L238-L244)

工具调用与 Agent 循环机制详见 [工具调用与Agent循环](工具调用与agent循环.md)。

## 配置层：文件系统持久化

`src/config/config-store.ts` 管理用户配置的生命周期：

- 配置文件存储在 `~/.wiki-cli/config.json`（`homedir()` 确保跨平台兼容） [来源](src/config/config-store.ts#L25-L26)
- `loadConfig()` 读取并解析 JSON，失败返回 `null` [来源](src/config/config-store.ts#L40-L46)
- `saveConfig()` 先递归创建目录再写入文件 [来源](src/config/config-store.ts#L48-L51)
- `default-models.json` 定义了 7 个提供商共 21 个模型条目，每个包含 `provider`、`model`、`baseUrl`、`description`、`pricingHint` [来源](src/config/default-models.json)

辅助函数 `supportsJsonMode()` 通过硬编码的 Set 判断提供商是否已知支持 JSON mode，Custom 提供商返回 `undefined`（由交互流程询问用户）。 [来源](src/config/config-store.ts#L30-L33)

完整配置架构见 [配置持久化与模型注册表](配置持久化与模型注册表.md)。

## 工具层：文件操作与日志显示

### `utils/file.ts`——跨平台文件系统封装

7 个函数覆盖生成流程的所有文件操作需求：

| 函数 | 职责 |
|------|------|
| `ensureDir` | 递归创建目录 |
| `writeTextFile` | 自动创建父目录后写入文本 |
| `readTextFile` | 读取 UTF-8 文本 |
| `removeDir` | 递归删除目录 |
| `moveDir` | 重命名目录 |
| `getTimestamp` | 生成 ISO 风格时间戳（冒号替换为横线以兼容文件名） |
| `toSlug` | 中文+英文标题 slug 化 |

所有路径操作均基于 Node.js 内置模块，不依赖外部库，确保跨平台兼容性。 [来源](src/utils/file.ts)

### `utils/progress.ts`——控制台美化

基于 `chalk` 和 `ora` 提供 8 个输出函数：

- `logInfo` / `logSuccess` / `logWarning` / `logError`：分别用蓝/绿/黄/红色前缀标记不同级别消息
- `createSpinner`：返回 ora spinner 实例
- `logStreamContent`：以青色输出流式内容
- `logToolCall` / `logToolResult`：格式化工具调用与结果预览

详细的日志设计见 [日志与进度显示系统](日志与进度显示系统.md)。

## prompts/ 目录：与代码解耦的提示模板

4 个 Markdown 文件构成两对 system/user 模板：

```
prompts/
├── outline-system.md    # 定义 LLM 作为代码分析专家的角色和工具使用规则
├── outline-user.md      # 描述仓库路径、语言偏好、输出格式要求
├── page-system.md       # 定义 LLM 作为技术文档写手的角色和写作规范
└── page-user.md         # 包含页面标题、受众级别、交叉引用列表等上下文变量
```

模板中使用 `{{varName}}` 语法标记变量插值点，由 `prompts.ts` 引擎在运行时填充。这种设计让提示词的修改无需重新编译，产品经理或技术作者可直接编辑 Markdown 文件调整文档风格和深度。[来源](prompts/)

## package.json 的 bin 映射

```json
{
  "bin": {
    "wiki-cli": "dist/cli.js"
  }
}
```

`bin` 字段将包名 `wiki-cli` 映射到编译后的入口文件 `dist/cli.js`。npm 安装时（全局 `npm install -g` 或本地 `npx`），Node.js 会在 PATH 中创建一个指向该文件的符号链接。文件首行的 `#!/usr/bin/env node` shebang 告诉系统使用 Node.js 执行此脚本。 [来源](package.json#L8-L10)

构建流程由 `npm run build` 触发 TypeScript 编译器，将 `src/` 下的 TypeScript 文件编译为 `dist/` 目录中的 JavaScript 文件（同时生成 `.d.ts` 类型声明和 `.js.map` 源码映射）。[来源](tsconfig.json#L3-L5)

## 模块依赖关系

```
cli.ts
  ├── commands/config.ts ──────────► config/config-store.ts
  │                                      └── default-models.json
  │
  ├── commands/generate.ts ────────► config/config-store.ts
  │                              ├──► ai/llm-client.ts (LLMClient, stripCodeFence)
  │                              ├──► ai/prompts.ts (renderPrompt)
  │                              ├──► ai/tools.ts (toolDefinitions, executeToolCall)
  │                              └──► utils/file.ts (ensureDir, writeTextFile, ...)
  │
  └── commands/browse.ts ──────────► utils/progress.ts (logInfo, logSuccess, logError)
                                    utils/file.ts (通过 imports 间接使用 Node.js API)

config/config-store.ts ◄────────── commands/config.ts (写入)
                                  commands/generate.ts (读取)

ai/prompts.ts ◄──────────────────── prompts/*.md (文件系统读取)

ai/tools.ts ◄────────────────────── Node.js: fs/promises, child_process, path

utils/progress.ts ◄──────────────── cli.ts, commands/generate.ts, commands/config.ts
                                    commands/browse.ts
```
