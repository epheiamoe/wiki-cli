# 会话管理系统

每次与代码库的 AI 对话都可能产生有价值的探索路径——你可能发现了一个 bug 的根因，或理清了某个模块的调用链。会话管理系统将这些对话持久化，让你可以随时回到任意断点继续追问，甚至跨项目检索所有历史对话。

## Session 接口：五字段模型

会话的核心数据结构十分精简：

```typescript
export interface Session {
  id: string;        // 8 位唯一标识
  created: string;   // ISO 8601 创建时间
  updated: string;   // ISO 8601 最后更新时间
  summary: string;   // 会话摘要（用户首条消息前 60 字符）
  messages: ChatMessage[];  // 消息数组
}
```

五个字段覆盖了会话管理的全部需求：`id` 用于查找和引用，时间戳用于排序和展示，`summary` 提供快速预览，`messages` 则是对话历史的主体。其中 `ChatMessage` 类型来自 LLM 客户端层，包含 `role`、`content`、`tool_calls` 等字段，与 [LLM 客户端：流式与非流式](llm-客户端-流式与非流式.md) 中的消息格式一致。

## 双层存储架构

会话的物理存储采用"本地 + 全局"的双层设计，兼顾项目隔离性与跨项目检索能力。

### 本地层：`.wiki/sessions/{id}.json`

每个会话以独立的 JSON 文件存储在项目目录下：

```
<project-root>/
  .wiki/
    sessions/
      a1b2c3d4.json
      e5f6g7h8.json
```

路径由 `SESSIONS_DIR_REL = '.wiki/sessions'` 加上运行时设置的 `sessionsBaseDir` 拼接而成：

```typescript
function getSessionsDir(): string {
  return join(sessionsBaseDir ?? process.cwd(), SESSIONS_DIR_REL);
}
```

默认情况下 `sessionsBaseDir` 为 `null`，此时 `getSessionsDir()` 回退到 `process.cwd()`，即当前工作目录。这是最常见的场景——你在哪个项目下运行 `wiki-cli ai`，会话就保存在哪个项目的 `.wiki/sessions` 下。

[来源](src/ai/ai-session.ts#L17-L29)

### 全局层：`~/.wiki-cli/sessions-index.json`

全局索引是一个轻量的 JSON 文件，位于用户家目录下，记录了每个会话 ID 与其所属项目的 `sessions` 目录完整路径的映射：

```json
{
  "a1b2c3d4": "/home/user/projects/my-app/.wiki/sessions",
  "e5f6g7h8": "/home/user/projects/another-app/.wiki/sessions"
}
```

索引的读写通过同步 I/O 操作实现，并带有内存缓存：

```typescript
let indexCache: Record<string, string> | null = null;

function readIndex(): Record<string, string> {
  if (indexCache) return indexCache;  // 内存缓存命中
  // 从 ~/.wiki-cli/sessions-index.json 读取
}

function writeIndex(idx: Record<string, string>): void {
  indexCache = idx;  // 更新内存缓存
  // 写入文件
}
```

`INDEX_PATH` 定义为 `join(homedir(), '.wiki-cli', 'sessions-index.json')`。这种设计确保了索引文件独立于任何项目，不会被 `.gitignore` 排除，也不会因项目删除而丢失。

[来源](src/ai/ai-session.ts#L18-L60)

## `setSessionsDir`：切换项目上下文

当 `ai` 命令的 `-C/--dir` 参数指定了不同的工作目录时，系统需要在正确的项目下创建和保存会话。`setSessionsDir` 提供这个能力：

```typescript
export function setSessionsDir(dir: string): void {
  sessionsBaseDir = dir;
}
```

在 `commands/ai.ts` 中，该函数会在命令入口处被调用：

```typescript
const { setSessionsDir } = await import('../ai/ai-session.js');
setSessionsDir(workDir);
```

这行代码发生在工作目录解析（`resolveWorkDir`）之后，确保后续所有 `getSessionsDir()` 调用都指向正确的项目路径。[工作目录解析](工作目录解析.md) 中详细说明了 `-C`、`-u`、`-o` 和 `-b` 参数如何影响最终的 `workDir`。

[来源](src/commands/ai.ts#L87-L89)

## `generateSessionId`：8 位 UUID

会话 ID 通过截取 UUID v4 的前 8 个字符生成：

```typescript
export function generateSessionId(): string {
  return randomUUID().slice(0, 8);
}
```

8 位十六进制字符提供了约 42.9 亿（16⁸）种可能的组合，碰撞概率在实际使用中可忽略。这一设计兼顾了 ID 的**唯一性**和**可读性**——8 字符短 ID 便于在终端中展示和手动输入。

对比：`/load <id>` 命令中用户需要手动输入会话 ID，8 位长度比完整 UUID 的 36 字符友好得多；同时比自增数字 ID 更难被猜测，提供了一定的安全性。

## `saveSession`：索引优先的双写策略

保存会话时，系统遵循"索引优先"的写入策略：

```typescript
export async function saveSession(session: Session): Promise<void> {
  session.updated = new Date().toISOString();

  const idx = readIndex();
  const knownDir = idx[session.id];
  const targetDir = knownDir || getSessionsDir();

  // 确保目标目录存在
  if (!existsSync(targetDir)) await mkdir(targetDir, { recursive: true });

  // 写入会话文件
  await writeFile(join(targetDir, `${session.id}.json`), ...);

  // 如索引中尚无此 ID，补充写入索引
  if (!knownDir) indexAdd(session.id);
}
```

核心逻辑是：**先查索引，索引命中则写入原项目目录，否则写入当前项目目录并补录索引**。这一策略确保了：

1. **会话归属不变**——恢复一个旧会话后，再次保存仍然写回原项目，不会漂移到当前工作目录。
2. **索引最终一致性**——新建会话时先写文件再写索引，索引写入失败不阻塞主流程（`writeIndex` 的 `catch` 块明确标注 `/* non-critical */`），保证会话数据不丢失。

对应的 `loadSession` 也采用类似的**本地优先、索引兜底**的两阶段查找：

1. 先在当前 `getSessionsDir()` 下查找。
2. 找不到时，通过索引查找会话的原始项目目录。

## `listAllSessions`：跨项目遍历

`listAllSessions` 与 `listSessions` 的根本区别在于查找范围：

| 函数 | 数据源 | 项目范围 | 用途 |
|------|--------|----------|------|
| `listSessions` | 当前 `getSessionsDir()` 目录遍历 | 单项目 | CLI 快捷列表 |
| `listAllSessions` | 全局索引逐条加载 | 所有项目 | `--all` 参数触发 |

`listAllSessions` 的实现从全局索引入手，遍历每个映射条目并加载对应的 JSON 文件，同时通过 `dirname(dirname(sessionsDir))` 逆推出项目根目录路径追加到结果中：

```typescript
all.push({
  id,
  created: s.created,
  updated: s.updated,
  summary: s.summary,
  projectDir: dirname(dirname(sessionsDir))  // sessionsDir = <project>/.wiki/sessions
});
```

返回的结果会按 `updated` 时间降序排列，并在 `showSessionsTable` 渲染时按项目分组显示，不同项目之间用粗体项目名分隔。

在 CLI 中，用户通过 `wiki-cli ai --list-sessions` 查看当前项目会话，加 `--all` 后切换为跨项目视图：

```typescript
if (options.listAllSessions) {
  sessions = await listAllSessions();
  console.log(chalk.bold('\n📋 所有项目的会话:'));
} else {
  sessions = await listSessions();
  console.log(chalk.bold('\n📋 保存的会话:'));
}
```

## 完整的 CRUD 操作

系统提供了完整的增删改查接口，所有操作都遵循双层写入原则：

| 操作 | 函数 | 本地文件 | 全局索引 |
|------|------|----------|----------|
| 创建 | `createSession()` | 写入 `.wiki/sessions/{id}.json` | `indexAdd(id)` |
| 读取 | `loadSession(id)` | 本地优先，索引兜底 | 索引辅助定位 |
| 更新 | `saveSession(session)` | 覆盖写入原路径 | 缺失时补充 |
| 删除 | `deleteSession(id)` | `rm({id}.json)` | `indexRemove(id)` |

删除操作同样按"本地→索引"的顺序尝试，任一位置找到文件就执行删除并清理索引。

## 会话的生命周期

完整的会话流程贯穿 [AI 问答](ai-问答.md) 和 [AI 聊天面板：浏览器内对话](ai-聊天面板-浏览器内对话.md) 两种交互模式：

**CLI 模式**（`wiki-cli ai`）：
1. 无 `--session` 参数 → `createSession()` 新建会话
2. 有 `--session <id>` → `loadSession(id)` 恢复历史
3. 每轮对话后 `saveSession(session)` 自动保存
4. 退出时调用 `exitSession` 保存并打印恢复命令
5. 交互过程中支持 `/sessions` 列出、`/load <id>` 切换、`/new` 新建

**浏览器面板**（`wiki-cli browse`）：
1. SSE 端点 `/api/chat/` 的 POST 请求中，从请求体提取 `sessionId`
2. 无 ID 则自动创建，有 ID 则恢复历史
3. 每次流式响应完成后写入 `saveSession`
4. 浏览器端 `localStorage` 持久化当前 `sessionId`，刷新后可恢复
