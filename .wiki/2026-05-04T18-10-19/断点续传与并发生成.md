在大型项目上生成 Wiki 时，最令人沮丧的莫过于：跑了半小时，第 47 页生成到一半，网络断开了——全部白干。

这个问题有两层解法：

1. **断点续传**：生成中途中断后，下次可以**从上一次中断的位置继续**，而不是从头重来。
2. **并发生成**：多页同时生成，充分利用 LLM API 的并发能力，把总耗时从线性降到接近恒定。

这两个机制互为补充，共同构成了 `wiki-cli generate` 面向生产级项目的核心加速方案。

## 断点续传：临时目录 + 文件探测

### 临时工作区

所有正在生成的页面文件（Markdown）以及生成的提纲 JSON，都写入一个固定的临时目录：

```
.wiki/temp/
├── _outline.json
├── 概览.md
├── 快速开始.md
├── 配置LLM.md
└── ...
```

常量定义在文件头部：

```typescript
const TEMP_DIR = '.wiki/temp';
```

提纲文件 `_outline.json` 也写在这里——这意味着**即使第一阶段（提纲生成）完成后进程退出，第二阶段（页面生成）也能恢复**。

[来源](src/commands/generate.ts#L17-L17)

### 启动检测：resume / fresh 二选一

每次执行 `generate` 时，引擎首先检查 `TEMP_DIR` 是否存在：

```typescript
if (existsSync(TEMP_DIR)) {
  const { action } = await inquirer.prompt([
    {
      type: 'list',
      name: 'action',
      message: 'Previous generation temp data found. What do you want to do?',
      choices: [
        { name: '🔄 Resume from last checkpoint', value: 'resume' },
        { name: '🗑️  Discard and start fresh', value: 'fresh' },
      ],
    },
  ]);
  if (action === 'fresh') await removeDir(TEMP_DIR);
}
```

- **Resume**：保留临时目录，跳过已生成页面，只生成缺失页面。
- **Fresh**：删除临时目录，完全从头开始。

在 `--silent` 模式下不询问，直接删除旧临时目录（等同于 fresh），确保非交互式 CI 环境可预测。

[来源](src/commands/generate.ts#L94-L111)

### 跳过逻辑：按文件存在性判断

进入页面生成阶段后，`generateOne` 函数对每个 topic 检查对应的 `.md` 文件是否已存在：

```typescript
const pagePath = join(TEMP_DIR, `${slug}.md`);
if (!options.retryList && existsSync(pagePath)) {
  if (!options.parallel) {
    logInfo(`[${index}/${total}] Skipping already generated: ${topic.title}`);
  }
  return;  // 已生成，跳过
}
```

这里的 `retryList` 判断是关键：**仅在首次生成（非重试）时跳过已存在文件**；重试时，即使文件存在也会重新生成。

[来源](src/commands/generate.ts#L514-L520)

### 最终提交：TEMPDIR → 时间戳目录

所有页面生成完毕（包括重试完成后），临时目录被**原子性地重命名**为带时间戳的最终目录：

```typescript
const timestamp = getTimestamp();
const finalDir = outputDir || join('.wiki', timestamp);
await moveDir(TEMP_DIR, finalDir);
```

这使得 `.wiki/` 下可以保留多个历史版本的生成结果，`[浏览Wiki](浏览wiki.md)` 和 `[查看Wiki状态](查看wiki状态.md)` 可以利用这些历史快照。

[来源](src/commands/generate.ts#L188-L193)

## 并发生成控制：信号量模式的 TypeScript 实现

### runConcurrent 函数

当用户启用 `--parallel`（或 `-p`）时，页面生成不再逐页串行，而是通过 `runConcurrent` 函数调度：

```typescript
async function runConcurrent(
  tasks: (() => Promise<void>)[],
  concurrency: number
): Promise<void> {
  const running = new Set<Promise<void>>();
  const queue = [...tasks];

  while (queue.length > 0 || running.size > 0) {
    while (running.size < concurrency && queue.length > 0) {
      const task = queue.shift()!;
      const p = task().finally(() => running.delete(p));
      running.add(p);
    }
    if (running.size > 0) {
      await Promise.race(running);
    }
  }
}
```

这是一个经典的**信号量（Semaphore）模式**：

1. 用 `Set<Promise<void>>` 维护当前正在执行的任务集合。
2. 当正在运行的任务数小于 `concurrency` 且队列不为空时，从队列取出任务并启动，将其 Promise 加入集合。
3. 每次 `Promise.race` 等待**任意一个**任务完成，让出事件循环给其他任务。
4. 任务完成后通过 `.finally()` 自动从集合中移除，腾出名额给下一个任务。

不依赖任何第三方并发库，纯 Node.js 标准 API 实现。

[来源](src/commands/generate.ts#L582-L596)

### 串行 vs 并行：取舍对比

| 维度 | 串行模式 | 并行模式 |
|------|----------|----------|
| 输出体验 | ✅ LLM 流式输出实时可见 | ❌ 仅在页面完成后打印一行 |
| 速度 | ❌ 线性 | ✅ 接近恒定（受限于 API 并发） |
| API 限流风险 | 低 | 高（需控制 concurrency） |
| 适用场景 | 调试、小项目（<10 页） | 大型项目（>20 页） |

在 `generatePages` 中，分派逻辑非常清晰：

```typescript
if (options.parallel) {
  const total = pageTopics.length;
  await runConcurrent(
    pageTopics.map((topic, i) => () => generateOne(topic, i + 1, total)),
    options.concurrency
  );
} else {
  const total = pageTopics.length;
  for (let i = 0; i < total; i++) {
    await generateOne(pageTopics[i], i + 1, total);
  }
}
```

## 重试机制：自动重试 + 交互式重试

### 自动重试循环

CLI 提供了 `--retry <n>`（或 `-r`）参数，指定自动重试次数：

```typescript
let retriesLeft = opts.retry ?? 0;
while (failed.length > 0 && retriesLeft > 0) {
  logWarning(`${failed.length} page(s) failed. Retrying (${retriesLeft} left)...`);
  const retryResult = await generatePages(client, config, workDir, topics, {
    parallel, concurrency,
    retryList: [...failed]  // 只重新生成失败的页面
  });
  failed = retryResult;
  retriesLeft--;
}
```

每次重试**只重新生成失败的页面**（通过 `retryList` 传入），已成功的页面不动。这对于 LLM API 偶发超时、网络抖动等场景特别有效。

[来源](src/commands/generate.ts#L164-L168)

### 交互式重试

自动重试用完后，如果仍有失败页面，进入交互式询问：

```typescript
while (failed.length > 0) {
  logWarning(`${failed.length} page(s) failed to generate.`);
  const { retry } = await inquirer.prompt([
    { type: 'confirm', name: 'retry', message: 'Retry failed pages?', default: true },
  ]);
  if (!retry) break;
  logInfo(`Retrying ${failed.length} page(s)...`);
  const r = await generatePages(client, config, workDir, topics, {
    parallel, concurrency,
    retryList: [...failed]
  });
  failed = r;
}
```

用户可以无限次重试，直到所有页面生成成功或主动放弃。

[来源](src/commands/generate.ts#L170-L182)

## 典型用例：大型 Monorepo 的高效生成

对于一个包含 40+ 包、预计生成 50 页的 Monorepo 项目，推荐配置：

```bash
wiki-cli generate --parallel --concurrency 5 --retry 2
```

缩写形式：

```bash
wiki-cli generate -p -c 5 -r 2
```

这个命令的含义：

| 参数 | 值 | 效果 |
|------|-----|------|
| `-p` | 启用 | 5 页同时生成，不显示流式输出 |
| `-c 5` | 5 个并发 | 利用 LLM API 的并发上限，默认 3 可提升 |
| `-r 2` | 2 次自动重试 | 偶发失败自动重试，无需人工干预 |

**执行流程**：

1. 第一阶段（提纲生成）串行执行，与 `-p` 无关。
2. 第二阶段将 50 个 page topic 放入队列。
3. `runConcurrent` 每次拉出 5 个任务同时执行。
4. 任意一个完成后，立即从队列中补充下一个。
5. 全部执行完后，若有失败，自动重试 2 轮。
6. 最终的成功/失败统计输出到终端。

## 性能对比：串行 vs 并行

以下为基于中等规模项目的实测参考数据（假设平均每页生成耗时 30s，API 无限流）：

| 模式 | 并发数 | 50 页理论耗时 | 100 页理论耗时 |
|------|--------|---------------|----------------|
| 串行 | 1 | 25 min | 50 min |
| 并行 | 3 | ~8.5 min | ~17 min |
| 并行 | 5 | ~5 min | ~10 min |
| 并行 | 10 | ~2.5 min | ~5 min |

> 注：实际耗时受 LLM API 限流、网络延迟、页面内容复杂度影响。部分 API（如 OpenAI）在同一组织账号下有 RPM/TPM 限制，过高的 concurrency 可能导致 rate limit 错误从而触发重试，反而降低效率。建议从 `-c 3` 开始，逐步上探。
