## 架构总览

Wiki 生成过程被明确拆分为两个独立的阶段，每个阶段对应一个独立的函数和一组 **Prompt 模板**。这种分离不是偶然的——它的设计理由是：**先确定「写什么」，再决定「怎么写」**。

```
        Phase 1                          Phase 2
┌──────────────────────┐     ┌──────────────────────────┐
│  generateOutline()   │────→│    generatePages()       │
│                      │     │                          │
│  LLM + 工具调用      │     │  任务队列调度             │
│  ≤ 25 轮迭代         │     │  并行 / 串行模式         │
│  解析 JSON 大纲      │     │  断点续传 (TEMP_DIR)     │
│  写入 _outline.json  │     │  失败重试                 │
└──────────┬───────────┘     └─────────────┬────────────┘
           │                               │
           ▼                               ▼
    {sections: [...]}              {slug}.md × N
           │                               │
           └───────────┬───────────────────┘
                       ▼
              generateIndex()
                  ↓
             index.json
```

[来源](src/commands/generate.ts#L1-L30)

`generateOutline` 接收一个已初始化的 `LLMClient`、配置对象和仓库工作目录，返回一个 `Topic[]` 数组。它不生成任何文件，只产生一个**结构化的目录蓝图**。

```typescript

```

[来源](src/commands/generate.ts#L169-L171)

#### Prompt 渲染

函数首先加载两个 Prompt 模板，注入运行时变量：

| 模板 | 文件 | 注入变量 |
|------|------|----------|
| 系统提示 | `prompts/outline-system.md` | `workDir`, `os` |
| 用户提示 | `prompts/outline-user.md` | `workDir`, `os`, `lang` |

系统提示定义了 LLM 的角色（资深软件工程师兼技术文档专家），列出了所有可用工具，并给出了四步分析框架（高层愿景 → 架构剖析 → 受众分析 → 生成 JSON 目录）。用户提示则要求 LLM 为指定仓库生成文档目录，并提供了从 `config.lang` 读取的语言设置。

[来源](src/commands/generate.ts#L173-L179) | [来源](prompts/outline-system.md#L1-L10) | [来源](prompts/outline-user.md#L1-L10)

#### 主循环：最多 25 轮

核心循环是一个 **最大 25 次的迭代**，每次迭代调用 LLM 并尝试从响应中解析 JSON 大纲：

```typescript
for (let i = 0; i < maxIterations; i++) {
  // 1. 调用 collectFullResponse → 得到 LLM 的完整回复（含工具调用结果）
  const fullContent = await collectFullResponse(client, messages, config, true, useJsonMode);
  
  // 2. 尝试解析 JSON
  const topics = parseOutlineJson(fullContent);
  if (topics.length > 0) {
    // 成功！保存 _outline.json 并返回
    await writeTextFile(join(TEMP_DIR, '_outline.json'), fullContent);
    return topics;
  }
  
  // 3. 未解析到 JSON → 将回复加入消息历史，继续对话
  messages.push({ role: 'assistant', content: fullContent });
}
```

为什么需要迭代？因为 LLM 可能在第一轮没有足够的信息来生成完整目录——它需要先**探索代码库**。每次迭代都允许 LLM 发起工具调用（读取文件、列出目录、搜索源码等），然后将结果注入上下文，再尝试输出 JSON。

[来源](src/commands/generate.ts#L185-L213)

#### 工具调用的内循环：collectFullResponse

`collectFullResponse` 是 Phase 1 和 Phase 2 共用的**核心收集中介**。它的职责是：给定一组 messages，调用 LLM，**自动处理任意数量的工具调用链**，直到 LLM 产生纯文本回复为止。

```typescript
async function collectFullResponse(
  client: LLMClient,
  messages: ChatMessage[],
  config: WikiCliConfig,
  stream: boolean,
  jsonMode?: boolean
): Promise<string | null> {
  let accumulatedContent = '';
  let iteration = 0;
  const maxToolIterations = 30;

  while (iteration < maxToolIterations) {
    iteration++;
    // 1. 过滤掉 Phase 1 不需要的 Wiki 工具
    const genTools = getFilteredTools().filter(t => 
      !['list_wiki_pages', 'read_wiki', 'search_wiki', 'semantic_search'].includes(t.function.name)
    );
    
    // 2. 调用 LLM（流式或非流式）
    // ...
    
    // 3. 如果有工具调用 → 执行并将结果追加到 messages
    for (const tc of toolCalls) {
      const result = await executeToolCall(tc.function.name, args);
      messages.push({ role: 'tool', tool_call_id: tc.id, name: tc.function.name, content: JSON.stringify(result) });
    }
    
    // 4. 如果没有工具调用 → 返回纯文本内容
    if (!hasToolCalls) return currentContent;
  }
}
```

关键设计点：

- **工具过滤**：Phase 1 排除所有 Wiki 相关工具（`list_wiki_pages`、`read_wiki`、`search_wiki`、`semantic_search`），因为大纲生成阶段还没有 Wiki 页面可供查询。
- **最大工具迭代 30 次**：防止无限工具调用循环。如果 30 轮后 LLM 仍在调用工具，函数返回已累积的内容。
- **流式输出感知**：当 `stream = true` 时，content/reasoning/tool_call 三种 chunk 类型分别处理，同时将 reasoning_content 以黄色文字输出到终端，让用户看到 LLM 的思维过程。

[来源](src/commands/generate.ts#L242-L334) | [来源](src/commands/generate.ts#L248-L250)

### 解析器：parseOutlineJson

`parseOutlineJson` 将 LLM 返回的任意文本解析为结构化的 `Topic[]`。它的设计容忍了 LLM 输出的各种不一致：

```typescript
function parseOutlineJson(text: string): Topic[] {
  let cleaned = stripCodeFence(text);  // 移除 ```json ... ``` 围栏
  const jsonMatch = cleaned.match(/\{[\s\S]*\}/);  // 贪婪匹配第一个 JSON 对象
  if (!jsonMatch) return [];
  
  const parsed = JSON.parse(jsonMatch[0]);
  if (!parsed.sections || !Array.isArray(parsed.sections)) return [];
  
  // 遍历 sections → topics，支持两种字段格式
  for (const item of section.topics) {
    if (item.type === 'group') {
      // 分组标记
      topics.push({ title, isGroup: true, ... });
    } else {
      // 兼容遗留格式：brief 同时回退到 description 和 task
      const description = item.description || item.brief || '';
      const task = item.task || item.brief || '';
      topics.push({ title, level: item.level || '中级', slug: toSlug(item.title), description, task, ... });
    }
  }
}
```

**双字段回退策略**：最初的大纲格式只有一个 `brief` 字段，后来拆分为 `description`（供其他页面看到的简介）和 `task`（仅供本页面的 LLM 指令）。解析器同时支持两种格式——如果 `description`/`task` 缺失，则回退到 `brief`。这意味着旧的 `_outline.json` 缓存仍然兼容。

[来源](src/commands/generate.ts#L215-L240) | [来源](tests/outline-parser.test.ts#L73-L83)

#### 生成单个页面：generateOne

`generateOne` 是页面的实际生成单元：

1. **跳过检查**：如果文件已存在且不是重试模式，直接跳过（断点续传的核心机制）
2. **Prompt 渲染**：加载 `page-system.md` 和 `page-user.md`，注入 `pageTitle`、`audienceLevel`、`pageSlug`、`availablePages`、`pageTask` 等变量
3. **LLM 调用**：通过 `collectFullResponse` 流式收集内容
4. **写入文件**：成功时写入 `TEMP_DIR/{slug}.md`，失败时加入 `failed[]`

[来源](src/commands/generate.ts#L377-L414)

### 并行模式与信号量

`generatePages` 支持两种调度模式，用户通过 inquirer 交互选择或 `--parallel` 标志控制：

#### 串行模式（默认）

每次生成一个页面，`stream = true`，每个页面的生成过程实时输出到终端。适合希望看到逐页流式输出的场景。

#### 并行模式

使用 `runConcurrent` 信号量实现可控并发：

```typescript
async function runConcurrent(
  tasks: (() => Promise<void>)[], 
  concurrency: number
): Promise<void> {
  const running = new Set<Promise<void>>();
  const queue = [...tasks];

  while (queue.length > 0 || running.size > 0) {
    // 填充运行槽位
    while (running.size < concurrency && queue.length > 0) {
      const task = queue.shift()!;
      const p = task().finally(() => running.delete(p));
      running.add(p);
    }
    // 等待任意一个完成
    if (running.size > 0) {
      await Promise.race(running);
    }
  }
}
```

这是一个经典的 **信号量模式**，不同于 `Promise.all`（全部并发）或 `for...of await`（完全串行）。它维护一个固定大小的运行集合，始终填满到 `concurrency` 上限，任意任务完成后立即启动下一个。默认并发数 3，可通过 `--concurrency` 调整（1-10）。

并行模式下 `stream = false`——因为多个流式输出同时写入终端会造成混乱。每个页面完成时通过 `[index/total]` 前缀报告进度。

[来源](src/commands/generate.ts#L418-L431) | [来源](src/commands/generate.ts#L145-L164)

### 重试机制

生成失败有两种重试路径：

1. **自动重试**：如果 `opts.retry > 0`，在 Phase 2 结束后自动对失败页面重新调用 `generatePages`，传入 `retryList` 参数。重试次数耗尽后停止。
2. **交互式重试**：非静默模式下，如果仍有失败页面，循环询问用户是否重试，直到用户确认取消或全部成功。

```typescript
let retriesLeft = opts.retry ?? 0;
while (failed.length > 0 && retriesLeft > 0) {
  const retryResult = await generatePages(client, config, workDir, topics, 
    { parallel, concurrency, retryList: [...failed] });
  failed = retryResult;
  retriesLeft--;
}
```

## 断点续传机制

整个生成过程围绕 `TEMP_DIR`（`.wiki/temp`）工作：

```
Phase 1:  写入 _outline.json
Phase 2:  写入 {slug1}.md, {slug2}.md, ...
完成:     moveDir(.wiki/temp → .wiki/2024-01-01T12-00-00)
```

启动时如果检测到 `.wiki/temp` 存在，交互式提示用户：

- **🔄 Resume from last checkpoint**：保留临时文件，跳过已生成的页面
- **🗑️ Discard and start fresh**：清空临时目录，重新开始

跳过逻辑在 `generateOne` 中实现：如果文件已存在且不是重试模式，直接 `return`。这意味着即使生成过程中断（如终端关闭），重新运行并选择 Resume 即可从断点继续。

[来源](src/commands/generate.ts#L77-L89) | [来源](src/commands/generate.ts#L383-L387)

## Index 文件生成

`generateIndex` 在页面全部生成后调用，从 `Topic[]` 构建 `index.json`：

```typescript
async function generateIndex(wikiDir: string, topics: Topic[]): Promise<void> {
  const jsonOut: { sections: { name: string; topics: any[] }[] } = { sections: [] };
  const sections = [...new Set(topics.map(t => t.section).filter(Boolean))];

  for (const section of sections) {
    const items = sectionTopics.map(topic => {
      if (topic.isGroup) return { type: 'group', title: topic.title };
      return { level: topic.level, title: topic.title, description?, task? };
    });
    jsonOut.sections.push({ name: section, topics: items });
  }

  await writeTextFile(join(wikiDir, 'index.json'), JSON.stringify(jsonOut, null, 2));
}
```

这个 `index.json` 是整个 Wiki 的导航骨架，被 HTTP 服务器用于渲染侧边栏目录，同时被 `list_wiki_pages` 工具用于提供页面查询。

## 总体数据流

```
generateCommand()
  │
  ├─ resolveWorkDir() → workDir
  │
  ├─ Phase 1: generateOutline()
  │   ├─ renderPrompt('outline-system.md', {workDir, os})
  │   ├─ renderPrompt('outline-user.md', {workDir, os, lang})
  │   ├─ loop (≤ 25):
  │   │   ├─ collectFullResponse() → 含工具调用的内循环 (≤ 30)
  │   │   ├─ parseOutlineJson() → Topic[]
  │   │   └─ 成功 → 写入 _outline.json，返回
  │   └─ 失败 → 返回 []
  │
  ├─ Phase 2: generatePages()
  │   ├─ 构建 availablePages 交叉引用
  │   ├─ 选择模式: 并行 (runConcurrent) / 串行 (流式)
  │   ├─ generateOne() × N:
  │   │   ├─ 检查断点 (TEMP_DIR/{slug}.md 已存在?)
  │   │   ├─ renderPrompt('page-system.md', ...)
  │   │   ├─ renderPrompt('page-user.md', ...)
  │   │   ├─ collectFullResponse() → 页面 Markdown
  │   │   └─ 写入 TEMP_DIR/{slug}.md
  │   └─ 返回 failed[]
  │
  ├─ 重试循环 (自动 / 交互式)
  │
  ├─ moveDir(TEMP_DIR → finalDir)
  ├─ generateIndex(finalDir, topics) → index.json
  └─ 写入 .meta.json
```

## 关键设计决策总结

| 决策 | 选择 | 理由 |
|------|------|------|
| 两阶段分离 | 先大纲后页面 | 让 LLM 先理解全貌再逐个深入，避免上下文碎片化 |
| 迭代式大纲 | ≤ 25 轮 | 允许多轮工具调用探索代码，LLM 逐步 build 理解 |
| 信号量并发 | Set + Promise.race | 比 `Promise.all` 更好的资源控制，比队列库更轻量 |
| 文件级断点 | TEMP_DIR + 存在性检查 | 简单可靠，无需状态数据库，支持任意中断恢复 |
| 双字段兼容 | description/brief + task/brief | 支持旧版 `_outline.json` 缓存，向后兼容 |
| 工具内循环上限 | 30 次 | 防止 LLM 陷入无限工具调用，确保进展 |

两阶段引擎的设计核心是：**将复杂任务分解为 LLM 能够可靠执行的子任务**。Phase 1 利用工具调用让 LLM 像人类开发者一样浏览代码，Phase 2 利用并行/串行切换和断点续传让大规模文档生成变得可行且可恢复。
