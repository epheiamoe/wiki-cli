# 配置存储架构

配置文件是 wiki-cli 所有运行时行为的"神经中枢"。无论是 LLM 对话、Embedding 语义搜索还是 Web Fetch 工具，它们的提供商、模型、API 密钥和端点地址都统一存储在一个 JSON 文件中。这个文件的位置、结构和访问方式，构成了配置层的完整骨架。

## 配置文件路径

配置文件位于用户主目录下的 `~/.wiki-cli/config.json`。路径由两个常量组合而成：

```typescript
const CONFIG_DIR  = join(homedir(), '.wiki-cli');
const CONFIG_PATH = join(CONFIG_DIR, 'config.json');
```

`homedir()` 来自 Node.js 的 `os` 模块，在 Windows 上解析为 `C:\Users\<用户名>`，在 macOS/Linux 上解析为 `~`。`saveConfig` 函数在写入前会通过 `mkdir(CONFIG_DIR, { recursive: true })` 确保目录存在，调用方无需担心目录创建。`loadConfig` 则先用 `existsSync` 检查文件是否存在 —— 若不存在直接返回 `null`，而非抛出异常。

[来源](src/config/config-store.ts#L1-L4)

## WikiCliConfig 接口：三组配置项

`WikiCliConfig` 接口定义了 JSON 文件中所有可存储的字段，按功能分为三组：

| 组别 | 字段 | 类型 | 说明 |
|------|------|------|------|
| **LLM** | `provider` | `string` | 提供商名称（如 OpenAI） |
| | `baseUrl` | `string` | API 端点地址 |
| | `model` | `string` | 模型标识符（如 gpt-5.4） |
| | `apiKey` | `string` | API 密钥 |
| | `jsonMode` | `boolean?` | JSON 模式开关 |
| | `lang` | `string` | 输出语言（如 zh） |
| **Embedding** | `embeddingProvider` | `string?` | 嵌入提供商 |
| | `embeddingModel` | `string?` | 嵌入模型 |
| | `embeddingBaseUrl` | `string?` | 嵌入 API 地址 |
| | `embeddingApiKey` | `string?` | 嵌入 API 密钥 |
| **WebFetch** | `webFetchDisabled` | `boolean?` | 禁用 Web Fetch |
| | `webFetchProvider` | `string?` | Web Fetch 提供商 |
| | `webFetchBaseUrl` | `string?` | Web Fetch API 地址 |
| | `webFetchApiKey` | `string?` | Web Fetch API 密钥 |

LLM 组是核心必填项（除 `jsonMode` 外均为必填），Embedding 和 WebFetch 组均为可选。这种分层设计让用户可以只配置 LLM 就开始生成，后续再按需开启高级功能。

[来源](src/config/config-store.ts#L10-L27)

## 默认模型加载

`loadDefaultModels()` 函数从 `default-models.json` 文件加载预定义的模型列表，返回值类型为 `ModelEntry[]`：

```typescript
export interface ModelEntry {
  provider: string;     // 提供商名称
  model: string;        // 模型标识符
  baseUrl: string;      // API 端点
  description: string;  // 简要说明
  pricingHint?: string; // 价格提示（可选）
}
```

该 JSON 文件通过静态导入（`import defaultModels from './default-models.json' with { type: 'json' }`）在编译时嵌入，覆盖 8 家提供商的 21 个模型 —— 从 OpenAI 的五档 GPT 到 Kimi 的两代 K2，再到 Mistral 的三款差异化模型。这些数据在[配置命令详解](配置命令-wiki-cli-config.md)的交互选择器中被直接使用。

[来源](src/config/config-store.ts#L29-L39)

## 提供商与模型的分类查询

`getProviders(models)` 和 `getModelsByProvider(models, provider)` 提供了两个基础筛选操作：

- `getProviders` —— 遍历模型数组，提取所有去重后的提供商名称，返回 `string[]`。
- `getModelsByProvider` —— 按提供商名过滤，返回该提供商旗下的所有 `ModelEntry` 对象。

两者组合使用，即可实现"先选提供商、再选模型"的两级选择器。这种模式在交互式配置命令和[LLM 客户端设计](llm-客户端-流式通信与重试机制.md)中均有体现。

[来源](src/config/config-store.ts#L75-L81)

## Embedding 模型：硬编码列表

与 LLM 模型从 JSON 文件加载不同，Embedding 模型被直接**硬编码**在代码中，定义为 `EMBEDDING_MODELS: EmbeddingModelEntry[]` 常量数组：

```typescript
export interface EmbeddingModelEntry {
  provider: string;    // 提供商
  model: string;       // 模型名称
  baseUrl: string;     // API 端点
  description: string; // 功能描述，如"最佳通用，MTEB ~64.6"
  dimensions: number;  // 输出向量维度
  pricingHint?: string;// 价格提示
}
```

列表覆盖 7 家提供商的 10 个模型，包括 OpenAI 的三款（text-embedding-3-large/small/ada-002）、Google Gemini、Cohere、Voyage AI（large/lite）、Jina AI 和 Mistral。每个模型标注了 `dimensions`（向量维度），这直接影响到[语义搜索缓存](embedding-缓存与语义搜索.md)的索引结构。

对应的查询函数 `getEmbeddingProviders()` 和 `getEmbeddingModelsByProvider(provider)` 与 LLM 版的逻辑完全一致 —— 前者去重提取提供商列表，后者按提供商过滤模型条目。

[来源](src/config/config-store.ts#L41-L64)

## JSON 模式支持判定

`supportsJsonMode(provider)` 函数负责回答一个关键问题："这个 LLM 提供商是否支持 JSON 模式？" 答案通过一个 `Set` 查找实现：

```typescript
const JSON_MODE_PROVIDERS = new Set([
  'OpenAI',
  'DeepSeek',
  'xAI Grok',
  'Mistral',
  'Kimi (Moonshot)',
]);
```

支持的提供商返回 `true`，不支持的返回 `false`。当 `provider` 为 `'Custom'`（自定义提供商）时返回 `undefined` —— 这是一个有意为之的三态设计：`undefined` 表示"未知，由用户自行判断"，这与布尔值的明确 yes/no 区分开来。该逻辑在[LLM 提供商与模型](llm-提供商与模型注册.md)页面中有更详细的讨论。

[来源](src/config/config-store.ts#L66-L73)

## 配置的读写流程

配置的持久化只有两个异步函数：

- **`loadConfig()`** —— 检查文件是否存在，存在则 `readFile` 后 `JSON.parse` 返回 `WikiCliConfig`；不存在或解析失败返回 `null`。
- **`saveConfig(config)`** —— 先确保目录存在，然后用 `JSON.stringify(config, null, 2)` 格式化写入。

两者均不涉及校验或迁移逻辑 —— 配置被视作一个纯粹的 JSON 文档，由消费方（如配置命令、Generate 命令）自行保证其语义合法性。
