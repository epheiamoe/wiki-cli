# 工具系统：12 个只读工具

工具系统是 wiki-cli 的 LLM 与文件系统之间的桥梁。12 个只读工具被暴露为 OpenAI 兼容的 `function calling` 格式，由 LLM 自主选择调用，所有操作均不产生副作用——不创建、不修改、不删除任何文件。

## 工具全景

12 个工具按领域分为四组：

| 领域 | 工具 | 功能概括 |
|---|---|---|
| **文件系统** | `list_directory` | 目录结构树，递归深度控制 |
| | `list_files` | 扁平文件列表，扩展名过滤 |
| | `read_file` | 文件内容读取，可选行范围切片 |
| | `search_in_files` | 正则搜索文件内容，返回命中行 |
| **Git** | `git_log` | 提交历史（--oneline 格式） |
| | `git_show` | 提交/树/Blob 对象详情 |
| | `git_remote_info` | 远程仓库 URL 列表 |
| **Wiki 查询** | `list_wiki_pages` | 列出所有 Wiki 页面（slugs + 标题） |
| | `read_wiki` | 按 slug 读取 Wiki 页面 |
| | `search_wiki` | 关键词搜索 Wiki 页面（大小写不敏感） |
| | `semantic_search` | 语义搜索 Wiki 页面（需 Embedding 配置） |
| **网络** | `fetch_web_markdown` | 通过 Jina Reader API 将 URL 转为 Markdown |

每个工具定义遵循 OpenAI Tool Definition 接口：`{ type: 'function', function: { name, description, parameters } }`。description 字段是 LLM 判断何时使用该工具的唯一依据，因此每段描述都经过精炼以消除歧义。例如 `read_file` 明确标注了行号从 1 开始计数，`semantic_search` 提示"在关键词搜索失败或概念性问题时使用"。

[来源](src/ai/tools.ts#L20-L162)

## 路由表：toolHandlers

工具的执行路由通过 `toolHandlers` 对象实现——一个将工具名称直接映射到处理函数的 **策略模式** 实现：

```typescript
const toolHandlers: Record<string, (args: any) => Promise<ToolResult>> = {
  list_directory: (args) => listDirectory(args.dir_path, args.max_depth),
  list_files: (args) => listFiles(args.path, args.extensions),
  read_file: (args) => readFileTool(args.file_path, args.start_line, args.end_line),
  search_in_files: (args) => searchInFiles(args.path, args.pattern, args.extensions),
  git_log: (args) => gitLog(args.max_count, args.path),
  git_show: (args) => gitShow(args.object, args.path),
  git_remote_info: () => gitRemoteInfo(),
  dotenv_template: () => dotenvTemplate(),
  list_wiki_pages: () => listWikiPages(),
  read_wiki: (args) => readWiki(args.slug),
  search_wiki: (args) => searchWiki(args.query, args.max_results),
  semantic_search: (args) => semanticSearch(args.query, args.max_results),
  fetch_web_markdown: (args) => fetchWebMarkdown(args.url),
};
```

所有路由汇总到 `executeToolCall(name, args)` 这一统一入口，它在查找不到处理函数时返回 `{ type: 'error', data: 'Unknown tool: ...' }`。[项目架构全景](项目架构全景.md) 中展示了该入口在整体数据流中的位置。

[来源](src/ai/tools.ts#L651-L672)

## 运行时配置注入：initTools / getFilteredTools

两个导出函数将配置层与工具层解耦：

**`initTools(embConfig?, webConfig?)`** — 在命令启动时注入 Embedding 和 Web Fetch 配置。语义搜索依赖 Embedding 提供商和模型参数；Web Fetch 依赖 Jina Reader 的 base URL 和 API Key。这两个配置分别来自用户的 [Embedding 语义搜索配置](embedding-语义搜索配置.md) 和 [Web Fetch 配置](web-fetch-配置.md)。如果 LLM 未配置 Embedding，`semantic_search` 工具会直接返回错误信息"Embedding not configured. Run wiki-cli config to set up."

**`getFilteredTools(): ToolDefinition[]`** — 在 LLM 发起聊天请求前调用，根据运行时的 webFetchConfig 决定是否移除 `fetch_web_markdown`。如果用户在配置中将 Web Fetch 设为禁用状态，该工具会从 definitions 数组中移除，LLM 完全不会感知到它的存在。

`ai` 命令还在此基础上叠加了一道 **上下文感知过滤**：它维护一个 `skipTools` Set，根据是否已生成 Wiki、是否已配置 Embedding，动态移除 `list_wiki_pages`、`read_wiki`、`search_wiki`、`semantic_search` 中的部分或全部工具。

## 递归实现的边界条件

### buildTree — 目录结构树

`listDirectory` 通过递归函数 `buildTree` 构建嵌套的目录树。关键边界条件：

1. **深度截断**：当 `depth > maxDepth` 时返回 `{ name: '...', type: 'truncated' }`，而非继续递归。默认最大深度为 3。
2. **隐藏文件/目录过滤**：以 `.` 开头的文件或目录（如 `.git`、`.env`）直接跳过。
3. **node_modules 排除**：目录名恰好为 `node_modules` 时跳过——这是硬编码的最优先排除项，因为 npm 依赖树可能无限深且对代码理解无意义。

```typescript
if (item.name.startsWith('.') || item.name === 'node_modules') continue;
```

[来源](src/ai/tools.ts#L175-L189)

### collectFiles — 扁平文件列表

`listFiles` 通过递归函数 `collectFiles` 收集所有文件路径。边界条件：

1. **同样的过滤规则**：跳过隐藏文件和 `node_modules`。
2. **扩展名过滤**：仅当 `extensions` 数组有值时生效。如果传入了 `['.ts', '.js']`，只收集这两类文件。
3. **空数组 vs 未定义**：`extensions` 为 `undefined` 或空数组时收集所有文件——这是通过 `!extensions || extensions.length === 0` 判断的。

[来源](src/ai/tools.ts#L201-L218)

### searchInDir — 正则搜索

`searchInFiles` 采用相同的递归模式，额外包含：

1. **大小写不敏感**：`new RegExp(pattern, 'i')`。
2. **文件读取容错**：对不可读文件用 `try/catch` 静默跳过，不中断整个搜索。
3. **相对路径输出**：搜索结果中的 `file` 字段使用 `relative(root, fullPath)`，返回相对于搜索根目录的路径。

[来源](src/ai/tools.ts#L246-L272)

## 三个特殊工具的实现细节

**`read_file`**：支持 `startLine` 和 `endLine` 切片。行号从 1 开始（`const s = Math.max(0, startLine - 1)`），对应开发者直觉中的行号概念。如果只传 `startLine` 不传 `endLine`，则从该行一直读到文件末尾。

[来源](src/ai/tools.ts#L222-L240)

**`fetch_web_markdown`**：代理请求到 `webFetchConfig.baseUrl`（默认 `https://r.jina.ai`），支持 Bearer Token 认证。实现了完整的三次指数退避重试（300ms → 2s → 4s），对 429（限流）和 5xx（服务端错误）分别做不同的重试延迟策略。请求超时 15 秒。

[来源](src/ai/tools.ts#L579-L649)

**`semantic_search`**：运行时动态导入 `./embeddings.js` 的 `semanticSearch` 函数。这避免了 Embedding 模块及其依赖（如向量计算库）在未配置时被加载。搜索结果会通过 `index.json` 将 slug 映射回中文标题。

[来源](src/ai/tools.ts#L543-L577) | [来源](src/ai/embeddings.ts#L73-L130)

## 主循环调度

工具调用不是一次性的，而是嵌入在 **LLM 主循环** 中：

```
LLM 返回 ➝ 解析 tool_calls ➝ executeToolCall 逐条执行 ➝ 结果注入 messages ➝ 再次请求 LLM
```

`ai` 命令的 `chatOnce` 和 `answerOnly` 函数都实现了这一循环，最多迭代 50 次。流式模式下（`generate` 命令的 Phase 1），工具调用的参数可能是分块到达的，调度器通过 `tc.index` 或 `tc.id` 作为 key 对分块进行合并去重。

当某次迭代 LLM 返回了多个 tool_calls 时，调度器会批量执行（`for...of` 循环），全部完成后再统一回传给 LLM，而非逐个串行等待。
