# 两阶段生成：大纲与页面

`generate` 命令的核心是一个 **两阶段流水线**：Phase 1 让 LLM 用工具探索仓库后输出结构化 JSON 大纲，Phase 2 按大纲逐页生成 Markdown。中间产物落在 `.wiki/temp` 目录，支持断点续传和失败重试。

[来源](src/commands/generate.ts#L1-L50)

---

## Phase 1：大纲生成

大纲生成的核心矛盾是：LLM 可能一次给不出合法 JSON，也可能需要多轮工具调用才能了解仓库。`generateOutline` 用一个 **25 次迭代的外循环** 兜底，每次迭代调用 `collectFullResponse` 获取完整响应，然后尝试 `parseOutlineJson` 解析。

### collectFullResponse：工具调用主循环

`collectFullResponse` 内部有一个 **30 次迭代的内循环**，专门处理工具调用（tool calls）。其逻辑如下：

```
外循环(25次): collectFullResponse → parseOutlineJson
  └── 内循环(30次): stream 或 chat → 检查 tool_calls → 执行工具 → 继续
```

每次内循环迭代中，如果 LLM 返回了 `tool_calls`，系统会将这些调用追加到消息历史，依次执行 `executeToolCall`，将结果以 `role: 'tool'` 消息推回对话，然后继续请求 LLM。只有当某次响应中 `tool_calls` 为空时，循环才终止并返回纯文本内容。

流式模式下，工具调用参数可能被分片传输——代码通过 `index` 字段聚合同一个 tool call 的多个参数块，存入 `Map<string, ToolCall>` 后再一次性执行。

[来源](src/commands/generate.ts#L118-L143)

### parseOutlineJson：容错解析

`parseOutlineJson` 的容错策略有三层：

1. **去除代码围栏**：调用 `stripCodeFence` 移除 ```json ... ``` 包裹。
2. **正则提取 JSON 对象**：用 `/\{[\s\S]*\}/` 从任意文本中提取第一个 `{}` 结构——这意味着 LLM 响应前后可以有任意额外文字。
3. **结构校验**：解析后验证 `parsed.sections` 是否为数组，然后逐 section 提取 topics。每个 topic 支持 `description` / `brief` 双字段回退：优先取 `description`，无则用 `brief`。`task` 同理。

如果解析返回空数组，外循环不会直接放弃——它将 LLM 的响应作为普通 `assistant` 消息追加到对话历史，然后发起下一轮。这意味着 LLM 可以在后续轮次中修正输出格式。

[来源](src/commands/generate.ts#L93-L116)

### 临时文件的写入时机

一旦 `parseOutlineJson` 返回非空 topics，立即将 raw 响应写入 `join(TEMP_DIR, '_outline.json')`。这份文件在 Phase 2 并不直接使用（Phase 2 从内存中的 `topics` 数组读取），但用于断点续传的检测——见下文。

## Phase 2：页面生成

### 并发池：Set + Promise.race

`generatePages` 支持串行和并行两种模式。并行模式的核心是一个 **固定大小的并发池**，实现方式极为简洁：

```typescript
async function runConcurrent(tasks, concurrency) {
  const running = new Set<Promise<void>>();
  const queue = [...tasks];

  while (queue.length > 0 || running.size > 0) {
    while (running.size < concurrency && queue.length > 0) {
      const task = queue.shift()!;
      const p = task().finally(() => running.delete(p));
      running.add(p);
    }
    if (running.size > 0) {
      await Promise.race(running);
    }
  }
}
```

关键设计点：

- **`Set` 管理活跃 Promise**：每个任务完成后通过 `finally` 从集合中移除自身，保证 `running.size` 准确反映当前并行数。
- **`Promise.race` 驱动循环**：等待任意一个任务完成，然后立即尝试塞入新任务。这比 `Promise.allSettled` + 分片的方式更高效——不会等整批完成再启动下一批，始终维持最大并发水位。
- 每个 task 是 `() => Promise<void>` 的惰性闭包，`queue.shift()` 按顺序消费。

在没有并行的串行模式下，直接用 `for` 循环依次 `await generateOne`，此时用户能看到逐页的流式输出效果。

### page-system.md 模板渲染与 availablePages 注入

每生成一页之前，`generateOne` 构建两组模板变量：

**系统 prompt 变量**（注入 `page-system.md`）：
- `workDir`, `os`：环境信息
- `pageTitle`, `audienceLevel`：当前页面标题与目标受众

**用户 prompt 变量**（注入 `page-user.md`）：
- 以上全部，再加上 `pageSlug`, `projectSummary`, `lang`, `pageTask`
- **`availablePages`**：从 `allTopics` 过滤出所有非 group 的 topic，格式化为 `- slug: xxx.md | 标题: xxx | 简介: xxx` 的多行字符串，每个 topic 的描述截取前 80 字符

`page-user.md` 模板中有一段固定的交叉引用段落：

```
## 本 Wiki 所有其他页面（交叉引用依据）
{{availablePages}}
```

这意味着生成每一页时，LLM 都能看到整个 Wiki 的完整目录结构，从而在正文中生成精确的 `[页面标题](slug.md)` 交叉引用链接。这是 **从大纲数据到页面内容的元信息注入**，而非运行时搜索。

### 失败收集与重试机制

`generateOne` 中若 `collectFullResponse` 返回 `null`，该 topic 被推入 `failed` 数组。`generateCommand` 在 Phase 2 结束后检查失败数量：

1. 若有 `opts.retry`（命令行参数），自动重试指定次数。
2. 若在交互模式下且仍有失败，反复询问用户是否重试。

重试时，`failed` 数组作为 `retryList` 传入新的 `generatePages` 调用，跳过已成功页面。`retryList` 会覆盖 `pageTopics` 的过滤逻辑：直接使用 `retryList` 而非 `allTopics.filter(t => !t.isGroup)`。

## 断点续传

断点续传涉及三个检查点：

| 检查点 | 位置 | 逻辑 |
|--------|------|------|
| 启动时 TEMP_DIR 存在 | `generateCommand` 开头 | 询问"从上次检查点恢复"或"重新开始"。选择 resume 则保留 TEMP_DIR；选择 fresh 则删除 |
| `_outline.json` | 在 Phase 1 写入 | 仅作为检查点标记存在，Phase 2 不从该文件读取数据 |
| 已生成的 `.md` 文件 | `generateOne` 内部 | 若非重试模式且文件已存在，直接跳过（仅串行模式打印 skip 日志） |

`_outline.json` 的存储路径硬编码为 `.wiki/temp/_outline.json`。Phase 2 每生成一页先检查 `existsSync(pagePath)`，命中即跳过——这保证了 resume 后不会重复生成已有页面。

Phase 2 全部完成后，`TEMP_DIR` 通过 `moveDir` 重命名为最终时间戳目录（如 `.wiki/2025-01-15T10-30-00`），然后在该目录生成 `index.json`。
