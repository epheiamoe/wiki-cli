# 工具系统与函数调用

## 10 个只读工具的 OpenAI Function Calling 定义

整个工具系统的核心是一份 `ToolDefinition` 接口声明和 10 个具体工具定义。每个工具都是**只读**的——它们只能探查代码库和 Wiki 内容，不能执行任何写操作。这是 LLM Agent 安全性的第一道防线。

### ToolDefinition 接口

```typescript
export interface ToolDefinition {
  type: 'function';
  function: {
    name: string;
    description: string;
    parameters: Record<string, any>;
  };
}
```

该接口完全符合 **OpenAI Function Calling 规范**：顶层 `type` 固定为 `'function'`，`function` 对象内嵌 `name`、`description` 和符合 JSON Schema 的 `parameters`。这意味着这些定义可以直接注入任何兼容 OpenAI API 的 LLM 请求体中的 `tools` 字段。[来源](src/ai/tools.ts#L11-L18)

### 10 个工具一览

| 工具名 | 描述 | 参数 | 必需参数 |
|--------|------|------|----------|
| `list_directory` | 获取目录结构树 | `dir_path` (string), `max_depth` (number, nullable) | `dir_path` |
| `list_files` | 按扩展名过滤列出目录中所有文件 | `path` (string), `extensions` (string[], nullable) | `path` |
| `read_file` | 读取文件内容，可选行范围 | `file_path` (string), `start_line` (number, nullable), `end_line` (number, nullable) | `file_path` |
| `search_in_files` | 在文件中搜索关键词或正则 | `path` (string), `pattern` (string), `extensions` (string[], nullable) | `path`, `pattern` |
| `git_log` | 获取 Git 提交历史 | `max_count` (number, nullable), `path` (string, nullable) | 无 |
| `git_show` | 显示 Git 对象详情 | `object` (string), `path` (string, nullable) | `object` |
| `git_remote_info` | 获取远程仓库信息 | 无参数 | 无 |
| `dotenv_template` | 读取 `.env.example` 模板 | 无参数 | 无 |
| `list_wiki_pages` | 列出所有 Wiki 页面及其 slug | 无参数 | 无 |
| `read_wiki` | 按 slug 读取 Wiki 页面内容 | `slug` (string) | `slug` |

[来源](src/ai/tools.ts#L20-L182)

从参数模式上可以清晰看到两个设计梯队：**文件系统工具**（前四个）需要明确指定路径或搜索范围，属于"有目标的探查"；**Git 工具**（中间三个）和 **Wiki 工具**（最后两个）则面向项目元数据和已生成的文档，属于"上下文感知的读取"。`dotenv_template` 作为一个特殊工具，用于让 LLM 了解项目所需的配置环境变量。

## 动态分发：`executeToolCall` 与 `toolHandlers`

工具定义是静态的声明，而调用则需要动态路由。系统使用一个 `Record<string, Handler>` 映射表实现这一点：

```typescript
const toolHandlers: Record<string, (args: any) => Promise<ToolResult>> = {
  list_directory: (args) => listDirectory(args.dir_path, args.max_depth),
  list_files: (args) => listFiles(args.path, args.extensions),
  read_file: (args) => readFileTool(args.file_path, args.start_line, args.end_line),
  search_in_files: (args) => searchInFiles(args.path, args.pattern, args.extensions),
  git_log: (args) => gitLog(args.max_count, args.path),
  git_show: (args) => gitShow(args.object, args.path),
  git_remote_info: () => gitRemoteInfo(),
  dotenv_template: () => dotenvTemplate(),
  list_wiki_pages: () => listWikiPages(),
  read_wiki: (args) => readWiki(args.slug)
};
```

[来源](src/ai/tools.ts#L422-L434)

暴露的入口函数 `executeToolCall` 极其简洁：

```typescript
export async function executeToolCall(name: string, args: any): Promise<ToolResult> {
  const handler = toolHandlers[name];
  if (!handler) {
    return { type: 'error', data: `Unknown tool: ${name}` };
  }
  return handler(args);
}
```

[来源](src/ai/tools.ts#L438-L444)

### 设计要点

- **无 `switch`/`if-else`**：利用对象字面量的属性查找实现 O(1) 路由。新增工具只需在 `toolDefinitions` 数组中添加定义，同时在 `toolHandlers` 映射中注册处理函数。
- **参数解构在映射层**：调用者传递原始 `args` 对象，映射函数解构出具体参数。LLM 返回的 `arguments` 是 JSON 字符串，由调用方 `JSON.parse` 后再传入——这个解析在 `generate.ts` 和 `ai.ts` 中完成。[来源](src/commands/generate.ts#L357-L358)
- **错误兜底**：未知工具名返回 `{ type: 'error', data: 'Unknown tool: ...' }`，而不是抛异常。这保证了 LLM Agent 循环不会因一个错误的工具名调用而崩溃。

在 `generate.ts` 和 `ai.ts` 中，工具调用的完整生命周期是：LLM 返回 `tool_calls` → 解析参数 → 调用 `executeToolCall` → 结果以 `role: 'tool'` 消息追加回 `messages` 数组 → 继续下一轮 LLM 请求。这个循环最多迭代 30 次。[来源](src/commands/generate.ts#L245)

## 核心工具实现分析

### `listDirectory` + `buildTree`：递归目录遍历

```typescript
async function buildTree(root: string, current: string, depth: number, maxDepth: number): Promise<any> {
  if (depth > maxDepth) return { name: '...', type: 'truncated' };
  const name = relative(root, current) || '.';
  const entry = { name, type: 'directory', children: [] as any[] };
  const items = await readdir(current, { withFileTypes: true });
  for (const item of items) {
    if (item.name.startsWith('.') || item.name === 'node_modules') continue;
    const fullPath = join(current, item.name);
    if (item.isDirectory()) {
      const child = await buildTree(root, fullPath, depth + 1, maxDepth);
      entry.children.push(child);
    } else {
      entry.children.push({ name: item.name, type: 'file' });
    }
  }
  return entry;
}
```

[来源](src/ai/tools.ts#L192-L208)

关键设计：

- **剪枝机制**：默认 `maxDepth` 为 3，超过深度返回 `{ name: '...', type: 'truncated' }` 占位符，而不是暴力全量递归。这避免了 LLM 意外请求根目录时产生巨量输出。
- **黑名单过滤**：跳过所有 `.` 开头的隐藏文件和 `node_modules`。这是 Node.js 工具的标准保护策略，防止 `node_modules` 的指数级膨胀拖垮递归。
- **相对路径**：`relative(root, current)` 保证返回的树结构中路径对 LLM 可读且上下文相关。
- **异步递归**：使用 `await readdir` + `withFileTypes` 在单次系统调用中同时获取名称和类型信息，比先 `readdir` 再 `stat` 每个条目更高效。

### `listFiles` + `collectFiles`：扁平文件收集

与 `buildTree` 不同，`listFiles` 输出一个**扁平的绝对路径数组**。它的递归逻辑 `collectFiles` 更简单——不构建树结构，而是在遍历过程中将匹配文件路径推入结果数组：

```typescript
if (!extensions || extensions.length === 0 || extensions.includes(extname(item.name))) {
  result.push(fullPath);
}
```

[来源](src/ai/tools.ts#L224-L237)

关键在于 `extname` 匹配：`extensions` 参数需要带点号前缀的完整扩展名（如 `".ts"`），直接与 `path.extname` 返回值比较。若 `extensions` 为空或未提供，则收集所有文件。这比 `list_directory` 更"扁平"，适合 LLM 快速获取特定类型的文件清单再做下一步 `read_file`。

### `searchInFiles` + `searchInDir`：正则内容搜索

这是最"重量级"的工具——它逐行正则匹配文件内容：

```typescript
const regex = new RegExp(pattern, 'i');
const results: { file: string; line: number; content: string }[] = [];
await searchInDir(absPath, absPath, regex, extensions, results);
```

[来源](src/ai/tools.ts#L255-L275)

关键设计：

- **大小写不敏感**：`new RegExp(pattern, 'i')` 硬编码了 `i` 标志。这意味着 LLM 传入的 pattern 会被强制忽略大小写——这是一个权衡，避免了大小写匹配的微妙差异导致 LLM "找不到"代码，但也意味着 LLM 无法做大小写敏感搜索。
- **三字段结果**：每条匹配记录包含 `file`（相对路径）、`line`（1-indexed 行号）、`content`（trimmed 行内容）。相对路径使用 `relative(root, fullPath)` 计算，保持简洁。
- **异常静默**：单个文件读取失败（如二进制文件）时 `catch {}` 静默跳过，不影响整体搜索。
- **扩展名前置过滤**：在读取文件内容之前先检查 `extname`，避免不必要的 I/O。

[来源](src/ai/tools.ts#L278-L298)

### Wiki 工具：`findLatestWikiDir` 的版本排序策略

Wiki 相关工具（`listWikiPages`、`readWiki`）共享一个底层函数 `findLatestWikiDir`：

```typescript
async function findLatestWikiDir(): Promise<string | null> {
  if (!existsSync(WIKI_DIR)) return null;
  const entries = await readdir(WIKI_DIR, { withFileTypes: true });
  const dirs = entries
    .filter(e => e.isDirectory() && e.name !== 'temp' && e.name !== 'sessions')
    .map(e => e.name)
    .sort()
    .reverse();
  return dirs.length > 0 ? join(WIKI_DIR, dirs[0]) : null;
}
```

[来源](src/ai/tools.ts#L326-L336)

排序策略是**字典序降序**：`.sort().reverse()`。这意味着 Wiki 版本目录的命名必须保证**字典序与时间序一致**，才能正确找到最新版本。当前的 `index.json` 时间戳格式（如 `2025-01-15T143022.123Z`）天然支持字典序排序，最新的时间戳字符串排在最后，`reverse()` 后排到最前。[更多关于输出目录结构的细节](生成结果说明.md)

`listWikiPages` 的读取策略有两层回退：

1. **首选 `index.json`**：解析 JSON 结构中的 `sections[].topics[]`，提取每个 topic 的 `title` 字段，通过 slug 化算法生成 Markdown 文件名。slug 化规则是 `toLowerCase()` → 去除非单词字符（含中文 `\u4e00-\u9fff`）→ 去首尾连字符。
2. **回退扫描 `.md` 文件**：若 `index.json` 不存在，则直接 `readdir` 获取 `*.md` 文件列表，排除 `index.md`。

[来源](src/ai/tools.ts#L338-L375)

`readWiki` 在精确文件名查找失败时，还会尝试**模糊匹配**——遍历 Wiki 目录下所有 `.md` 文件，检查文件名是否包含 slug 或 slug 是否包含文件名。这使得 LLM 在 slug 记忆不精确时仍能容错命中目标页面。[来源](src/ai/tools.ts#L377-L416)

## `ToolResult`：type/data 双字段约定

```typescript
export interface ToolResult {
  type: 'success' | 'error';
  data: any;
}
```

[来源](src/ai/tools.ts#L5-L8)

这个简单的接口承担了两个角色：

- **区分成功与失败**：`type` 字段让调用者（LLM Agent 循环）可以一线判断工具调用是否成功，而不需要 try/catch。失败时 `data` 包含人类可读的错误消息字符串。
- **统一序列化**：工具调用结果最终通过 `JSON.stringify(result)` 序列化为字符串，作为 `role: 'tool'` 消息的 `content` 回传给 LLM。[来源](src/commands/generate.ts#L361)

注意 `data: any` 的灵活性——`listDirectory` 返回嵌套对象树，`listFiles` 返回字符串数组，`searchInFiles` 返回对象数组，`gitLog` 返回纯文本。这种设计避免了为每种返回类型定义独立接口，代价是 LLM 端需要从上下文推断 `data` 的结构。

## 工具协作场景

这些工具并非孤立使用，而是在 LLM Agent 的多轮对话中组合成**探查策略**。以下是典型的协作链路：

```
list_directory("/src") → 发现 src/ai/ 目录
  → list_files("src/ai", [".ts"]) → 获取文件清单 [tools.ts, llm-client.ts, ...]
    → read_file("src/ai/tools.ts", 20, 50) → 读取工具定义片段
      → search_in_files("src", "executeToolCall") → 查找调用点
```

[来源](src/commands/generate.ts#L245-L366) 展示了这个循环的实际运行：LLM 在最多 30 轮迭代中，每次可以发起多个并行工具调用（LLM 返回多个 `tool_calls`），执行结果依次追加到消息历史，然后带着新上下文继续请求 LLM 的下一步决策。

另一个常见的模式是探索+理解：

```
git_log(5) → 了解最近提交信息
  → git_show("abc1234") → 查看某次提交的详细变更
    → 结合 read_file 读取变更涉及的文件
```

在交互式 AI 模式中（[`wiki-cli ai` 命令](ai-交互命令-wiki-cli-ai.md)），工具集合根据是否存在已生成的 Wiki 动态过滤——如果没有 Wiki，`list_wiki_pages` 和 `read_wiki` 不会被注入 LLM 的 `tools` 参数中，避免了 LLM 调用不存在工具的错误。[来源](src/commands/ai.ts#L75-L78)

## 设计哲学总结

整个工具系统的设计可以用三个词概括：**只读、映射分发、递归遍历**。10 个工具覆盖了代码探索的四个维度——文件系统（结构/内容/搜索）、Git 历史（日志/对象/远程）、配置（环境模板）和 Wiki（列表/读取）。`toolHandlers` 映射表使路由逻辑与处理逻辑解耦，每新增一个工具只需添加定义+处理函数，不需要修改任何控制流。这种架构使得工具集可以随项目需求平稳扩展，而 LLM Agent 循环本身不需要感知具体工具的差异。
