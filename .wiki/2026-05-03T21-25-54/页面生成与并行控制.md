# 页面生成与并行控制

Phase 2 的页面生成是整个流水线的输出瓶颈：它接收 [大纲生成阶段](大纲生成阶段.md) 产出的 `Topic[]`，逐页调用 LLM 生成 Markdown 正文。本页面解剖 `generatePages`、`runConcurrent` 和 `generateIndex` 三个核心函数的实现，重点说明 **并发控制策略** 与 **模板变量注入机制**。

---

## `PageGenOptions`：三个控制参数

`generatePages` 的最后一个参数是 `PageGenOptions` 接口，仅三个字段，各司其职：

| 参数 | 类型 | 默认值 | 语义 |
|------|------|--------|------|
| `parallel` | `boolean` | `false` | 是否启用并行模式。`false` 时为串行流式输出，逐页可见实时内容；`true` 时无流式输出，但整体速度更快 |
| `concurrency` | `number` | `3` | 并行模式下的固定并发数，在命令行交互时限制为 `1-10` |
| `retryList` | `Topic[]` | `undefined` | 重试列表。不为空时，`generatePages` 跳过 `allTopics.filter(t => !t.isGroup)` 的逻辑，直接用 `retryList` 作为待生成页面集 |

`retryList` 的存在使得**断点续传与重试**得以实现：`generateCommand` 顶层有一个 `while (failed.length > 0)` 循环，每次失败后提示用户是否重试，并将 `failed` 数组传入新的 `generatePages` 调用做 `retryList`。

## 每页生成流程：模板 → 变量注入 → LLM 调用 → 写入

`generateOne` 是定义在 `generatePages` 内部的闭包，负责单页生成。流程分四步：

### 1. 跳过检测

如果目标文件 `.wiki/temp/<slug>.md` 已存在且当前**不是**重试模式（`!options.retryList`），则直接跳过。这是断点续传的基础：已经生成的页面不会重复调用 LLM。

[来源](src/commands/generate.ts#L413-L416)

### 2. 模板变量注入

两个模板文件通过 `renderPrompt` 引擎填充 Mustache 风格变量：

```
page-system.md ← {{workDir}}, {{os}}, {{pageTitle}}, {{audienceLevel}}
page-user.md   ← {{workDir}}, {{pageTitle}}, {{audienceLevel}}, {{pageSlug}},
                  {{projectSummary}}, {{lang}}, {{availablePages}}, {{pageTask}}
```

`renderPrompt` 的实现见 [`prompts.ts`](src/ai/prompts.ts#L24-L27)，核心是正则替换：`result.replace(new RegExp("\\{\\{" + key + "\\}\\}", "g"), value)`。

`audienceLevel` 取自 `Topic.level`（如"中级"、"高级"），直接写入 System Prompt 的"目标受众"段，控制 LLM 的输出深度。`pageTask` 取自 `Topic.task`，是 user prompt 中"本页编写任务"段的内容。

[来源](src/commands/generate.ts#L421-L438) | [来源](src/ai/prompts.ts#L15-L27)

### 3. 调用 LLM 获取全文

组装完 `messages: [systemPrompt, userPrompt]` 后调用 `collectFullResponse`。此函数是 LLM 调用的通用编排器，内部处理：

- **流式/非流式**：串行模式下 `stream = true`，实时输出 token 到终端；并行模式下 `stream = false`，静默完成
- **工具调用循环**：最多 30 轮迭代。任何一轮检测到 `tool_calls` 就执行工具、将结果追加到 `messages`、继续下一轮，直到 LLM 返回纯文本
- **重连与错误上报**：流式连接出错返回 `null`，由上层将当前 topic 推入 `failed`

`collectFullResponse` 与 [LLM 客户端实现](llm-客户端实现.md) 中的 `chatStream` / `chat` 方法对接，后者内置指数退避重试（最多 3 次）。

[来源](src/commands/generate.ts#L440-L445) | [来源](src/commands/generate.ts#L213-L309)

### 4. 写入临时文件

LLM 返回的有效内容直接写入 `.wiki/temp/<slug>.md`。`writeTextFile` 会自动创建父目录。

[来源](src/commands/generate.ts#L447-L455)

## `runConcurrent`：固定并发数的 Promise.race 调度

这是整个工具中**唯一**的并发控制点。实现采用经典的"固定大小线程池"模式，代码不足 15 行：

```typescript
async function runConcurrent(tasks: (() => Promise<void>)[], concurrency: number): Promise<void> {
  const running = new Set<Promise<void>>();
  const queue = [...tasks];

  while (queue.length > 0 || running.size > 0) {
    while (running.size < concurrency && queue.length > 0) {
      const task = queue.shift()!;
      const p = task().finally(() => running.delete(p));
      running.add(p);
    }
    if (running.size > 0) {
      await Promise.race(running);
    }
  }
}
```

工作循环可以用状态机理解：

```
      ┌──────────────────────────────────┐
      │  queue 非空 且 running < 并发数  │──→ 出队 task → 执行 → 加入 running
      └──────────────────────────────────┘
                      │
                      ↓  queue 为空 或 running 已满
              ┌───────────────────┐
              │  Promise.race     │──→ 某个 task 完成 → 从 running 删除
              │ (等待任意一个完成) │      → 回到循环顶部
              └───────────────────┘
```

关键设计决策：

- **`Set<Promise<void>>` 作为任务跟踪器**：每个 task 的 `finally` 回调保证无论 resolve 还是 reject 都会从 Set 中移除，避免内存泄漏
- **`Promise.race` 作为调度触发器**：当并发数满时，等待**任意一个**完成，释放一个槽位，立即从队列中拉入新任务。相比 `Promise.all` 需要等整批完成，`race` 的吞吐量更优
- **无超时机制**：没有为单个 task 设置超时。LLM 调用如果挂起，会永久阻塞一个槽位。这是有意为之——重试由外层 `while (failed.length > 0)` 循环处理，单页超时会导致不可预测的状态

## `availablePages`：交叉引用列表的构建

这是模板变量中最复杂的部分，它在 `generatePages` 入口处一次性构建：

```typescript
const availablePages = allTopics
  .filter(t => !t.isGroup && t.slug)
  .map(t => `- slug: ${t.slug}.md | 标题: ${t.title} | 简介: ${(t.description || t.task || '').slice(0, 80)}`)
  .join('\n');
```

筛选逻辑：排除 `isGroup`（分组标题，无内容）和 `slug` 为空（解析错误）的条目。每条格式为：

```
- slug: 页面生成与并行控制.md | 标题: 页面生成与并行控制 | 简介: Phase 2 详解：遍历大纲逐页生成...
```

`description` 优先于 `task`，最长截断 80 字符。这个变量被注入到 `page-user.md` 模板的 `{{availablePages}}` 位置，LLM 借此知晓所有兄弟页面的 slug 和简介，从而生成正确的 `[页面标题](slug.md)` 交叉引用。

[来源](src/commands/generate.ts#L400-L403) | [来源](prompts/page-user.md#L8-L12)

## `generateIndex`：从 topics 重建 index.json

生成完成后，`generateIndex` 将 `Topic[]` 还原为 `index.json`。其步骤：

1. **提取去重章节名**：`[...new Set(topics.map(t => t.section).filter(Boolean))]`，保持首次出现顺序
2. **按章节分组**：逐章遍历，`topics.filter(t => t.section === section)`
3. **重建条目**：`isGroup` 的 topic 输出 `{ type: "group", title }`；普通 topic 输出 `{ level, title, description?, task? }`——注意 slug 不被写入 index.json，因为 slug 由标题在浏览端动态生成
4. **写入**：输出到 `.wiki/<timestamp>/index.json`

输出的 JSON 结构与 [生成结果说明](生成结果说明.md) 中定义的索引格式完全一致。

## 串行 vs. 并行：决策矩阵

| 维度 | 串行（`parallel: false`） | 并行（`parallel: true`） |
|------|--------------------------|--------------------------|
| 流式输出 | ✅ 实时可见 LLM 回复 | ❌ 仅显示最终结果 |
| 速度 | 慢（一次一页） | 快（并发数可调） |
| 中间状态 | 可随时目视检查质量 | 需等全部完成 |
| API 调用压力 | 1 路并发 | `concurrency` 路并发 |
| 适用场景 | 调试、质量敏感 | 批量生产、速度快优先 |

两种模式在命令行交互中由用户选择，默认串行。
