# 测试策略与单元测试

wiki-cli 的 6 个测试文件分布在 `tests/` 目录下，使用 **Vitest** 作为测试运行器。这些测试不追求覆盖率数字，而是针对项目中四类核心风险区域逐一击破：配置数据完整性、核心算法边界、网络层容错、以及工具调用的输入输出契约。

## Vitest 配置的决策逻辑

`vitest.config.ts` 只有寥寥数行，但每个选项都有它的理由：

```typescript
export default defineConfig({
  test: {
    globals: true,
    environment: 'node',
    include: ['tests/**/*.test.ts'],
  },
});
```

**`globals: true`** 让 `describe`、`it`、`expect`、`vi` 等 API 成为全局变量。项目中部分测试文件（如 `outline-parser.test.ts`、`prompts.test.ts`、`tools.test.ts`）利用了这一点，头部没有显式导入；而 `config-store.test.ts` 和 `llm-client.test.ts` 保留了 `import { describe, it, expect } from 'vitest'`——这反映出代码库从显式导入到全局 API 的渐进过渡。

**`environment: 'node'`** 是一个关键选择。项目完全依赖 Node.js 运行时：文件读写（`file.test.ts` 使用 `node:fs`）、HTTP 请求（`llm-client.test.ts` mock 了 `fetch`）、临时目录（`mkdtempSync`）——这些都不需要浏览器 DOM 模拟。`node` 环境是最轻量且精准的选择。

## config-store.test.ts：模型数据完整性

这个文件不测试配置的读写逻辑（那涉及文件系统），而是测试 **`default-models.json` 的数据完整性**。测试在 `beforeAll` 中从源码加载 JSON 文件，然后执行一组断言：

- JSON 必须是合法数组且条目数 ≥ 20
- 每个条目必须包含 `provider`、`model`、`baseUrl`、`description` 四个字段
- 7 个核心提供商（OpenAI、Google Gemini、Anthropic、xAI Grok、DeepSeek、Kimi、Mistral）全数在列
- 某些关键模型（如 `gpt-5.5`、`claude-opus-4-7`）存在
- `getProviders()` 返回唯一值，`getModelsByProvider()` 能按提供商正确筛选

这种测试策略适配项目生命周期：当开发者增加新模型或修改已有条目时，测试能立刻捕获格式不完整或拼写错误。这是 **契约测试** 在配置层的一种轻量实现。

## llm-client.test.ts：Mock 网络层覆盖 8 个场景

这是测试代码量最大（约 220 行）、Mock 策略最精妙的文件。核心思路：**用 `vi.fn()` 替换全局 `fetch`，让客户端的 `chat()` 和 `chatStream()` 以为在请求真实 API，实际接收的是预制响应**。

`beforeEach` / `afterEach` 负责保存和恢复 `globalThis.fetch`，确保测试间隔离。

### `createMockStream`：SSE 流的模拟工厂

这个辅助函数是流式测试的核心，值得仔细拆解：

```typescript
function createMockStream(chunks: any[]) {
  const encoder = new TextEncoder();
  const lines = chunks.map(c => `data: ${JSON.stringify(c)}\n`);
  lines.push('data: [DONE]\n');
  const all = lines.join('');

  return {
    body: {
      getReader() {
        let pos = 0;
        return {
          read() {
            if (pos >= all.length) {
              return Promise.resolve({ done: true, value: undefined });
            }
            const chunk = all.slice(pos, pos + 50);
            pos += 50;
            return Promise.resolve({ done: false, value: encoder.encode(chunk) });
          },
        };
      },
    },
    ok: true,
  };
}
```

它的工作流程分三步：

1. **序列化**：将传入的 chunk 数组（如 `[{ choices: [{ delta: { content: 'Hello' } }] }]`）逐个 `JSON.stringify`，每行加上 `data: ` 前缀和 `\n` 后缀。末尾追加 `data: [DONE]\n`——这是 OpenAI SSE 终止标记。
2. **分片**：将所有行拼接后，以 50 字节为单位切割（`all.slice(pos, pos + 50)`）。这不是必需，但更真实地模拟了网络分块传输。
3. **编码**：用 `TextEncoder` 将字符串片段编码为 `Uint8Array`，匹配浏览器 `ReadableStream` 的 `value` 类型。

返回的对象结构（`{ body: { getReader() { ... } }, ok: true }`）完全匹配 `Response` 接口，因此 `LLMClient.chatStream()` 中的 `response.body.getReader()` 调用可以无缝工作。

[来源](tests/llm-client.test.ts#L18-L46)

### 覆盖的测试场景

| 测试用例 | Mock 方式 | 验证点 |
|---|---|---|
| 正常内容流 | `createMockStream` 产生两个 `content` chunk | 输出包含 `type: 'content'` 和 `type: 'done'` |
| 工具调用流 | `createMockStream` 产生 `tool_calls` chunk | 输出包含 `type: 'tool_call'` |
| Reasoning 内容 | `createMockStream` 产生 `reasoning_content` chunk | 至少 2 个 reasoning chunk，内容正确 |
| 错误响应 | 返回 `{ ok: false, status: 401 }` | 输出 `type: 'error'`，不重试 |
| 非流式请求 | 拦截请求体后返回 `{ choices: [{ message: { content: '...' } }] }` | 请求体含 `model`、`messages`、`tools` |
| 5xx 重试 | 首次返回 503，第二次成功 | `chat()` 调用 2 次，最终得到内容 |
| 流式重试 | 首次返回 502，第二次正常 SSE | `chatStream()` 最终输出 `type: 'done'` |
| 网络错误重试 | 前 2 次 throw `ECONNRESET`，第 3 次成功 | `chat()` 调用 3 次 |
| 4xx 不重试 | 返回 401 | `fetch` 仅调用 1 次 |
| baseUrl 拼接 | 检查最终调用的 URL | URL 为 `{baseUrl}/chat/completions` |

重试机制的测试特别重要：每次 5xx 错误或网络异常触发重试时，`vi.fn().mockImplementation` 的内部计数器 `callCount` 会递增。测试通过断言 `callCount` 的最终值来验证重试次数，而非仅仅检查结果。

## outline-parser.test.ts：LLM 输出容错的 10 道防线

这个文件测试 `parseOutlineJson` 函数——它是 [两阶段生成流程](两阶段生成流程.md) 中从 LLM 原始响应中提取结构化大纲的关键环节。LLM 的输出格式极不可控，测试需要覆盖所有已知变体：

**基础解析**：将 `{ sections: [{ name: "入门指南", topics: [...] }] }` 展平为页面列表，每个 topic 映射为 `{ title, level, section, description, task }`。group 类型条目标记 `isGroup: true`。

**代码围栏剥离**：测试 `stripCodeFence` 处理三种情况：
- ` ```json ... ``` `——标准的 JSON 围栏
- ` ``` ... ``` `——无语言标识的围栏
- 无围栏的纯 JSON——不做处理

**杂讯文本过滤**：LLM 可能在大纲前后写解释性文字（如 "Here is the result: ... End."），测试使用 `match(/\{[\s\S]*\}/)` 提取 JSON 内容。

**字段兼容性**：新格式使用 `description` / `task`，旧格式使用 `brief`。测试验证 `brief` 能自动回退为 `description` 和 `task`。

**边界处理**：无效 JSON、错误结构（如无 `sections` 字段）、空字符串——全部返回空数组，不抛异常。

[来源](tests/outline-parser.test.ts#L1-L118)

## prompts.test.ts：模板渲染的边界条件

测试 `fillPrompt` 函数——一个基于 Mustache 风格 `{{变量}}` 替换的简易模板引擎。7 个测试覆盖了所有边界：

| 输入 | 变量 | 期望 | 测试意图 |
|---|---|---|---|
| `'Hello {{name}}'` | `{ name: 'World' }` | `'Hello World'` | 基础替换 |
| `'{{greeting}}, {{name}}!'` | `{ greeting: 'Hi', name: 'Alice' }` | `'Hi, Alice!'` | 多变量 |
| `'{{x}} + {{x}} = {{y}}'` | `{ x: '2', y: '4' }` | `'2 + 2 = 4'` | 同一变量多次 |
| `'Hello {{name}}'` | `{}` | `'Hello {{name}}'` | 变量缺失——保留原样 |
| `''` | `{ a: 'b' }` | `''` | 空模板 |
| `'static text'` | `{}` | `'static text'` | 无变量 |
| `'语言：{{lang}}'` | `{ lang: '中文' }` | `'语言：中文'` | 中文值 |

关键设计决策：变量缺失时不抛异常、不删除占位符，而是 **保留原样**。这让模板即使在不完整的上下文中也能部分工作，而不是完全崩溃。

## 当前测试的局限与改进方向

现有测试覆盖了单元层，但缺少以下维度的覆盖：

- **端到端 CLI 流程**：从 `wiki generate` 命令调起到完整的生成链路未测试，可以通过 `child_process.spawn` 配合 mock HTTP 服务器实现。
- **断点续传验证**：[断点续传与重试机制](断点续传与重试机制.md) 是项目特色功能，可以在临时目录中构造部分生成结果，验证 `generate` 命令识别并恢复的能力。
- **SSE 到工具调用的闭环**：`llm-client.test.ts` 验证了流式 chunk 包含 `tool_call`，但未验证这些 chunk 能否驱动完整的 **工具调用→结果回传→继续生成** 循环。
- **HTTP 与前端**：[HTTP 服务与前端渲染](http-服务与前端渲染.md) 和 [版本切换与源代码预览](版本切换与源代码预览.md) 当前无任何测试覆盖。
