- **`include: ['tests/**/*.test.ts']`** — 只匹配 `tests/` 目录下的 `.test.ts` 文件。

使用 `npm test`（即 `vitest run`）执行单次测试，或 `npm run test:watch` 进入监听模式。

### Mock 流式响应

测试文件定义了一个 `createMockStream` 辅助函数，接受 chunks 数组，构造一个可迭代的 `ReadableStream` 模拟对象。每个 chunk 被序列化为 SSE 格式的 `data: {...}\n`，末尾追加 `data: [DONE]\n` 标记结束。调用端通过 `getReader().read()` 逐段消费，模拟真实的流式读取。

[来源](tests/llm-client.test.ts#L13-L37)

### 流式 API：chatStream

| 测试场景 | mock 行为 | 断言 |
|---------|----------|------|
| 内容块 | 两次 `delta.content`（`Hello`、` World`） | yield 出 `type: 'content'` 和 `type: 'done'` |
| Tool Call 块 | `delta.tool_calls` 包含函数名和参数 | yield 出 `type: 'tool_call'` |

### 自动重试

| 场景 | 触发条件 | 行为 |
|------|---------|------|
| 5xx 服务端错误 | status 503/502 | 自动重试一次后成功（共 2 次调用） |
| 网络异常 | `Error('ECONNRESET')` 抛两次 | 第三次成功（共 3 次调用） |
| 4xx 客户端错误 | status 401 | **不重试**，只调用一次 |

这是区分 **临时故障** 和 **配置错误** 的关键策略：5xx 和网络错误有重试价值，4xx（如 API Key 无效）重试是浪费。

## Prompt 模板变量替换（prompts.test.ts）

`fillPrompt` 是 Prompt 模板系统的核心函数，负责将 `{{variable}}` 风格的占位符替换为实际值。

[来源](tests/prompts.test.ts#L4-L5)

### 覆盖的七种场景

| 场景 | 输入 | 期望输出 |
|------|------|---------|
| 单变量 | `'Hello {{name}}'` + `{name: 'World'}` | `'Hello World'` |
| 多变量 | `'{{greeting}}, {{name}}!'` + `{greeting: 'Hi', name: 'Alice'}` | `'Hi, Alice!'` |
| 重复变量 | `'{{x}} + {{x}} = {{y}}'` + `{x: '2', y: '4'}` | `'2 + 2 = 4'` |
| 未提供变量 | `'Hello {{name}}'` + `{}` | 保持 `'Hello {{name}}'` 不变 |
| 空模板 | `''` + `{a: 'b'}` | `''` |
| 无变量的静态文本 | `'static text'` + `{}` | `'static text'` |
| 中文内容 | `'语言：{{lang}}'` + `{lang: '中文'}` | `'语言：中文'` |

最值得注意的设计是 **未提供变量时保留原占位符**，而不是抛出错误或替换为空字符串。这意味着模板渲染是容错的，不会因为遗漏变量就崩溃。

[来源](tests/prompts.test.ts#L7-L41)

## 实践建议

如果你要添加新功能，以下测试模式值得遵循：

1. **工具类函数**：用 `mkdtempSync` 创建临时目录，测试完成后由操作系统自动清理，避免 mock 文件系统。
2. **网络客户端**：替换 `globalThis.fetch` 而非 mock 内部方法，这是最彻底的隔离方式。
3. **纯函数**（如 `fillPrompt`、`toSlug`）：无需任何 setup，直接调用、直接断言。
4. **配置数据**：直接读取 JSON 文件验证完整性，确保添加新模型时不会破坏已有结构。
