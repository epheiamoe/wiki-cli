# 命令行入口与命令注册

## 入口文件

`src/cli.ts` 是整个 wiki-cli 的单一入口，通过 `#!/usr/bin/env node` 声明为可执行脚本。所有用户操作——无论是生成 Wiki、浏览文档、AI 问答还是查看状态——都从这个文件分发。它只用了一层结构：文件顶部声明了 6 个命令的导入和 `logError`，中间是 `new Command()` 注册所有子命令，末尾调用 `program.parse(process.argv)`。[来源](src/cli.ts#L1-L3)

---

## 命令注册总览

`program` 使用 Commander.js 的链式 API 注册了 6 个子命令。下面是每个命令的标识、作用与参数数量对比：

| 命令 | 描述 | 选项数量 | 参数 |
|------|------|---------|------|
| `config` | 交互式配置 LLM/Embedding | 6 | 无 |
| `generate` | 分析仓库并生成 Wiki | 12 | 无 |
| `browse` | 在浏览器中浏览 Wiki | 2 | 无 |
| `status` | 对比 Wiki 版本与 Git 状态 | 5 | 无 |
| `ai` | AI 问答（交互式/单次） | 12 | 1 个可选 `[question]` |
| `tool-call` | 为 AI Agent 暴露工具接口 | 0 | 2 个必选 `<name> [args]` |

这些命令的实现函数分散在 `src/commands/` 目录下，cli.ts 只负责注册和参数映射，不包含业务逻辑。[来源](src/cli.ts#L11-L16)

---

## 通用参数：`-C`、`-u`、`-o`、`-b`

多个命令共享一组关于工作目录和远程仓库的参数。这些参数在 `src/cli.ts` 中各自独立定义，但实际解析逻辑统一由 [工作目录解析](工作目录解析.md) 模块 `resolveWorkDir` 处理。

- **`-C, --dir <path>`**：指定本地仓库目录。出现在 `generate`、`status`、`ai` 三个命令中。
- **`-u, --url <url>`**：指定远程 Git 仓库 URL，会自动克隆。出现在 `generate`、`browse`、`status`、`ai` 四个命令中。
- **`-o, --output <path>`**：输出路径。出现在 `generate` 和 `ai` 两个命令中。
- **`-b, --branch <name>`**：Git 分支。出现在 `generate` 和 `ai` 两个命令中。

另外，`generate` 和 `ai` 还共享 `-d, --depth <n>`（克隆深度）和 `-t, --temp`（临时模式）两个选项。这些重复定义不是巧合：Commander 的设计鼓励每个命令自描述，而不是从全局参数继承。[来源](src/cli.ts#L40-L42)

## `action` 回调中的 try-catch 模式

6 个命令的 `action` 回调遵循完全相同的错误处理结构：

```
action(async (...) => {
  try {
    await commandImpl(...);
  } catch (err: any) {
    logError(err.message);
    process.exit(1);
  }
});
```

这个模式做了两件事：

1. **统一错误输出**：所有业务异常都通过 `logError`（来自 `src/utils/progress.ts`）输出，保证错误信息的视觉风格一致。
2. **硬退出**：`process.exit(1)` 确保 CLI 进程不会在异常后保持挂起状态。

注意到 **只有 `err.message` 被输出**，不输出堆栈。这是面向终端用户的 CLI 设计：堆栈信息对调试有用，但对命令行操作者而言只是噪音。如果命令实现函数内部有更精细的错误处理（例如 LLM 超时重试），那是在 `commands/*.ts` 内部完成的，cli.ts 只负责最外层兜底。[来源](src/cli.ts#L33-L37)

## `config` 命令：无通用参数

`config` 是唯一没有 `-C/-u/-o/-b` 选项的命令。它只接受自身配置相关的选项（`--provider`、`--base-url`、`--model`、`--api-key`、`--lang`、`--llm-only`、`--embedding-only`），因为它的操作对象是用户主目录下的 `~/.wiki-cli/config.json`，不受项目工作目录影响。[来源](src/cli.ts#L18-L31)

这是合理的职权分离：[配置文件详解](配置文件详解.md) 中详细说明了配置的存储路径和字段含义。

---

## `generate` 命令：选项最多的命令

12 个选项中除了通用参数外，还包括：

- `-p, --parallel` 和 `-c, --concurrency <n>`：控制并行生成
- `-r, --retry <n>`：失败重试次数
- `-s, --silent`：静默模式，跳过交互提示
- `--browse`：生成后自动启动浏览器
- `--update`：[增量更新](增量更新-update-模式.md) 模式

注意 `-c` 和 `-r` 的默认值是字符串 `'3'` 和 `'0'`，在 `action` 中通过 `parseInt` 转为数字。这是 Commander 的惯用做法——选项默认值只能是字符串，类型转换在 action 层完成。[来源](src/cli.ts#L44-L58)

[生成 Wiki](生成-wiki.md) 页面详细描述了这些选项的完整使用场景。

## `ai` 命令：唯一带参数的命令

`ai` 是唯一使用 Commander `argument()` 方法的命令：

```
.argument('[question]', 'Optional question for single-answer mode')
```

这意味着用户可以直接输入 `wiki-cli ai "这个项目的架构是怎样的？"` 而无需使用 `-q` 前缀。同时，它也保留了 `-q, --question <text>` 作为与参数等价的替代方式。action 回调中通过 `const q = options.question || question;` 合并两者来源。[来源](src/cli.ts#L94-L105)

`ai` 还管理着会话相关的参数（`--session`、`--list-sessions`、`--all`、`--delete-session`）和 `-a, --answer-only`（非流式纯文本输出）。[AI 问答](ai-问答.md) 对这些功能有详细展开。

---

## `tool-call` 命令：两个必选参数

`tool-call` 不使用 option，而是两个 `argument`：

```
.argument('<name>', 'Tool name')
.argument('[args]', 'JSON arguments string')
```

`<name>` 带尖括号表示必选，`[args]` 带方括号表示可选——如果没有传入 JSON 参数，工具会使用默认空参数运行。`action` 回调直接调用 `toolCallCommand(name, args)`，内部由 [Tool 系统](tool-系统-定义与执行.md) 负责查找和验证工具名。[来源](src/cli.ts#L127-L133)

## `status` 命令：为什么 README 不强调它

对照 README，开头的命令概览只列出了 **generate、browse、ai、tool-call** 四个命令，config 在 Quick Start 中有说明，但 status 完全没有被提及。git log 显示 status 是在一次提交中完整加入的（`7841c14 wiki-cli status: 版本状态 + git diff对比 + .meta.json 元数据`），之后没有被删除。

status 的"隐身"有合理原因：

1. **它面向维护者而非首次使用者**：status 用于对比 Wiki 版本和当前 Git 状态的差异，属于"我已经生成过 Wiki，想看看有没有过时"的高级场景。
2. **增量更新是其真实消费者**：[增量更新](增量更新-update-模式.md) 作为 generate 的子模式，内部已经集成了 diff 分析能力。status 只是把同一套逻辑暴露给用户手动调用。
3. **它没有独立的配置或交互**：status 只读、只输出信息，不需要 Prompt 模板，也没有 AI 调用。

项目根目录的 README 定位是快速吸引新用户，自然优先展示"生成→浏览→问答"这条核心用户旅程，status 作为诊断工具被降级处理。[来源](src/cli.ts#L72-L89)

关于 status 的详细用法，参见 [查看状态](查看状态.md)。

## `program.parse` 与 `outputHelp` 兜底

```typescript
program.parse(process.argv);

if (!process.argv.slice(2).length) {
  program.outputHelp();
}
```

这两行是 CLI 的最后一道防线：

1. **`program.parse(process.argv)`**：Commander 的标准入口，解析 `process.argv`（即 `node cli.ts generate --parallel` 这样的命令行参数）。它内部会自动匹配子命令并触发对应的 `action`。

2. **`if (!process.argv.slice(2).length)` 兜底**：如果用户输入 `wiki-cli` 不带任何子命令（`process.argv.slice(2)` 为空数组），Commander 默认不会做任何事。这里显式调用 `program.outputHelp()` 打印帮助文本，让用户看到所有可用的子命令和选项。这是极简但有效的**零参数保底策略**。

这种"先 parse 再检查"的顺序需要注意：`outputHelp` 必须在 `parse` 之后调用，因为 Commander 需要先解析出子命令信息才能正确渲染帮助内容。[来源](src/cli.ts#L154-L157)

## 架构要点总结

- **cli.ts 只负责路由**：不包含任何业务逻辑，所有实现委托给 `src/commands/*.ts` 中的函数。
- **错误处理单一出口**：所有 action 共用 `catch (err) → logError → process.exit(1)` 模式，无例外。
- **每个命令自描述**：选项在各命令的 `.option()` 链中独立声明，不通过全局配置继承，保证了 `--help` 输出的完整性。
- **零参数友好**：无子命令时输出帮助信息，而非静默退出。
