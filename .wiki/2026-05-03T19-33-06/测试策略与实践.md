# 测试策略与实践

## 测试范围总览

wiki-cli 基于 **Vitest** 构建单元测试体系，共 6 个测试文件，覆盖了项目核心模块的独立验证。以下是各模块的测试分布：

| 测试文件 | 覆盖模块 | 测试重点 |
|---|---|---|
| `config-store.test.ts` | 配置存储与模型清单 | default-models.json 的完整性验证 |
| `file.test.ts` | 文件工具集 | 文件读写、Slug 生成、时间戳 |
| `llm-client.test.ts` | LLM 客户端核心实现 | 流式/非流式通信、重试机制、SSE 解析 |
| `outline-parser.test.ts` | 两阶段生成流程 | JSON 格式大纲解析、代码围栏剥离 |
| `prompts.test.ts` | 提示词模板引擎 | 变量插值模板渲染 |
| `tools.test.ts` | 工具调用系统 | 工具定义校验、工具执行模拟 |

所有测试匹配 `tests/**/*.test.ts` 模式，由 Vitest 自动收集执行。[来源](vitest.config.ts#L1-L7)

---

## Vitest 配置要点

配置文件 `vitest.config.ts` 中有两个关键选项：

### `globals: true`

使 `describe`、`it`、`expect`、`vi` 等全局可用，无需在每个测试文件中手动导入。对比项目中的实际代码，测试文件头部确实一分为二：`config-store.test.ts` 和 `llm-client.test.ts` 保留了显式导入，而 `outline-parser.test.ts`、`prompts.test.ts`、`tools.test.ts` 则利用了全局 API——这反映了项目从传统导入向全局 API 迁移的过渡状态。

### `environment: 'node'`

指定测试运行在 Node.js 环境而非浏览器的 jsdom 环境中。这是关键决策：项目操作的是文件系统、HTTP 请求、进程等 Node.js 原生 API，无需 DOM 模拟。例如 `file.test.ts` 直接使用 `node:fs` 和 `node:os` 创建临时目录，`llm-client.test.ts` 模拟 `fetch` 的流式响应——这些都要求纯 Node 运行时。

[来源](vitest.config.ts#L1-L7)

## 各模块测试深度分析

### 1. 配置存储 (`config-store.test.ts`)

测试不直接测试用户配置的读写（依赖文件系统），而是聚焦于 **模型清单数据的完整性**：

- 验证 `default-models.json` 是合法 JSON 数组且条目数 ≥ 20
- 每个条目必须包含 `provider`、`model`、`baseUrl`、`description` 四个必要字段
- 包含所有 7 个核心提供商：OpenAI、Google Gemini、Anthropic、xAI Grok、DeepSeek、Kimi、Mistral
- 验证 `getProviders()` 返回唯一值、`getModelsByProvider()` 按提供商筛选正确

这种测试数据完整性而非业务逻辑的策略尤其适合配置数据：当未来添加新模型时，测试能立即捕获格式错误。

[来源](tests/config-store.test.ts#L1-L68)

### 2. 文件工具集 (`file.test.ts`)

测试覆盖三个工具函数，均在 **临时目录** 中操作以避免污染项目文件：

- **`ensureDir` / `writeTextFile` / `readTextFile` / `removeDir`**：验证多层目录创建、文件读写、递归删除
- **`toSlug`**：7 个用例覆盖中文保留、英文转写、混合内容、多分隔符压缩、空输入兜底、前后空格处理、特殊字符替代——这是典型 **边界值全覆盖** 的单元测试风格
- **`getTimestamp`**：验证输出格式 `YYYY-MM-DDTHH-MM-SS` 和当前年份

关键设计：使用 `mkdtempSync` 创建独立沙箱，测试间互不干扰。[来源](tests/file.test.ts#L1-L61)

### 3. LLM 客户端 (`llm-client.test.ts`)

这是测试代码量最大、覆盖场景最深的文件。核心策略是 **通过 mock 全局 `fetch` 来模拟 OpenAI 兼容 API 的响应**，无需真实网络请求。

测试覆盖了 `LLMClient` 的两个核心方法：

| 方法 | 覆盖场景 | 关键验证点 |
|---|---|---|
| `chatStream()` | 正常内容流 | 逐块拼接 `content` 类型 chunk |
| `chatStream()` | 工具调用流 | 识别 `tool_call` 类型 chunk |
| `chatStream()` | reasoning 流 | 解析 `reasoning_content` 并回传 |
| `chatStream()` | 错误响应 (401) | 生成 `error` 类型 chunk，不重试 |
| `chat()` | 非流式请求 | 验证请求体含 `messages`、`tools`、`model` |
| `chat()` | 重试机制 | 5xx 错误自动重试最多 3 次，4xx 不重试 |
| `chat()` | 网络错误 | `ECONNRESET` 异常重试并最终成功 |
| `chat()` | baseUrl 拼接 | 验证最终 URL 为 `{baseUrl}/chat/completions` |

mock 流式响应的实现值得关注：`createMockStream` 将 JSON 数据编码为 SSE 格式的 `data: {...}\n\n`，并用 `TextEncoder` 分割成小块模拟分块传输——这直接反映了生产环境中真实的流式响应模式。[来源](tests/llm-client.test.ts#L1-L220)

### 4. 大纲解析器 (`outline-parser.test.ts`) ⭐ 项目特色

这是区分 wiki-cli 与通用工具测试的关键文件。它测试的是 **LLM 生成的 JSON 格式大纲的解析逻辑**，这是 [两阶段生成流程](两阶段生成流程.md) 的核心环节。

解析器 `parseOutlineJson` 需要处理以下现实场景：

- **纯 JSON 解析**：将 `{ sections: [{ name, topics: [...] }] }` 结构展平为页面列表
- **代码围栏剥离**：LLM 经常将输出包裹在 ` ```json ... ``` ` 中，`stripCodeFence` 必须处理 ` ```json ` 和 ` ``` ` 两种变体
- **杂讯文本过滤**：LLM 可能在大纲前后添加解释性文本，测试模拟了"Here is the result: ... End."这种常见格式
- **字段兼容性**：支持 `description`/`task` 新字段与 `brief` 旧字段的自动回退
- **边界处理**：无效 JSON、错误结构、缺失字段均返回空数组

测试共计 10 个用例，几乎穷举了 LLM 输出格式的所有变体。[来源](tests/outline-parser.test.ts#L1-L118)

### 5. 提示词模板 (`prompts.test.ts`)

测试引擎 `fillPrompt` 的变量插值功能：

- 单变量、多变量、同一变量多处的替换
- 未提供变量时保留原样（不抛出异常）
- 空模板、空变量对象、中文变量值

这个模块本身逻辑简单（基于正则替换），测试更关注的是 **容错性**：确保生产环境中即使缺少上下文变量也不会崩溃。[来源](tests/prompts.test.ts#L1-L39)

### 6. 工具调用系统 (`tools.test.ts`) ⭐ 项目特色

这是第二个具有 wiki-cli 独特价值的测试套件。它测试的是 [工具调用系统](工具调用系统.md) 中的 `toolDefinitions` 与 `executeToolCall` 两个核心导出。

**第一部分：工具定义校验**

- 确认导出数组包含全部 **10 个工具**
- 验证每个工具名称准确：`list_directory`、`list_files`、`read_file`、`search_in_files`、`git_log`、`git_show`、`git_remote_info`、`dotenv_template`、`list_wiki_pages`、`read_wiki`
- 每个工具的 `parameters.type` 必须为 `"object"`（OpenAI Function Calling 规范要求）

**第二部分：工具执行模拟**

在临时目录中搭建微型测试环境（含 `test.txt`、`app.ts`、嵌套子目录），模拟实际工具调用：

| 工具调用 | 场景 |
|---|---|
| `list_files` | 列出目录文件、按扩展名过滤 |
| `read_file` | 读取内容、指定行范围、文件不存在错误 |
| `search_in_files` | 匹配模式存在/不存在 |
| `list_directory` | 返回目录树 |
| 缺失参数 | 验证 `file_path`/`dir_path`/`path` 缺失时返回 error |

每个工具调用的结果结构包含 `type`（`success`/`error`）和 `data`，与 LLM Function Calling 的规范一致。[来源](tests/tools.test.ts#L1-L158)

## 当前测试体系的优势与局限

### 优势

- **独立沙箱化**：文件工具与工具函数测试均使用临时目录，不依赖生产文件
- **无外部依赖**：LLM 客户端测试通过 mock `fetch` 实现，不依赖真实 API
- **边界全覆盖**：Slug 生成 7 个用例、JSON 解析 10 个用例，体现了严谨的测试设计

### 局限与改进方向

当前缺失 **集成测试**，这主要体现在：

1. **端到端 CLI 流程**：从 `wiki generate` 命令调用到大纲生成→页面生成的完整链路未测试。建议使用 Vitest 的 `child_process` spawn 执行 CLI 实际命令，配合 mock HTTP 服务器模拟 LLM API 响应。

2. **断点续传场景**：[断点续传与并行生成](断点续传与并行生成.md) 机制缺少验证。可以通过在临时目录创建部分生成结果后重新运行命令来验证恢复逻辑。

3. **SSE 解析与工具调用的闭环**：`llm-client.test.ts` 模拟了流式响应中的 `tool_call` chunk，但未验证这些 chunk 能否驱动 `executeToolCall` 完成一轮完整的 **工具调用→结果回传→继续生成** 循环。建议添加一个端到端 mock，让 LLM 先返回工具调用、系统自动执行工具后再次请求 LLM。

4. **HTTP 服务器测试**：[本地 HTTP 服务器实现](本地-http-服务器实现.md) 和 [浏览器端 SPA 体验](浏览器端-spa-体验.md) 没有任何覆盖，可以通过 `node:http` 发送实际请求并验证响应状态码和内容类型。

[来源](tests/config-store.test.ts#L1-L68)
