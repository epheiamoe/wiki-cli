# 错误处理与日志体系

终端用户体验的质量，往往取决于反馈的即时性与可读性。wiki-cli 围绕 **chalk** 与 **ora** 两个轻量库，构建了一套分级清晰的日志输出与进度指示体系，让用户在漫长的 LLM 生成过程中，始终能感知到系统的状态变化。

## 五级日志函数

所有日志函数集中定义在 `src/utils/progress.ts` 中，每个函数对应一种语义颜色和一个 Unicode 符号前缀：

| 函数 | 颜色 | 符号 | 语义 |
|------|------|------|------|
| `logInfo` | `chalk.blue` | `ℹ` | 阶段性提示，如"开始生成大纲" |
| `logSuccess` | `chalk.green` | `✔` | 操作成功完成 |
| `logWarning` | `chalk.yellow` | `⚠` | 非致命异常，如部分页面生成失败 |
| `logError` | `chalk.red` | `✖` | 致命错误，如网络断开、配置缺失 |
| `logStreamContent` | `chalk.cyan` | 无（写入 stdout） | 流式文本内容实时输出 |

前四个函数通过 `console.log` 输出带前缀的消息，第五个则使用 `process.stdout.write` 直接写入标准输出流，避免换行，适合持续追加的流式场景。[来源](../src/utils/progress.ts#L8-L25)

这些函数在四条 CLI 命令中均有使用。以 `cli.ts` 为例，每个命令的顶层 `catch` 块都调用 `logError` 终止进程：

```typescript
} catch (err: any) {
  logError(err.message);
  process.exit(1);
}
```

[来源](../src/cli.ts#L28-L31)

## LLM 工具调用的可视化

当生成流程触发了 LLM 的 **Function Calling** 时，系统需要在终端呈现工具调用的完整链路，让开发者看到"AI 调用了什么工具、传了什么参数、拿到了什么结果"。

`logToolCall` 使用 `chalk.magenta` 渲染扳手图标 `🔧`，以粗体显示工具名称，灰色展示参数 JSON：

```typescript
console.log(chalk.magenta('🔧'), chalk.bold(`Tool: ${name}`), chalk.gray(JSON.stringify(args)));
```

`logToolResult` 以缩进箭头 `↳` 开头，截取结果的前 100 字符作为预览（过长则截断加 `...`），防止大量源码数据填满终端：

```typescript
const preview = typeof result.data === 'string'
  ? result.data.slice(0, 100) + (result.data.length > 100 ? '...' : '')
  : JSON.stringify(result.data).slice(0, 100);
console.log(chalk.green('  ↳'), chalk.gray(`Result: ${preview}`));
```

[来源](../src/utils/progress.ts#L28-L35)

在 `generate.ts` 的 `collectFullResponse` 函数中，这两者配对出现：

```typescript
if (stream) logToolCall(tc.function.name, args);
const result = await executeToolCall(tc.function.name, args);
if (stream) logToolResult(tc.function.name, result);
```

[来源](../src/commands/generate.ts#L356-L358)

这样的设计让因果链一目了然：工具名 → 参数 → 结果预览。

## 基于 ora 的进度指示器

**createSpinner** 是对 `ora` 库的极薄封装：

```typescript
export function createSpinner(text: string) {
  return ora(text).start();
}
```

[来源](../src/utils/progress.ts#L3-L5)

`ora` 提供了终端 spinner 动画，`start()` 立即开始旋转并显示文本。调用方可以保留返回的 spinner 实例，在操作完成后调用 `succeed()` 或 `fail()` 切换状态。这一模式在 `generate.ts` 的两阶段流程中尤其有用——大纲生成和页面生成期间，spinner 配合 `logInfo` 提示用户当前处于哪个阶段。

## 流式输出中的 reasoning 与 content 交替

这是整个日志体系中最具表现力的部分。当 LLM 返回流式响应时，`collectFullResponse` 函数需要解析两种不同类型的流块：**推理过程**（reasoning）与 **最终内容**（content），并在终端中差异化呈现。

核心逻辑位于 `generate.ts` 的 `collectFullResponse` 函数中（约第 260-285 行）：

```typescript
if (chunk.type === 'reasoning' && chunk.reasoning_content) {
  currentReasoning += chunk.reasoning_content;
  if (!reasoningStarted) {
    reasoningStarted = true;
    process.stdout.write(chalk.dim.yellow('\nThinking: '));
  }
  process.stdout.write(chalk.dim.yellow(chunk.reasoning_content));
} else if (chunk.type === 'content') {
  if (!contentStarted && reasoningStarted) {
    contentStarted = true;
    console.log('');
  }
  currentContent += chunk.content ?? '';
  process.stdout.write(chunk.content ?? '');
}
```

[来源](../src/commands/generate.ts#L260-L275)

这段代码实现了三个关键的视觉过渡：

1. **首次出现 reasoning 块**：输出暗黄色的 `\nThinking: ` 标签，提示用户模型正在内部推理。
2. **reasoning 持续输出**：后续内容全部以 `chalk.dim.yellow` 渲染，视觉上弱化，暗示这是"中间思考过程"而非最终输出。
3. **切换到 content**：遇到内容块时，如果此前已有 reasoning 输出，插入一个空行作为分隔，然后以默认颜色（无 chalk 修饰）输出最终内容，与 reasoning 的暗黄色形成鲜明对比。

同样的模式也在 `ai.ts` 中的交互式 AI 会话中完整复现，确保用户在[AI 问答交互](ai-问答交互.md)时获得一致的视觉体验。[来源](../src/commands/ai.ts#L152-L160)

这种"先暗黄推理、再清亮回答"的视觉节奏，直接映射了 LLM 的思考-回答两阶段行为。数据来源是 `llm-client.ts` 中解析 SSE 流时对 `delta.reasoning_content` 和 `delta.content` 的分发：

```typescript
if (delta?.content) {
  yield { type: 'content', content: delta.content };
}
if (delta?.reasoning_content) {
  yield { type: 'reasoning', reasoning_content: delta.reasoning_content };
}
```

[来源](../src/ai/llm-client.ts#L159-L163)

## chalk 的跨平台终端颜色支持

以上所有日志函数都依赖 **chalk** 实现颜色输出。chalk 的核心价值在于**跨平台兼容性**：它在 Node.js 的标准输出上自动检测终端是否支持 ANSI 转义序列，若不支持则降级为纯文本输出，不会出现乱码。在 Windows 环境下（如本项目的开发环境 `win32 x64`），chalk 利用 Node.js 的 `process.stdout.getColorDepth()` 自动适配 PowerShell、CMD 和 Windows Terminal 的不同颜色能力。

所有日志函数使用的 chalk 调用总结：

| 效果 | chalk API | 用途 |
|------|-----------|------|
| 蓝色 | `chalk.blue('ℹ')` | `logInfo` |
| 绿色 | `chalk.green('✔')` / `chalk.green('  ↳')` | `logSuccess` / `logToolResult` |
| 黄色 | `chalk.yellow('⚠')` / `chalk.dim.yellow(...)` | `logWarning` / reasoning 内容 |
| 红色 | `chalk.red('✖')` | `logError` |
| 青色 | `chalk.cyan(...)` | `logStreamContent` |
| 品红 | `chalk.magenta('🔧')` | `logToolCall` 图标 |
| 灰色 | `chalk.gray(...)` | 参数与结果预览 |
| 粗体 | `chalk.bold(...)` | 工具名称强调 |

[来源](../src/utils/progress.ts#L8-L35)

无需关心颜色代码本身，chalk 的链式 API（如 `chalk.dim.yellow`）让渲染逻辑在代码中一目了然，与 `console.log` / `process.stdout.write` 无缝集成。

## 设计要点回顾

- **单一职责**：`progress.ts` 只负责终端输出，不包含业务逻辑，可在所有命令中按需导入。
- **因果可视化**：`logToolCall` → `logToolResult` 的配对输出，让 LLM Function Calling 的决策-执行链透明化。
- **视觉梯度**：reasoning 用 `dim.yellow` 弱化，content 用默认色强化，用户自然地将注意力导向最终内容。
- **零依赖封装**：对于 spinner 和颜色，没有在项目内再包一层抽象——直接导出 `ora` 和 `chalk` 的一行封装，保持了底层库的完整 API 能力。
