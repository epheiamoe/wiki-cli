# 提示词模板引擎：解耦的模板渲染

提示词是与 LLM 沟通的桥梁。写死在代码里的提示词难以维护——改一句提示词就要重新编译；更糟糕的是，用户无法自定义文档风格和回答方式。[提示词模板引擎]()模块将模板外化为 `prompts/` 目录下的 Markdown 文件，只保留一个轻量的插值引擎在代码中，实现了**模板与逻辑的彻底解耦**。

## 路径解析：PROMPTS_DIR 的计算逻辑

引擎的核心入口是 `src/ai/prompts.ts`，仅 30 行代码。它的第一个关键决策是定位模板目录。

```typescript
const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

const PROMPTS_DIR = resolve(__dirname, '..', '..', 'prompts');
```

这里的计算链是：

1. `import.meta.url` 拿到 ESM 模块的 `file://` 协议路径；
2. `fileURLToPath` 将其转为平台原生路径；
3. `dirname` 取到 `src/ai/`；
4. `resolve(__dirname, '..', '..', 'prompts')` 向上两级回到项目根目录，再进入 `prompts` 目录。

最终 `PROMPTS_DIR` 指向 `<project-root>/prompts/`。[来源](src/ai/prompts.ts#L3-L9)

`loadPrompt` 函数只是简单地将文件名拼接在这个路径上：

```typescript
export async function loadPrompt(filename: string): Promise<string> {
  const fullPath = join(PROMPTS_DIR, filename);
  return readFile(fullPath, 'utf-8');
}
```

因此调用 `loadPrompt('outline-system.md')` 实际读取的是 `prompts/outline-system.md`。[来源](src/ai/prompts.ts#L14-L17)

> 注意：用户修改 `prompts/` 下的模板后，无需重启应用即可生效——模板是运行时读取的，这是解耦带来的直接好处。

## 两步渲染流程：loadTemplate → fillPrompt

渲染一个提示词涉及两个纯粹的步骤，暴露三个 API：

```
┌────────────────────────────────────────────────────────────────────┐
│                        renderPrompt(filename, vars)                │
│                                                                     │
│   ┌──────────────┐     ┌──────────────────┐                        │
│   │ loadPrompt()  │ ──► │ fillPrompt()     │ ──► 最终字符串      │
│   │ (读文件)      │     │ (正则替换 {{var}})│                        │
│   └──────────────┘     └──────────────────┘                        │
│         │                       │                                   │
│   从 PROMPTS_DIR          用 /{{key}}/g 全局替换                    │
│   读取完整文件内容        未匹配的变量保持原样                      │
└────────────────────────────────────────────────────────────────────┘
```

**`fillPrompt`** 使用正则 `/\{\{key\}\}/g` 对模板中所有出现的 `{{key}}` 做全局替换。它的关键行为：

- **同一变量出现多次**，全部替换（`{{x}} + {{x}} = {{y}}` → `"2 + 2 = 4"`）；
- **不存在的变量**，保持原样不报错（`"Hello {{name}}"` 传入空对象 → 输出 `"Hello {{name}}"`）；
- **空模板** 或 **空变量对象** 都安静处理。[来源](src/ai/prompts.ts#L19-L25)

这些特性通过 7 个单元测试覆盖，包括中文字符值。[来源](tests/prompts.test.ts#L1-L37)

**`renderPrompt`** 是组合函数，先 `loadPrompt` 再 `fillPrompt`。[来源](src/ai/prompts.ts#L27-L30)

## 五个模板的用途与变量契约

`prompts/` 目录下存放 5 个 Markdown 模板，分为三组。

### 大纲生成组：outline-system + outline-user

这对模板用于 [生成命令：wiki-cli generate](生成命令-wiki-cli-generate.md) 中的**大纲生成阶段**。

| 模板 | 角色 | 注入变量 |
|------|------|----------|
| `outline-system.md` | System Prompt | `workDir`, `os` |
| `outline-user.md` | User Prompt | `workDir`, `os`, `lang` |

**`outline-system`** 定义 LLM 作为"资深软件工程师兼技术文档专家"的角色，授予它 8 个只读探索工具（[工具系统：LLM 只读探索工具的设计](工具系统-llm-只读探索工具的设计.md)），并指定 4 步分析框架（高层愿景→架构剖析→受众分析→生成JSON目录）。[来源](prompts/outline-system.md)

**`outline-user`** 是任务指令模板：向 LLM 传递工作目录、操作系统和文档语言，要求它探索项目后输出 JSON 格式的文档目录。[来源](prompts/outline-user.md)

调用位置在 `src/commands/generate.ts#L169-L170`：

```typescript
const systemPrompt = await renderPrompt('outline-system.md', outlineSysVars);
const userPrompt = await renderPrompt('outline-user.md', outlineUserVars);
```

### 页面生成组：page-system + page-user

这对模板用于**页面生成阶段**，每个大纲主题都会触发一次。

| 模板 | 角色 | 注入变量 |
|------|------|----------|
| `page-system.md` | System Prompt | `workDir`, `os`, `pageTitle`, `audienceLevel` |
| `page-user.md` | User Prompt | `workDir`, `pageTitle`, `audienceLevel`, `pageSlug`, `projectSummary`, `lang`, `availablePages`, `pageTask` |

**`page-system`** 定义 LLM 作为"架构分析型技术作者"的角色，强调：
- Diátaxis 框架组织内容
- 叙事节奏（吸引→兴趣→欲望→行动）
- 关键概念首次出现用粗体
- 每段末尾标注源码来源
- 交叉引用使用 Markdown 链接格式

它还包含严格的内容生成规则和工具使用策略。[来源](prompts/page-system.md)

**`page-user`** 是页面生成的任务卡片：传递元数据（页面标题、受众水平、slug）、项目上下文（工作目录、已有页面列表）、以及该主题的生成任务（`task` 字段）。[来源](prompts/page-user.md)

调用位置在 `src/commands/generate.ts#L469-L470`：

```typescript
const systemPrompt = await renderPrompt('page-system.md', pageSysVars);
const userPrompt = await renderPrompt('page-user.md', pageUserVars);
```

两个阶段的完整编排逻辑参见 [生成管线：从大纲到页面的完整流程](生成管线-从大纲到页面的完整流程.md)。

### AI 问答组：ai-system

**`ai-system`** 是唯一独立的模板，用于 [AI 交互命令：wiki-cli ai](ai-交互命令-wiki-cli-ai.md)。

相比大纲/页面模板的严格生成规则，`ai-system` 的角色设定更灵活——它定义 LLM 为"资深代码分析师"，负责为开发者解释代码库。它注入的变量包括：

| 变量 | 来源 | 用途 |
|------|------|------|
| `workDir` | 工作区路径 | 告诉 LLM 当前分析哪个仓库 |
| `os` | `process.platform + process.arch` | 操作系统环境 |
| `wikiInfo` | 已生成的 Wiki 内容 | 预读上下文，优先使用 |
| `wikiTools` | 是否存在 Wiki | 有条件地暴露 Wiki 工具 |

它还列出了可用的工具集（目录探索、文件读取、Git 操作），并指定行为准则：先查 Wiki 再查源码、标注引用来源、支持持续对话。[来源](prompts/ai-system.md)

调用位置在 `src/commands/ai.ts#L112`：

```typescript
const systemPrompt = await renderPrompt('ai-system.md', aiSysVars);
```

## 设计启示

模板引擎的极简设计（30 行源码 + 7 行测试）并非能力不足，而是有意为之。它的职责边界清晰：

1. **只做一件事**：从文件系统读取模板，用变量替换占位符；
2. **不做的事**：不解析模板语法，不缓存，不校验变量完整性；
3. **信任调用方**：未匹配的变量保持原样而非报错，把校验责任交给上层。

这种"薄引擎 + 厚模板"模式让用户可以通过修改纯文本模板来定制整个生成流程，无需接触 TypeScript 代码。详见 [自定义提示词模板](自定义提示词模板.md)。
