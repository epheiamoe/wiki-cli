# 自定义提示词模板

## 模板架构全景

`wiki-cli` 的生成管线依赖 5 个外部 Markdown 模板文件，存放于项目根目录的 `prompts/` 文件夹。这些模板定义了 LLM 在 **大纲生成** 和 **页面生成** 两个阶段的行为，以及 **交互式 AI 问答** 的系统角色。模板与引擎的分离设计使你不必改动一行代码即可重塑整个文档的输出风格、分析深度和来源标注方式。

## {{变量}} 的注入机制

所有模板变量通过 `src/ai/prompts.ts` 中的 `renderPrompt` 函数注入。引擎分两步执行：

1. **`loadPrompt(filename)`** — 从 `prompts/` 目录读取原始 Markdown 文本。
2. **`fillPrompt(template, vars)`** — 遍历 `PromptVars` 键值对，用全局正则 `/\\{\\{key\\}\\}/g` 替换所有匹配的占位符。

关键实现细节：`fillPrompt` 使用的是 **贪婪全局替换**（`replaceAll` 通过正则 `g` 标志实现），这意味着如果模板中同一个变量出现多次，所有出现位置都会被正确替换。但如果模板中包含未在 `vars` 中定义的 `{{unknownVar}}`，它将 **保持原样** 留在输出中，不会被移除也不报错。

[来源](src/ai/prompts.ts#L15-L30)

## 分析框架的范式差异：outline vs page

这是整个模板系统中最重要的设计决策，理解这一点才能正确修改模板。

### `outline-system.md`：结构化分析框架

该模板定义一个 **4 步分析管线**，引导 LLM 采用工程化的方式拆解项目：

1. **高层愿景与价值** — 项目解决什么核心问题？
2. **架构深度剖析** — 核心模块有哪些？如何交互？
3. **受众分析** — 文档面向前端/后端/算法/学习者？
4. **生成 JSON 格式目录** — 按严格模式输出两级目录结构

输出格式为 **JSON**，包含 `sections` → `topics` 的嵌套结构，每个 topic 有 `level`、`title`、`description`、`task` 字段。要求 LLM **仅输出 JSON**，不附加任何文字。这意味着该模板实际上定义了一个 **受约束的生成协议**——LLM 的"思考"被限制在分析框架内，输出被限制在 JSON schema 内。

[来源](prompts/outline-system.md)

### `page-system.md`：Diátaxis 写作框架

该模板采用 **Diátaxis** 内容分类法（教程/指南/解释/参考），引导 LLM 根据主题类型选择组织方式：

- **叙事节奏**：吸引 → 兴趣 → 欲望 → 行动（AIDA 模型）
- **视觉规范**：Mermaid 图表、表格、粗体标记
- **证据标准**：每段末尾标注来源，路径含完整前缀
- **交叉引用**：使用 `[标题](slug.md)` 格式链接

输出格式为 **Markdown**，无 JSON 约束。LLM 被鼓励根据内容自由选择段落结构，但必须遵守来源标注和交叉引用的硬规则。

[来源](prompts/page-system.md)

### 差异总结

| 维度 | `outline-system.md` | `page-system.md` |
|---|---|---|
| 方法论 | 自定义 4 步分析框架 | Diátaxis 分类法 |
| 输出格式 | JSON（严格 schema） | Markdown（自由格式） |
| 约束强度 | 高（仅输出 JSON） | 中（格式自由，规则固定） |
| 认知负荷 | 分析型、结构化 | 创作型、叙事化 |
| 变量密度 | 低（2 个变量） | 高（4 + 8 个变量） |

## 如何通过修改模板调整输出格式

以下修改操作均在 `prompts/` 目录下进行，修改即时生效，**无需重新编译**（模板在运行时每次调用 `renderPrompt` 时重新读取）。

### 示例 1：在所有页面强制增加 Mermaid 图表要求

在 `prompts/page-system.md` 的「视觉规范」段落中增加指令：

```markdown
## 视觉规范
- 适当时使用 Mermaid 图表说明架构关系。
- **每个页面至少包含一个 Mermaid 图表**，除非页面内容不足 200 字。
- 多维比较使用表格。
```

大括号不会被 LLM 误解为变量，因为 `page-system.md` 中使用的变量是 `{{workDir}}`、`{{os}}` 等，Mermaid 代码块使用 ` ```mermaid` 标记，不在同一语法空间。

### 示例 2：调整来源标注风格

在 `prompts/page-system.md` 的「证据标准」段落中修改格式要求：

```markdown
## 证据标准
- 每节末尾标注来源，使用标准 Markdown 链接格式：`[来源](相对路径#L行号-L行号)`。
- **将来源标注集中到页面末尾的「参考资料」章节**，使用有序列表。
```

对应地，需要在 `page-system.md` 中增加一条约束，要求使用统一的「参考资料」节。

### 示例 3：改变大纲输出的目录深度

在 `prompts/outline-system.md` 中修改 JSON schema 约束。当前限定只有两级 section → topic：

```markdown
- 分为两个部分：`入门指南` 和 `深入探索`
- 主题总数不超过 30 个
```

若需支持三级目录，需扩展 JSON schema 定义并调整 `src/commands/generate.ts` 中的 `Topic` 类型解析逻辑（因为当前解析器只按 `Topic` 结构读取，不支持嵌套 `subTopics`）。

### 示例 4：修改用户提示以覆盖语言

`prompts/outline-user.md` 和 `prompts/page-user.md` 中通过 `{{lang}}` 变量传递语言参数。若要强制 LLM 以特定风格输出，可在模板中扩展指令：

```markdown
- 使用 {{lang}} 书写。
- **风格要求**：简明扼要，每段不超过 5 句。使用主动语态。
```

## 模板修改的风险与边界

### 风险 1：变量名不匹配导致占位符泄露

如果模板中引入了 `{{newVar}}` 但没有在调用处传入该键，`fillPrompt` 不会报错，模板中的 `{{newVar}}` 原样出现在发送给 LLM 的提示中。LLM 可能：

- 忽略它（如果能从上下文推断含义）
- 将其解释为模板语法并尝试"填充"
- 输出包含 `{{newVar}}` 的 Markdown 文本，破坏输出质量

**防御措施**：修改模板后运行 `wiki-cli generate` 前，务必检查 `src/commands/generate.ts` 和 `src/commands/ai.ts` 中的变量构造代码，确保每一对 `renderPrompt` 调用传入的 `PromptVars` 覆盖了模板中所有 `{{key}}`。

### 风险 2：JSON schema 破坏导致解析失败

如果修改 `prompts/outline-system.md` 中的 JSON 结构要求（如增加/减少字段、改变嵌套层级），但未同步更新 `src/commands/generate.ts` 中的 `Topic` 类型定义和 `parseOutlineContent` 函数，LLM 输出的 JSON 将无法被正确解析，生成管线会在此阶段卡死。

当前 `Topic` 接口期望的字段包括 `title`、`level`、`description`、`task`、`isGroup`、`slug`。任何面向 LLM 的 schema 变更都需要在解析器侧同步更新。

[来源](src/commands/generate.ts#L431-L434) | [参见生成管线](生成管线-从大纲到页面的完整流程.md)

### 风险 3：指令冲突导致 LLM 行为不稳定

`page-system.md` 和 `page-user.md` 分别作为 system prompt 和 user prompt 发送给 LLM。如果两者的指令存在矛盾（如 system 说"使用 Mermaid 图表"，user 说"不要使用任何图示"），LLM 的行为将不可预测——不同模型、不同温度参数下可能选择遵从不同的指令。

**设计原则**：system prompt 定义 **恒常规则**（来源格式、交叉引用规范），user prompt 定义 **任务参数**（页面标题、受众层级）。将行为约束集中在一处，避免分散。

### 风险 4：过度结构化扼杀 LLM 创造力

`outline-system.md` 的高度结构化约束（仅输出 JSON）在大纲阶段是合理的，因为它需要机器可解析的输出。但如果 `page-system.md` 也施加过强的格式模板（如要求每页必须包含"概述→架构→用法→总结"四个章节），LLM 将丧失根据主题类型选择叙事方式的能力，文档将变得千篇一律。

## 推荐工作流

```
修改 prompts/*.md → 运行 wiki-cli generate → 检查输出质量
        ↑                                        │
        └───────────── 调整模板 ──────────────────┘
```

具体步骤：

1. 备份原始模板：`cp prompts/page-system.md prompts/page-system.md.bak`
2. 编辑目标模板，保持变量名不变
3. 运行 `wiki-cli generate --parallel` 生成全部页面
4. 检查 `.wiki/temp/` 下的输出，验证来源格式、图表、语言风格
5. 若不满意，回滚或继续调整模板并重新生成（利用断点续传机制，已成功的页面不会被覆盖）
6. 确认满意后运行 `wiki-cli generate --finalize` 构建正式文档
