# 工作区管理与远程仓库克隆

工作区解析是 `wiki-cli` 所有命令的起点——无论是 `generate`、`ai` 还是 `browse`，在执行核心逻辑之前都需要先确定"代码在哪里"。这个决策由 `resolveWorkDir` 函数统一处理，它根据用户提供的参数走两条完全不同的路径：**远程克隆**或**本地目录**。

## 决策树：有 URL 与无 URL 的分岔口

`resolveWorkDir` 的入口是一个简单的 `if (url)` 判断，从这里分岔出两条执行路径。

```mermaid
flowchart TD
    A[resolveWorkDir 入口] --> B{有 url？}
    B -->|是| C{确定目标目录}
    B -->|否| D{有 dir？}
    
    C -->|temp=true| E[os.tmpdir()/wiki-cli-* 临时目录]
    C -->|有 output| F[resolve(output) 指定目录]
    C -->|默认| G[~/.wiki-cli/repos/<url-derived-name>]
    
    E --> H[ensureRepo: git clone]
    F --> H
    G --> H
    
    H --> I[process.chdir]
    I --> J{temp?}
    J -->|是| K[返回 cleanup 函数]
    J -->|否| L[不返回 cleanup]
    
    D -->|是| M[resolve(dir)]
    D -->|否| N[process.cwd()]
    
    M --> O[检查目录是否存在]
    N --> O
    
    O -->|不存在| P[抛出错误]
    O -->|存在| Q[process.chdir]
```

这是整个工作区管理的骨架。[来源](src/utils/workspace.ts#L30-L62)

### 远程克隆路径（有 `url`）

当提供 `--url` 参数时，系统需要决定把仓库克隆到哪里。这里有三种策略，由 `--temp` 和 `--output` 两个布尔/路径参数控制：

| 参数组合 | 目标目录 | 生命周期 | 适用场景 |
|---------|---------|---------|---------|
| 无 `--temp` 无 `--output` | `~/.wiki-cli/repos/<url-derived-name>` | 持久化，复用缓存 | 反复分析的长期项目 |
| 有 `--output` | 用户指定的绝对/相对路径 | 用户自行管理 | 生成后需要保留文档的项目 |
| 有 `--temp` | 系统临时目录 `os.tmpdir()` | 会话结束自动清理 | 一次性分析、CI 环境 |

**URL 到目录名的转换**由 `urlToDirName` 函数负责：它会剥离协议前缀（`https://`），移除 `.git` 后缀，再将剩余的 `/` 和 `:` 统一替换为 `-`。例如 `https://github.com/user/project.git` 会被转换为 `github.com-user-project`，然后拼接到 `~/.wiki-cli/repos/` 之后形成完整缓存路径。[来源](src/utils/workspace.ts#L16-L20)

目标目录确定后，调用 `ensureRepo` 执行实际的克隆或更新操作（见下一节）。克隆成功后执行 `process.chdir(targetDir)` 切换到该目录，后续所有文件操作都在此上下文中进行。[来源](src/utils/workspace.ts#L44-L54)

对于 `--temp` 模式，`resolveWorkDir` 还会返回一个 `cleanup` 函数，调用方在任务结束后执行它以递归删除临时目录。这个函数使用动态导入（`await import('node:fs/promises')`）来避免不必要的模块加载。[来源](src/utils/workspace.ts#L49-L56)

### 本地目录路径（无 `url`）

没有 `--url` 时，系统认为用户想分析本地已有的代码仓库。优先使用 `--dir`（即 `-C` 参数）指定的路径，若未提供则回退到 `process.cwd()`——即运行命令时的当前工作目录。[来源](src/utils/workspace.ts#L58-L62)

这里有一个**严格的目录存在性检查**：如果最终确定的路径在文件系统中不存在，直接抛出错误终止流程。这与克隆路径不同——克隆路径会在 `ensureRepo` 中自动创建目标目录。[来源](src/utils/workspace.ts#L60-L61)

## 缓存更新策略：先取后拉的弹性设计

`ensureRepo` 函数（位于 `src/utils/git.ts`）管理着 Git 仓库的获取和更新逻辑。它的核心设计理念是**幂等性与网络容错**。

```mermaid
flowchart LR
    A[ensureRepo 入口] --> B{targetDir 存在？}
    B -->|是, 缓存命中| C[git fetch --all]
    C --> D{branch 指定？}
    D -->|是| E[git checkout branch]
    D -->|否| F[git merge]
    E --> G[git merge origin/branch]
    G --> H[返回 {updated: true}]
    F --> H
    C -->|网络异常| I[返回 {updated: false}]
    I --> J[使用缓存仓库]
    
    B -->|否, 首次克隆| K[git clone]
    K -->|成功| L[返回 {updated: true}]
    K -->|失败| M[抛出 Error]
```

### 首次克隆

当目标目录不存在时，执行 `git clone`。命令构造方式如下：

```
git clone [--depth <n>] [--branch <name>] <url> "<targetDir>"
```

`--depth` 和 `--branch` 都是可选参数，按需拼接到命令字符串中。`stdio: 'inherit'` 意味着 `git clone` 的进度输出会直接透传给终端用户。如果克隆失败，会抛出一个包含原始错误信息的 `Error`，由调用方捕获处理。[来源](src/utils/git.ts#L25-L32)

### 缓存更新

当目标目录已存在（即之前克隆过），系统采用"先取后合"策略：
1. **`git fetch --all`**：从所有远程拉取最新提交，但不自动合并。
2. **分支切换**：如果指定了 `--branch`，执行 `git checkout <branch>` 切换到目标分支。
3. **合并**：有分支时执行 `git merge origin/<branch>`（合并远程跟踪分支），无分支时执行 `git merge`（合并当前跟踪的默认远程分支）。[来源](src/utils/git.ts#L12-L21)

### 网络容错

整个更新操作包裹在 `try/catch` 中。如果 `git fetch` 或后续操作因网络问题失败（例如离线环境），系统不会崩溃——它打印一条警告日志，然后**静默返回 `{ updated: false }`**。调用方据此知道仓库使用的是缓存版本而非最新版本，但仍可正常工作。[来源](src/utils/git.ts#L22-L24)

这种"降级使用"策略对 [`generate`](生成命令-wiki-cli-generate.md) 和 [`ai`](ai-交互命令-wiki-cli-ai.md) 命令尤为重要：分析或问答任务不完全依赖最新代码，缓存版本足以完成大部分工作。

## 清理与生命周期管理

`cleanup` 机制是工作区管理的一个重要设计细节。它只在 `--temp` 模式下被返回，由调用方（如 `generateCommand` 或 `aiCommand`）在任务完成后显式调用。

以 [`generate`](生成命令-wiki-cli-generate.md) 命令为例，其调用流程如下：
1. 调用 `resolveWorkDir` 获取 `workDir` 和可选的 `cleanup`
2. 执行完整的生成管线（大纲→页面→索引）
3. 在 `finally` 风格的代码末尾调用 `if (cleanup) await cleanup()`[来源](src/commands/generate.ts#L105)

这意味着临时克隆的仓库在整个生成过程中可用，但不会在磁盘上留下痕迹。结合 [`断点续传与重试机制`](断点续传与重试机制.md) 中对 `.wiki/temp` 目录的管理，整个工作区生命周期形成一个完整的闭环：从克隆开始，到临时文件清理结束。

## 六种使用场景详解

| # | 命令示例 | 参数组合 | 行为 |
|---|---------|---------|------|
| 1 | `wiki-cli generate` | 无参数 | 使用当前目录作为工作区 |
| 2 | `wiki-cli generate -C /path/to/repo` | `--dir` | 使用指定本地目录，不做任何 Git 操作 |
| 3 | `wiki-cli generate -u https://github.com/user/repo.git` | `--url` | 克隆到 `~/.wiki-cli/repos/user-repo`，后续复用该缓存 |
| 4 | `wiki-cli generate -u https://github.com/user/repo.git -o ./my-wiki` | `--url --output` | 克隆到当前目录下的 `my-wiki`，输出与克隆目录合一 |
| 5 | `wiki-cli generate -u https://github.com/user/repo.git --temp` | `--url --temp` | 克隆到系统临时目录，生成结束后自动清理 |
| 6 | `wiki-cli generate -u https://github.com/user/repo.git -b develop --depth 1` | `--url --branch --depth` | 浅克隆指定分支，适合大型仓库的快速分析 |

### 场景 1-2：纯本地模式

最常见的用法。用户已经在本地拥有代码仓库，`wiki-cli` 直接操作该目录。`--dir` 参数对应 CLI 的 `-C` 选项，与 [CLI 入口点与命令注册](cli-入口点与命令注册.md) 中定义的 Commander.js 参数解析关联。[来源](src/cli.ts#L36-L37)

### 场景 3：默认缓存模式

无 `--temp` 也无 `--output` 时，仓库被持久化到 `~/.wiki-cli/repos/`。第二次对该 URL 运行 `generate` 或 `ai` 命令时，`ensureRepo` 检测到目录已存在，执行增量 `git fetch` 而非完整克隆，大幅加速重复操作。[来源](src/utils/workspace.ts#L24-L27)

### 场景 4：指定输出目录

`--output` 让用户将克隆目标与文档输出目录合二为一。这在 [`配置命令：wiki-cli config`](配置命令-wiki-cli-config.md) 中配置好 LLM 后，直接对远程仓库生成文档并原地保存的场景下特别有用。

### 场景 5：一次性临时克隆

`--temp` 模式适合 CI/CD 管道或一次性实验。`cleanup` 函数确保临时目录在进程退出前被删除。注意临时目录名由 `mkdtempSync` 生成，带有随机后缀，因此**不会与其他并发进程冲突**。[来源](src/utils/workspace.ts#L37)

### 场景 6：分支与浅克隆

`--branch` 和 `--depth` 可以独立或组合使用。`--depth 1` 执行浅克隆，只拉取最新提交，大幅减少大型仓库的克隆时间。如果同时指定 `--branch`，`ensureRepo` 在更新阶段会执行 `git checkout` + `git merge origin/<branch>` 的组合操作，确保工作区与远程目标分支同步。[来源](src/utils/git.ts#L16-L19)

## 与命令系统的集成

`resolveWorkDir` 并非只服务于 `generate` 命令。从 [`cli.ts`](src/cli.ts) 的注册代码可以看出，`ai` 命令同样接受 `-C/--dir`、`-u/--url`、`-o/--output`、`-b/--branch`、`-d/--depth`、`-t/--temp` 六组参数，调用 `aiCommand` 时同样会通过 `resolveWorkDir` 解析工作区。[来源](src/cli.ts#L64-L73)

这意味着工作区管理的两种模式（本地/远程）被 `generate` 和 `ai` 两条命令共享，体现出**关注点分离**的设计原则：工作区解析逻辑封装在 `workspace.ts` 中，命令只需要关心"我在哪个目录下工作"这一结果。
