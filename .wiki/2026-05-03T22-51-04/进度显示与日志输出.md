# 进度显示与日志输出

Wiki CLI 的命令行界面由 **chalk**（彩色文本）和 **ora**（加载动画）两套工具驱动。所有终端输出都集中在 `src/utils/progress.ts` 中，提供了一个**一致且可组合的日志函数集**，便于不同命令模块按需引入。

## 日志函数总览

`progress.ts` 暴露了 8 个函数，覆盖五种日志级别和三种特殊输出场景。

| 函数 | 图标 | 颜色 | 输出通道 | 调用方 |
|------|------|------|---------|--------|
| `logInfo` | ℹ | 蓝色 | `console.log` | generate、ai、browse、git、workspace |
| `logSuccess` | ✔ | 绿色 | `console.log` | generate、ai、browse、config |
| `logWarning` | ⚠ | 黄色 | `console.log` | generate、ai、git |
| `logError` | ✖ | 红色 | `console.log` | cli、generate、ai、browse |
| `logStreamContent` | 无 | 青色 | `process.stdout.write` | 流式生成（直接输出原生内容） |
| `logToolCall` | 🔧 | 品红+粗体 | `console.log` | generate（仅流式模式） |
| `logToolResult` | ↳ | 绿色+灰色 | `console.log` | generate（仅流式模式） |

[来源](src/utils/progress.ts#L1-L37)

### 日志级别的设计意图

`logInfo`、`logSuccess`、`logWarning`、`logError` 这四者覆盖了所有常规交互场景，用法一目了然。但有两个值得注意的设计选择：

- **`logWarning` 的降级场景**：在 [`utils/git.ts`](src/utils/git.ts#L18-L20) 中，当 Git 网络不可达时，`ensureRepo` 函数调用 `logWarning` 告知用户降级为使用缓存——这不是错误，也不该中断流程，因此不用 `logError`。这种做法让**信息等级与流程影响解耦**。

- **`logError` 不终止进程**：所有 `logError` 调用只负责打印，是否退出由调用方决定。例如 [`browseCommand`](src/commands/browse.ts#L12-L14) 在找不到 `.wiki` 目录时打印后调用 `process.exit(1)`，而 [`generateOutline`](src/commands/generate.ts#L206-L208) 中解析失败后只返回空数组。错误输出与错误处理各自独立。

## 🔧 工具调用可视化：logToolCall / logToolResult

`logToolCall` 和 `logToolResult` 是进度系统中**最精细的设计**，它们共同构建了 LLM 工具调用循环的可观察性。

### `logToolCall`

```typescript
export function logToolCall(name: string, args: any): void {
  console.log(chalk.magenta('🔧'), chalk.bold(`Tool: ${name}`), chalk.gray(JSON.stringify(args)));
}
```

输出示例：

```
🔧 Tool: read_file {"path":"src/main.ts"}
```

三个视觉元素逐层递进：**🔧 图标**（一眼识别是工具调用）→ **品红粗体的工具名**（快速定位调用了哪个工具）→ **灰色 JSON 参数**（不刺眼，信息密度高）。

[来源](src/utils/progress.ts#L28-L30)

### `logToolResult`

```typescript
export function logToolResult(name: string, result: any): void {
  const preview = typeof result.data === 'string'
    ? result.data.slice(0, 100) + (result.data.length > 100 ? '...' : '')
    : JSON.stringify(result.data).slice(0, 100);
  console.log(chalk.green('  ↳'), chalk.gray(`Result: ${preview}`));
}
```

输出示例：

```
  ↳ Result: import { ora } from 'ora';\nimport chalk from 'chalk';\n\nexport f...
```

关键设计决策：

- **↳ 箭头缩进**——两个前置空格让结果行从属于上一行的 `logToolCall`，形成视觉上的嵌套结构，一眼看出"哪个工具产生了哪个结果"。
- **100 字符截断**——工具返回的数据可能很长（如整个文件内容），预览只取前 100 字符加 `...`，防止终端刷屏。这是对可读性的主动保护。
- **数据类型自适应**——若 `result.data` 是字符串直接截取，否则先 JSON 序列化再截取，兼容不同工具的输出格式。

[来源](src/utils/progress.ts#L32-L37)

### 调用场景对比：generate vs ai

同一个 `collectFullResponse` 循环中，`logToolCall` 和 `logToolResult` **仅在流式模式（`stream = true`）下触发**：

```typescript
if (stream) logToolCall(tc.function.name, args);
const result = await executeToolCall(tc.function.name, args);
if (stream) logToolResult(tc.function.name, result);
```

[来源](src/commands/generate.ts#L394-L396)

而在 [`ai` 命令的 `chatOnce`](src/commands/ai.ts#L208-L210) 中，工具调用使用更简单的 `logInfo` 输出 `Using tool: ${name}`，不展示参数和结果预览。这意味着两条命令对工具可视性的需求不同——generate 是自动批量生成，用户需要看到每一步的"证据"来建立信任；ai 是交互式对话，工具只是幕后支撑，不应过度显式。

## 加载动画：createSpinner 与 ora 集成

```typescript
export function createSpinner(text: string) {
  return ora(text).start();
}
```

[来源](src/utils/progress.ts#L4-L6)

`createSpinner` 是 `ora` 实例的**工厂函数**，调用即启动。返回的 `Ora` 实例可以后续调用 `.succeed()`、`.fail()`、`.stop()` 等方法控制动画状态。

ora 的注入方式有几个隐含的优势：

- **零配置启动**——调用方只需传入文本字符串，无需处理 `ora` 的构造函数和 `start()` 方法的链式调用。
- **可扩展的封装点**——如果需要统一修改 spinner 样式（如改成不同符号、添加前缀），只需改这一处工厂函数。
- **返回值透明**——直接返回原生 `Ora` 实例，不屏蔽任何下游方法，调用方可以用 `.succeed()` 做成功标记等高级操作。

虽然当前代码库中 `createSpinner` 仅在 `progress.ts` 中定义、尚未被任何命令调用（命令主要依赖日志函数而非 spinner），但这个接口的存在表明了设计上已为未来可能的长时间阻塞操作（如大型仓库克隆、多文件批量写入）预留了位置。

## collectFullResponse 中的流式输出与日志混合

`collectFullResponse` 是 [`generate` 命令](生成命令-wiki-cli-generate.md)的核心函数，负责执行 LLM 的工具调用循环。它巧妙地将**流式内容输出**和**日志标记**混合到同一个终端画面上，形成三段式信息流：

### 第一段：推理过程

当 LLM 返回 `reasoning_content` 时，函数在首次遇到时先打印 `Thinking: `（灰黄色），然后逐个字符追加推理内容：

```typescript
if (!reasoningStarted) {
  reasoningStarted = true;
  process.stdout.write(chalk.dim.yellow('\nThinking: '));
}
process.stdout.write(chalk.dim.yellow(chunk.reasoning_content));
```

[来源](src/commands/generate.ts#L296-L300)

### 第二段：正文内容

推理结束后，LLM 开始输出实际内容。若前一阶段有推理输出，会通过 `console.log('')` 换行分隔：

```typescript
if (!contentStarted && reasoningStarted) {
  contentStarted = true;
  console.log('');
}
currentContent += chunk.content ?? '';
process.stdout.write(chunk.content ?? '');
```

[来源](src/commands/generate.ts#L302-L306)

注意这里使用 `process.stdout.write` 而非 `console.log`——前者不追加换行符，保证了流式输出的连续性。

### 第三段：工具调用日志

当 LLM 决定调用工具时，流输出暂停，进入工具执行阶段：

1. `console.log()` 换行，结束流内容
2. `logInfo("Executing N tool call(s)...")` 告知工具数量
3. 对每个工具，依次执行 `logToolCall` → 执行 → `logToolResult`
4. 结果注入 `messages` 数组后，继续下一轮循环，LLM 再次开始流式输出

[来源](src/commands/generate.ts#L385-L396)

### 非流式模式：无日志

当 `stream = false`（即并行生成模式下），整个 `collectFullResponse` 函数**完全静默**——不做任何 `logToolCall`/`logToolResult`、不输出流内容、也不打印工具执行计数：

```typescript
// 非流式分支中没有任何控制台输出
const response = await client.chat(messages, toolDefinitions, jsonMode);
currentContent = response.content || '';
```

[来源](src/commands/generate.ts#L310-L318)

这使得并行生成时终端干净利落，只有每页完成时的一句 `logSuccess`。

### 完整视觉流

以 Phase 1 大纲生成为例，终端呈现的序列如下：

```
ℹ LLM round 1 (streaming below)...

Thinking: 让我先分析这个项目的目录结构...
（推理内容，灰黄色）

（正文内容，默认色）

🔧 Tool: list_directory {"path":".","depth":2}
  ↳ Result: ├── src/\n│   ├── commands/\n...

🔧 Tool: read_file {"path":"src/main.ts"}
  ↳ Result: import { ... } from './...\n...

ℹ Executing 2 tool call(s)...

（第二轮 LLM 输出...）
```

这种设计让用户不仅能看见最终结果，也能看见 LLM 的**思考过程**和**行动轨迹**——这是可解释 AI 在命令行界面中的一次务实落地。
